## 三种状态

## 1. 架构分层

### 1.1 内嵌 kiro.rs 到 bus-pooling 单进程 ❌
- **提议**：把 kiro.rs 号池能力做进 bus-pooling 自己的进程里
- **否决**：kiro.rs 已经作为独立服务运维（`kiro.aibbq.xyz`），是**外部依赖**；本项目只做它的 client
- **替代**：`internal/housepool/kirors/` 客户端调 kiro.rs admin API

### 1.2 用数据库替代 housepool ❌
- **提议**："housepool 的价值就是数据回流，用数据库也能做"
- **否决**：数据库只能记账（"这号归谁"），但**运行时**能力（校验凭证、存活探测、用量追踪、分组、并发监控 5 项）**必须号池实现才有**
- **参考**：`01-architecture.md §2 Layer 4`

### 1.3 拉号记录 = 独立数据库表（不进 housepool）❌
- **提议**：单独拉号的号先在数据库里躺着，用户派去向后再进 housepool
- **否决**：**要监控就必须进 housepool**（否则 5 项能力全废）。这些号也需要平均寿命统计
- **替代**：拉号记录 = **housepool 里的 `record-<pid>` group + `disabled=true`**（号已进池、已监控、不发下游）

### 1.4 号推给 passengerpool = 号离开系统 ❌
- **提议**：号一推到乘客的 kiro.rs 就完成交付，我方不再跟踪
- **否决**：**要监控存活就得留副本**。推给 passengerpool 是**双写** —— housepool 保留副本（我方监控），passengerpool 是复制品（乘客用）
- **例外**：只有**去向 ③ handoff（拿走）**才是真正离开系统，我方 `DELETE /credentials/{id}` 后不再跟踪

### 1.5 fire-and-forget 一律不管 ❌
- **提议**："发出去就不管了"
- **否决**：只有 handoff（拿走号数据）才 fire-and-forget。**推 passengerpool 是双写还监控**、进 bus 也监控
- **参考**：`00 §5 用户路径` 3 种去向表

### 1.6 provider 抽象层可以省 ❌
- **提议**：只有一个 provider（kiro），直接把 6 家 vendor 平铺在 `internal/vendors/`
- **否决**：未来加 `cursor` 等 provider 时会撞车
- **替代**：`internal/providers/kiro/vendors/*`；加新 provider 只加 `providers/<name>/`

### 1.7 kiroclient 命名放顶层 ❌
- **提议**：`internal/kiroclient/` 顶层
- **否决**：号池承载**当前**是 kiro.rs，未来可能换其他实现；按"层职责"命名而非"具体实现"命名
- **替代**：`internal/housepool/kirors/`

### 1.8 混淆"我方号池"和"乘客号池"❌
- **提议**：两个 kiro.rs 都叫"号池"或"pool"
- **否决**：**两个不同实体**：
  - 我方 = `housepool`（Layer 4，我方基础设施）
  - 乘客 = `passengerpool`（Layer 5 交付目标，外部系统）

## 2. 收费 / 商业模式

### 2.1 卖号（加价 pass-through 差价）⏸
- **提议**：我方在 vendor 号价上加价卖
- **当前不做**：号价永远 pass-through，我方只赚服务费（`00 §1 是什么/不是什么`）
- **未来可能做**：**利用 vendor 的开号能力**（乘客上传 AWS → 我方转发 vendor 开号，见 §5.1 阶段 3b/3c）→ 号进**公开池 / 市场**（阶段 3d）→ 卖给其他乘客 → **这条路径有利润空间**
- **关键区分**：**"我们不做开号"**（不复刻 vendor 的开号系统） ≠ **"我们不做号买卖"**（未来通过市场可以做）

### 2.2 会员制 / 订阅制 ⏸
- **提议**：月付订阅费享受服务费打折 / 优先撮合 / 优先补车 / 数据看板
- **当前不做**：阶段 1/2 先跑"每次固定服务费"的按需模型
- **未来可能做**：跟拼车主线不冲突，等有稳定用户量再评估

### 2.3 长效号预留池 ⏸
- **提议**：从平均寿命高的 vendor 定期拉号、储备一个小池，预付进入"长效池会员"
- **当前不做**：还没有"长效号"这种类型（vendor 未提供），也无平均寿命历史数据
- **未来是议价空间**：等阶段 1d 采集足够寿命数据后可以评估。**"长效号"是我方少数能提供的稀缺资源**，值得少量储备 → 议价空间
- **参考**：`00 §9 未来增值方向 · 长期稳定号源`

### 2.4 数据看板"作为收益点"（订阅 / API 收费）❌
- **区分两件事**：
  - **数据看板功能** —— 阶段 3a 要做（`00 §7 · 阶段 3a`），乘客和管理端都能看到平均寿命 / 价格趋势 / 缺货率等
  - **数据看板作为收益点**（订阅制收费卖数据 / API 卖看板数据）—— **不做**
- **否决理由**：跟"公益工具"人设不匹配。数据看板是**产品能力**，不是**收费点**
- **不影响**：阶段 3a 的数据图表功能照常做

### 2.5 API 售卖（"我们推自己的池 API 卖"）✅
- **提议**：我方直接用 API 卖自己 kiro.rs 号池给乘客
- **接受，且不需要任何新功能**：**把我方运营账号当作一个普通乘客**，用已有的乘客侧 API（`05-api-contract.md` §5 单独拉号 + `06-scenarios.md` B4 handoff / B3 推 passengerpool）即可完成"卖 API"的全部动作
- **明确不做的形态**：**API 拼车**（把 API 调用本身做成拼车）—— 太复杂，用户明确不搞
- **未来加值**：接入合作下游产品直接消费我方 API（`00 §9 · 合作下游消耗`）

### 2.6 & 2.7 · 稳定优先附加能力（排噪邻 + 优先撮合，打包）⏸
- **提议**：拼车时排除高流量成员 + 撮合优先级更高，打包 +20%
- **当前不做**：先不设限制，阶段 2c 压车治理数据成熟后作为附加能力候选实施
- **完整描述已在**：
  - `00 §9 未决 · 附加能力插槽候选清单 · 稳定优先`（含触发规则：手动勾 or 策略参数含 RPM/TPM 要求）
  - `00 §3 计费模型`（附加能力插槽定义 + 加法顺序）
- **本条只做交叉引用**，不重复叙述

### 2.8 指定 vendor 议价 ⏸
- **提议**：用户指定 X 家 vendor → 加价（限制我方选择）
- **当前不做**：跟"公益"人设不匹配；用户可以指定 vendor 但不加价，属于普通拉号
- **未来可能**：若有场景表明"指定 vendor"确实消耗我方资源，可作为附加能力候选

### 2.9 寿命 SLA 议价 ⏸
- **提议**：用户要求"平均寿命 ≥ X 小时" → 加价
- **当前不做**：**没有历史数据可用**（阶段 1 才开始采集平均寿命）
- **未来可能**：阶段 1d 后有数据再评估。可能与 2.3（长效号预留池）合并考虑

### 2.10 地区议价（海外 +20% / 国内 0）⏸
- **提议**：海外用户加 20%
- **当前不做**：**无法可靠识别**海外/国内：
  - 注册选地区 —— 无法校验
  - IP 定位 —— VPN 可绕
  - 支付通道 —— waffo 单通道不支持币种区分
- **未来可能**：等阶段 2+ 接入多通道（微信/支付宝/信用卡），按通道自然分层（"通道即价目"）；阶段 1 **统一定价**

### 2.11 CNY/USD 双币种价目表 ⏸
- **提议**：用户充值币种自选，CNY 走国内价、USD 走海外价
- **当前不做**：waffo 不收 RMB，单一币种，无法区分
- **未来可能**：同 2.10，等多通道再启用

### 2.12 IP + 手机号 + 时区多信号识别 ❌
- **提议**：多信号打分判定海外/国内
- **否决**：合规风险（跨境用户地区判定敏感）+ 用户可绕，误伤高
- **替代**：同 2.10 走通道自然分层

### 2.13 通道费我方承担 / 我方加收 5% ❌
- **提议**：(b) 我方承担 waffo 5% 通道费 / (c) 我方在通道费上再加收 5% 作为额外收入
- **否决**：违背 pass-through 人设
- **保留**：(a) 通道费 pass-through 给乘客，waffo 收，不进我方账

### 2.14 议价加在总价上 ❌
- **提议**：`总价 × (1 + 议价率)`
- **否决**：用户明确"附加费加在号价上，不加在总价"
- **保留**：`(号价 + 议价) + 服务费` → `× (1 + 通道费)`

### 2.15 一轮 = 一个号 ❌
- **提议**：拉 10 个号 = 10 轮，服务费 × 10
- **否决**：用户原话"每人每轮 1 元，18 轮就是 18 元"—— 一轮 = **一次拉号动作**
- **保留**：**1 轮 = 1 次拉号动作**（不管这次拉几个号）
- **推论**：批量天然便宜（拉 10 个号 1 元服务费 vs 分 10 次拉 10 元服务费），符合"鼓励批量"

### 2.16 退款支持现金 / 退到 payment-gateway ❌
- **提议**：号死了退现金给乘客
- **否决**：我方**只退积分，不退款 / 不退现金**
- **保留**：`wallet` 加积分 + ledger 落 `warranty_refund`；服务费 / 通道费 / 过窗口的号 **不退**
- **参考**：`00 §3 退款原则` + `§7.5 规则 B`

### 2.17 独立质保（超出上游窗口） ❌
- **提议**：我方对乘客做独立质保（例：号死 60 分钟内退款）
- **否决**：质保**完全跟随上游 vendor**，上游过窗口不退我方也不退
- **参考**：`00 §7.5 规则 B`

## 3. bus / 号 / 上车

### 3.1 solo bus / pooled bus 概念 ❌
- **提议**：区分 solo bus（独享）和 pooled bus（拼车）为两种类型
- **否决**：造成命名混乱。**1 人 bus 也是 bus**，多人 bus 也是 bus，都在 `bus-<id>` group
- **保留**：`bus.kind` 字段可以是 `single` / `anon` / `team`，但**都叫 bus**

### 3.2 mode: carpool / solo 二选一 ❌
- **提议**：策略参数带 `mode: carpool | solo`，二选一决定去向
- **否决**：号的去向由分配决定，不是 mode 二选一
- **参考**：拉号 ≠ 上车（`00 §5`）

### 3.3 混合上车（一次拉号分头上多 bus）❌
- **提议**：一次拉 10 个号，5 上 bus X + 5 上 solo bus + `allocation_plan`
- **否决**：**用户否决**（"什么混合上车是什么鬼"）
- **保留**：单独拉号后号进 `record-<pid>` group，用户再对每号选去向

### 3.4 allocation 组件 ❌
- **提议**：单独设 `internal/allocation/` 分配器
- **否决**：跟 3.3 一起否决
- **替代**：`internal/pullrecord/` 承担"派去向"职责

### 3.5 用 `personal-<pid>` group 表示乘客个人号池 ❌
- **提议**：housepool 里有 `personal-<pid>` 这种 group 表示乘客的号
- **否决**：**号池 = 乘客的 passengerpool（外部）**，我方 housepool 里的 group 不叫"号池"
- **替代**：叫 `record-<pid>`（拉号记录 group），只是号"归属"，不叫"号池"

### 3.6 拉号记录 = 数据库表（不进 housepool）❌
- 见 1.3

### 3.7 号归属 = Bus（不是乘客）✅
- **提议**：号在 credential_ledger 有唯一 owner
- **决策**：**号归属 Bus（`owner_bus_id`）**，成员通过 `bus_member` 表拿访问权
- **理由**：拼车语义 = "大家一起养的号"；owner 归 Bus 后：
  - 退出 Bus 不影响号（号仍在 bus group）
  - 解散 Bus 才需要决定号归谁（阶段 1a 简化：解散时号 handoff 给创建人 or 死号扫掉）
  - 拼车分摊 / 补车 / 退款 都以 Bus 为主体
- **单独拉号进 record group** 的号：`owner_bus_id = NULL, owner_record_passenger_id = <pid>`
- **参考**：`06-db-schema.md § 11 credential_ledger`（CHECK 约束保证 XOR）· `09-transactions.md`

## 4. 概念 / 术语作废

### 4.1 用 `carpool / car / carpool_room / carpool_id` ❌
- **提议**：英文命名用 car / carpool
- **否决**：用户明确"没有 car 这个概念"
- **保留**：**统一用 `bus`**（`bus_id`、`bus-<id>` group）

### 4.2 "方式 A / 方式 B" ❌
- **提议**：交付分方式 A（推 passengerpool）和方式 B（乘客调 API 拿）
- **否决**：把**入口**和**去向**糊在一起了
- **替代**：**3 种去向**（进车 / 推 passengerpool / handoff）+ **2 种入口**（UI / API）正交

### 4.3 "上车 = 独享/多人拼车" ❌
- **提议**："上车"泛指号分配到任何 group
- **否决**：号只有一个物理位置（housepool），"上车"这种动作性词汇没实质
- **保留**：只用**去向**表达

### 4.4 P0 / P1 / P4a / P∞ 等 P 标签 ❌
- **提议**：延续旧项目的 P0-P∞ 阶段命名
- **否决**：粒度过细
- **替代**：**3 大阶段 + 内部 milestone**（1a / 1b / 1c / 1d / 1e / 2a / 2b / 2c / 3a / 3b / 3c / 3d）

## 5. 未来产品线

### 1.9 用 SuperTokens 做登录方案 ⏸
- **提议**：用 SuperTokens 或 Casdoor / Ory Kratos 等外接身份管理服务
- **当前不做**：项目是公益工具（`README.md`），阶段 1 只需要"登录 / 登出 / API key"三件事，**Go 自建约 200 行代码**就够（Argon2id + session cookie）
- **未来可能做**：如果需要邮箱验证 / 忘记密码 / 社交登录（Google / GitHub）→ 阶段 3+ 用户量稳定后可评估接入 SuperTokens 或 Ory
- **参考**：`03-modules.md · authpassenger`；密码哈希算法用 Argon2id（跟登录方案是两回事，见对话记录）

### 5.1 散户切片（一把 key 切多份卖给小散户）⏸
- **提议**：用 kiro.rs `CreateClientKey(usage_limit)` 把一把号的额度切成多份卖
- **当前不做**：不是拼车主线，避免混乱；kiro.rs 天然支持但先聚焦拼车
- **未来可能做**：作为**独立产品线**（不并入拼车），阶段 3 之后再评估

### 5.2 数据图表作为收益点 ❌
- 见 2.4（数据看板功能仍做，只是不作为收益点）

### 5.3 拉号记录 N 天过期策略 ❌
- **提议**：拉号记录里号 N 天未处理 → 自动搬迁 / 提醒
- **否决**：**"过期"= 号本身死了**（vendor 判死），不是按 N 天计时
- **保留**：号还活但用户 N 天没处理 → 只**提醒**，不自动搬迁（尊重用户选择权）

## 7. 议价 / 计费历史（速查）

用户拍板的当前收费点（`00 §3` 权威）：

| 项 | 归属 | 说明 |
|---|---|---|
| 号价 | vendor（pass-through） | 拼车按 N 摊 |
| 单次议价 | 我方 | `count==1` 时号价 × 20% |
| 附加能力费 | 我方 | 插槽，可累加多项；阶段 1 无实例 |
| 服务费 | 我方 | 每人每次拉号动作固定 1 元 / 1 USDT |
| 通道费 | waffo（pass-through） | 5% × 小计，充值时扣 |

**议价加在号价上**，通道费加在（号价+议价+服务费）小计之上。

## 8. 前端 UX / 首页结构（阶段 1a mockup 定型）

### 8.1 全局搜索 / ⌘K 命令面板 ⏸
- **提议**：顶栏加全局搜索或 Cmd-K 命令面板（Linear / Superhuman / Arc 风格）
- **否决当前阶段**：阶段 1 数据量小（一个用户几辆车、几十号、几十条记录），翻页 + 筛选够用；用户是消费端普通乘客，不是效率工具用户；Apple Pay / Cash App 也没有全局搜索
- **重启条件**：车 / 号 / 记录列表大到用户找不到时，考虑**局部筛选**（车列表页顶部一个筛选框）—— 但**不做 ⌘K 全局命令面板**
- **参考**：`design/design-brief.md`（顶栏元素）

### 8.2 顶栏结构 · 左对齐 5 tab + 头像 dropdown ✅
- **决定**：顶栏 = K logo · 左对齐 5 tab（概览 / 拼车 / 提取 key / 我的发车 / 对接文档）· 右侧 3 元素（余额 chip / 通知 / 头像）
- **头像 dropdown 内容**：**我的**（用户名 → `/me`）· **设置**（→ `/settings` 索引页）· 语言 · 主题 · 登出
  - **「设置」是真的主入口**：`/settings` 是索引页，下面挂三类设置（我的号池 / 机器人通知 / API key）· dropdown 里**不再**把这三项跟「设置」并列（并列等于说它们跟设置平级，是另外三件事）
  - **「我的」在 `/me`，不在 `/settings/profile`** —— 账号本身不是一种设置；`/me` 也跟 API 的 `GET /api/me` 对齐

### 8.25 待派 key 的可用性 + 推送失败的结构化错误 ✅

#### 决定 1 · 待派列表必须标可用性，失效的禁止选中

**真实场景**（车主提出）：
- 拉下来的号**放半天没派**，中途挂了
- 号**刚拉下来就挂了**（走质保退款）

失效的号推不上去、进车也没意义，所以：
- 列表每行标状态 Chip：**正常**（ok）/ **质保内失效 · 可退**（warn）/ **已失效**（danger）
- 失效行 `checkbox disabled` + 整行 `opacity-55` + key 加删除线 + 整行不可点
- **全选只选可用的**（`items.filter(status !== 'dead')`）
- 副标显示「可用 N 个 · K 个已失效（不能派）」

**质保区分**：`warranty_until > now` 的失效号标「可退」—— 这是刚拉就挂的情况，用户能拿回积分；过了质保只能认（放太久没派）。

#### 决定 2 · 推送失败要结构化，不能只给一句文案

**原来**：`push_error: string`（一句人话）· 客服/用户都判不了该干什么。

**改成** `PushError` 结构（`web/src/types/index.ts`）：

| 字段 | 用途 |
|---|---|
| `code` | 内部稳定标识 · **判 code 不判文案**（跟 vendor 档案 §12 同原则） |
| `status` | 目标号池返回的 HTTP 码 · `null` = 没连上（超时/DNS） |
| `message` | 给用户看的人话 |
| `retriable` | **重试有没有意义** —— 决定 UI 给「重试」还是「去检查配置」 |
| `attempts` / `last_attempt_at` | 已试几次 · 什么时候 |

`code` 枚举：`unauthorized`（401/403 token 失效）· `not_found`（404 路径错）· `conflict`（409 已存在）· `timeout` · `unreachable`（DNS/拒连）· `rate_limited`（429）· `server_error`（5xx）· `bad_response`

**UI**（推送记录 tab）：
- 失败行直接显示 `message` + 状态码 badge
- `retriable: true` → 给「重试」按钮（title 显示已试几次）
- `retriable: false` → 给「去检查」跳 `/settings/downstream`（重试无用，要先改配置）

#### 决定 3 · 余额不足不会跟推送失败混（车主的顾虑，澄清）

两个**完全不同的域**，不可能误判：

| 域 | 谁返回的错 | 典型 code |
|---|---|---|
| **拉号** | vendor | `insufficient_balance` 402（我方在 vendor 余额不足）· `no_stock` 409 · `purchase_cap_reached` 409 |
| **推送** | 用户自己的号池 | 401 token 失效 · timeout · 409 已存在 |

**推送不涉及任何扣款** —— 号价在提取时已付（§8.21），推送只是把号复制给用户号池。所以 `insufficient_balance` 在推送域**永远不会出现**。

#### 决定 4 · 术语：悬浮栏「进车」改「加入拼车」

「进车」太简省，用户看不出是加入哪个东西。统一成「加入拼车」（跟顶栏「拼车」tab 呼应）。弹窗标题同步改「确认加入拼车」。

**参考**：`docs/vendors/91kiro.md §12`（错误码表 · 判 code 不判文案）· `§8.24`（售后追溯）· `§8.21`（通道费只在充值收）

### 8.24 号交付后的售后追溯 · 台账永不删 + masked 可查 ✅（补 `09-transactions.md §4` 的缺口）

**车主提出**：号不能立马清理干净，数据库起码得有记录 —— 万一没推成功、或者号有问题，用户找客服时无据可查。

**先澄清已有机制**（`09-transactions.md §4`）：
- handoff 已经是**两阶段 token 交付**（init → fulfill → confirm 才 DELETE），5 分钟 TTL 内可重试 GET 明文
- **这解决的是「下载时网络断线」**，不是售后
- `credential_ledger`（`06-db-schema §11`）**是永久台账，行永不删** —— housepool 里 DELETE 的是明文，台账留着

**真正的缺口**（现有机制没覆盖的）：

| 场景 | 现状 | 缺口 |
|---|---|---|
| 下载时断线 | ✅ 5 分钟 TTL 内重试 | — |
| 下载成功但**号推不上去 / 号本身有问题** | ⚠️ 台账有行 | 台账**没存 masked**，客服对不上用户说的号 |
| 用户**几小时后**说「这号有问题」 | ⚠️ 同上 | 没有工单/申诉入口 |

#### 决定 1 · 台账补三个售后字段（阶段 1b）

`credential_ledger` 加 `key_masked` / `region` / `credits_used`（见 `06-db-schema §11.1`）：
- `key_masked` **不是明文**（`ksk_live_9f4a…vn6` 只有前缀+后 3 位）· 可以安全长期保留
- 号入池时写入，交付/失效后不再变更（快照语义）
- 客服工作流：用户报 masked → 查台账 → 看到 vendor / 拉号时间 / 交付时间 / 已耗额度 / 死亡来源 → 判断质保内否、要不要退

#### 决定 2 · 台账永不删（阶段 1b）

- **不设保留期限** —— 台账行不含明文，体积极小（一行几十字节），没有清理必要
- housepool 里 DELETE 明文 ≠ 台账删行 · 两件事分开
- 这也是 `§8.22 价格走势` / `§8.19 数据 tab` 的数据基础 —— 删了历史统计就断了

#### 决定 3 · 推送失败要留错误原因（阶段 1b）

`credential_ledger.passengerpool_push_error` 字段已有，但要保证：
- 推送失败**不重置**该字段（保留首次失败原因，便于客服判断是用户 URL 配错还是我方问题）
- 重试成功后写 `pushed_to_passengerpool_at`，`push_error` **保留**（历史痕迹）
- UI：推送记录 tab 的失败行可展开看错误原因

#### 决定 4 · 申诉入口 ⏸（阶段 1c）

阶段 1a/1b **不做工单系统**（一个人运维，上工单系统是负担）。替代：
- 号列表 / 派发历史每行给「反馈问题」入口 → 预填 masked + 时间 + vendor → 走社群（TG / Discord）
- 客服（= 车主自己）拿 masked 去台账查
- 等用户量起来再评估要不要真做工单（阶段 1c 后）

**明确不做**：
- ❌ 保留明文备份「以防用户丢失」—— 违背 `CLAUDE.md §1.2` handoff 语义 + 合规风险（明文一秒不留是产品承诺）
- ❌ handoff 后可重新下载 —— 同上（UI 已明确告知「无法重新下载」）
- ❌ 延长 handoff TTL 到几小时 —— 明文在我方多留一秒都是风险，5 分钟够断线重试

### 8.32 三种码 · 各减免什么 + 加价栈定稿 ⏸（阶段 1b · **服务费口径 1 处待定**）

**车主原话**：
> 有系统邀请码，进去是没有区域附加费的。我们是 20% 单次/批量 + 20% 区域附加费 + 服务费（**感觉其实服务费按百分比更合理**）的，系统邀请码可以减免区域附加费，个人邀请码是按限制减免，限制过了就恢复了，比如减免的是充值通道费 5%（限次数或者限时）。随机的邀请码，这个是临时少量的，支付的时候少比如 20% 按此的。可能就是比如单次的有这个相当于可以把这个减免掉，批量的相当于更优惠了。但是我可能不会这么高，可能少 5% + vendor 附加费，是我们 vendor 定价的基础上加价，比如 5%。我们是多插槽的。

#### 三种码 · 职责完全不同（这是本条的核心）

| | **系统邀请码** | **个人邀请码** | **随机优惠码** |
|---|---|---|---|
| 谁发 | 我方 → 社群 | 每个乘客自动有 | 我方临时少量发 |
| 填在哪 | **注册时** | 注册时 / 使用时 | **支付 / 提号确认窗** |
| 减免什么 | **区域附加费 20%** | **充值通道费 5%** | 提号时**减 5~20%** |
| 持久性 | **永久绑账号** | **限次数或限时**，用完/过期就恢复 | **单次** |
| 解锁 vendor 真名 | ✅ | ❌ | ❌ |
| `passenger.invited` | `true` | 不变（仍 false） | 不变 |

**三条互不重叠** —— 各自减免的是**不同的费用项**，所以可以叠加（一个人可以同时是社群身份 + 有个人码额度 + 本次用了优惠码）。

**个人邀请码减免的是通道费**（车主明确说的）。这跟我上一轮 `§8.29` 写的「减免服务费」**不一样，按车主的改**。但要记清代价：

- 通道费是 **waffo 实收的 5%**，我方减免 = **我方自掏腰包垫付**
- 这**违反** `00 §3` / `§2.13` 的「pass-through，我方不加不承担」原则
- **但车主明确要这么做**，所以它不是"违反"而是**有意的营销支出** —— 类似"充值返现"
- 正因为是真金白银的支出，「**限次数或限时**」这个约束**不是可选项，是必须的**（车主也这么说了）· 必须有硬上限，否则是无底洞
- 会计上要**单独记一个科目**（`channel_fee_subsidy`），不要混进 `channel_fee` —— 否则财务上看不出补贴了多少

#### 加价栈定稿

```
号价（vendor 报价 · 按 vendor_pricing 换算成积分）
  + vendor 附加费     号价 × 5%（每家可不同 · 在我方 vendor 定价基础上加）
  + 区域附加费        号价 × 20%   ← 有系统邀请码则免
  + 单次议价          号价 × 20%   ← 仅 count==1
  + 插槽（多个）      号价 × N%    ← capability / adhoc · 动态增减
  + 服务费            ⚠️ 固定两档 or 百分比 · 见下面待定
  ──────────────────────────────
  = 本次扣除

（充值时另收）通道费 5% → 个人邀请码可在限额内减免
（提号确认窗）随机优惠码 → 减 5~20%
```

**「多插槽」= `§8.30 B` 那张 `surcharge_rule` 表**：上面每一项（vendor / region / capability / adhoc）都是表里一行，`applies_when_json` 控制什么条件开启、`waived_when_json` 控制什么条件减免。加新收费点 = 插一行，不改代码。这正是车主要的"控制哪个开启，什么条件开启，什么条件减免"。

#### 随机优惠码的额度 · 5% 还是 20%

车主自己在原话里推翻了一次：先说 20%，又说「**我可能不会这么高，可能少 5%**」。

他观察到的那个效应是对的：
- **20% 的码 + `count==1`** → 正好抵掉单次议价，等于"单拉也不罚"
- **20% 的码 + 批量**（本来就没单次议价）→ 净赚 20%，**批量反而更优惠**

这个"批量更优惠"的方向跟 `00 §3`「天然鼓励批量」一致，不冲突。但 20% 对批量单是纯让利，成本不低。

**建议：额度做成后台可配（`coupon_code.discount_bp`），默认 5%，需要冲量时临时发 20% 的。** 不写死在代码里 —— 这本来就是"临时少量发"的营销工具。

#### ⚠️ 待定：服务费按百分比还是固定两档？

车主这次说「**感觉其实服务费按百分比更合理**」，但上一轮刚定了两档固定（`§8.31`：社群 1 / 零售 7 积分）。**这两个方向互斥，得选一个。**

**百分比制的代价（必须知道再决定）**：

`00 §3` 有一条推导 —— 「我方收入 = Σ轮数 × **固定**单价」→ 所以「**我方没有动机加价号成本**」。这是写进价值观的**对齐激励**。服务费改成百分比后，号价越高我方赚越多，这条推导就不成立了。

**但**：`vendor 附加费` 和 `区域附加费` 本来就是按号价百分比的 —— 所以**这个激励其实已经部分破了**。服务费再改百分比，只是让它破得更彻底一点，不是从 0 到 1。

**两种制度的实际差异**（以零售用户为例，假设百分比取 10%）：

| 号价 | 固定制（7 积分） | 百分比制（10%） | 差异 |
|---|---|---|---|
| 拉 1 个 · 20 积分 | +7（**占号价 35%**） | +2 | 固定制贵得多 |
| 拉 1 个 · 100 积分 | +7 | +10 | 百分比制略贵 |
| 拉 10 个 · 200 积分 | +7（**占 3.5%**） | +20 | 百分比制贵 3 倍 |

**关键差异不在贵贱，在结构**：
- **固定制**：小单贵（7 积分对 20 积分的号是 35% 的税）· 大单几乎免费（3.5%）· **强烈鼓励批量**
- **百分比制**：跟单量无关，永远同一比例 · **对批量没有额外激励**，而且大单绝对额高
- 现在「单次议价 20%」已经在惩罚小单了，固定服务费是**第二层**惩罚 —— 两者叠加，小单可能贵到没人拉

**我的建议：保持固定两档，理由是它跟"鼓励批量"这个产品目标一致**（拼车的本质就是凑批量）。如果嫌 7 积分对小额号太重，调低零售档（比如 3-4 积分）比改成百分比更简单，也不动对齐激励。

**但这是你的商业判断，不是技术问题** —— 你说改我就改，代码里 `serviceFee()` 已经收口在一处，改动很小。**改之前告诉我**，因为它决定 `pull_round` 的计费字段怎么存。

### 8.31 服务费两档 · 社群 1 积分 / 零售 7 积分 ✅（定了 `§8.30 待确认 ①`）

**车主原话**：
> 服务费有系统邀请码是 1 积分，没有系统邀请码是 1$，1 积分 = 1RMB，没有系统邀请码是 7 积分约等于 1 $

| 身份 | 服务费 / 人·轮 | 判据 |
|---|---|---|
| **社群** | **1 积分**（= 1 RMB） | 注册时填了**系统**邀请码 → `passenger.invited = true` |
| **零售** | **7 积分**（≈ 1 USD） | 没填 / 只填了个人码 → `invited = false` |

**这解掉了 §8.30 待确认 ①，而且不是原来给的两个选项** —— 既不是"固定 1 元"也不是"1%"，是**两档固定费**。

**关键：仍是固定费** → `00 §3` 的对齐激励（**我方没有动机加价号成本**，因为收入 = Σ轮数 × 固定单价，跟号价无关）**完整保住**。百分比制才会破坏它。

#### 三条实现约束

1. **7 是定价档位，不是实时汇率**
   - 不接汇率 API 算这个数。汇率波动让用户看到服务费每天变是糟糕体验，而且 1 USD 这个量级下汇率波动的绝对值很小，不值得引入外部依赖 + 失败面
   - 真实汇率只用于 **vendor 成本换算**（`vendor_pricing.credits_per_unit` · `§8.30 A`）—— 那是我方成本，跟对用户的定价档位是两回事
   - 汇率长期漂移到 7 明显不合理时，**手工改这个常量**（后台可配）

2. **优惠码不改档位**
   - 优惠码只免**零售附加费**（`§8.20`）· 服务费档位**只看注册时的系统邀请码**
   - 理由：档位是**身份**（永久绑账号），优惠码是**单次减免**。让优惠码能降服务费档，等于把永久身份变成一次性可买 —— 社群身份就不值钱了

3. **个人邀请码不给社群档**
   - `§8.29` 已定个人码不解锁社群身份 · 本条让那个区分**更值钱**了（差 7 倍不是 20%）
   - 所以 `§8.29` 那个"邀请奖励 = N 轮服务费全免"对**零售**邀请人价值 7 倍于社群邀请人（3 轮 = 21 积分 vs 3 积分）· 这个不对称是合理的（零售本来付得多）

#### 零售总成本的量级（拍这个数之前先看清）

拉 1 个 20 积分的号：

| | 社群 | 零售 |
|---|---|---|
| 号价 | 20 | 20 |
| 零售附加费 20%（§8.20） | 0 | +4 |
| 单次议价 20%（count==1） | +4 | +4 |
| 服务费 | +1 | **+7** |
| **合计** | **25** | **35** |

**零售比社群贵 40%**。批量拉时差距收窄（服务费按轮不按号）：拉 10 个 → 社群 201 / 零售 247，贵 23%。

**这是主要的变现杠杆**，也意味着**社群邀请码的分发要克制** —— 发滥了收入结构就塌了。

#### 待确认（多人车 · 不挡 1a）

多人车里成员身份可能不同（2 个零售 + 1 个社群），服务费是「**各人按自己的档位付**」还是「**按 share_pct 分摊总额**」？

- 我倾向**各人按自己档位付**：服务费是"每人每次动作"的固定费，本来就不分摊（`00 §3` 明确写了"固定，不分摊"）· 3 人车一轮 = 7+7+1 = 15 积分
- 阶段 1a 全是 1 人车，不挡开工 · 2a 做多人车分摊时定

#### 落地

- `serviceFee(invited)` 已收口在 `web/src/lib/utils.ts`（前端 4 处硬编的 1 积分已改）
- 后端：`pull_round.service_fee_total` 按**参与人各自档位求和**算，不是 `人数 × 单一费率`
- **服务端裁定，不信客户端** —— 前端算的只是预览

### 8.30 加价栈重构 · vendor 定价配置 + 统一 surcharge 插槽 ⏸（阶段 1b）

**车主原话**：
> 我们后台或者服务配置，最好每个 vendor 对应有他的积分价格、vendor 积分对 rmb 还是 usd、对应价格是多少、转换 rmb 或 usd 是多少。我们每个 vendor 的加价控制之前是 1% 的服务费，内部还要有个加价。比如活得特别长的车可能临时加价。所以我们是 vendor 附加费 + 服务费 + 区域附加费 + 零售附加费 + 插槽（可动态增加减少）控制哪个开启，什么条件开启，什么条件减免。

#### A. vendor 定价配置（无冲突 · 直接做）

`07-provider-contract §161-166` 已经暴露出这个需求：**各家 vendor 的价格口径本来就不一致** ——

| vendor | 价格字段 | 币种 |
|---|---|---|
| 91kiro / kiroceo | `zones[].unit_price` | CNY |
| kirooo | `key-price-tiers` **阶梯**（产量越大单价越低） | CNY |
| kiroappio | `price_min` / `price_max` **区间** | CNY |
| **kirodrop** | `stock.price` | **USD** |

那份文档里写了「混币在 decider 里换算」但没定换算表在哪。落成一张配置表：

```sql
CREATE TABLE vendor_pricing (
  vendor_id            TEXT PRIMARY KEY,
  -- vendor 报价的原始币种（我方不改它，只做换算）
  quote_currency       TEXT NOT NULL,          -- CNY | USD
  -- 换算成积分的汇率 · 1 积分 = 1 CNY（decisions §8.7）
  -- CNY 家填 1_000_000（1:1）· USD 家填当期汇率 × 1_000_000
  credits_per_unit     INTEGER NOT NULL,       -- microunit
  rate_source          TEXT,                    -- manual | 汇率 API 名（阶段 1b 先 manual）
  rate_updated_at      TEXT,
  -- 该 vendor 的附加费（我方内部加价 · 见 B）
  vendor_surcharge_bp  INTEGER NOT NULL DEFAULT 0,
  active               INTEGER NOT NULL DEFAULT 1,
  updated_at           TEXT NOT NULL
);
```

**汇率阶段 1b 手工配**（`rate_source='manual'`）—— 接汇率 API 是额外的外部依赖和失败面，等 USD 家的量起来再说。手工配的风险是汇率漂移吃掉利润，所以 `rate_updated_at` 要在后台显眼处提示"多久没更新了"。

#### B. 统一 surcharge 插槽（**推荐把 5 类合并成一张表**）

车主列的 5 类：`vendor 附加费 + 服务费 + 区域附加费 + 零售附加费 + 插槽`。其中"插槽"本来就是 `capability_slot`（`06-db-schema §15`），而前 4 类的结构完全一样（都是"某条件下按号价加 X%"）。**建议合并成一张 `surcharge_rule`**，`capability_slot` 并入它：

```sql
CREATE TABLE surcharge_rule (
  id                  TEXT PRIMARY KEY,
  kind                TEXT NOT NULL,          -- vendor | zone | retail | capability | adhoc
  name                TEXT NOT NULL UNIQUE,   -- 'retail_markup' | 'zone_eu' | 'long_life_bump' …
  rate_bp             INTEGER NOT NULL,       -- basis point · 2000 = 20%
  base                TEXT NOT NULL DEFAULT 'key_cost',  -- 加在号价上（跟 00 §3「议价费加在号价上」一致）
  active              INTEGER NOT NULL DEFAULT 0,
  -- 什么条件开启（JSON 谓词 · 例 {"vendor_id":"kirodrop"} / {"zone":"eu"}
  --   / {"passenger.invited":false} / {"bus.avg_lifespan_h":{">":48}}）
  applies_when_json   TEXT,
  -- 什么条件减免（例 {"coupon_code":"any"} / {"passenger.invited":true}）· 优先级高于 applies_when
  waived_when_json    TEXT,
  -- 用户能否主动勾选（capability 类为 1，其余 0 —— 系统自动判定）
  user_selectable     INTEGER NOT NULL DEFAULT 0,
  priority            INTEGER NOT NULL DEFAULT 100,   -- 多条同时命中时的计算顺序
  created_at          TEXT NOT NULL,
  updated_at          TEXT NOT NULL
);
```

**为什么合并**：车主要的是「**插槽控制哪个开启、什么条件开启、什么条件减免**」—— 这句话对 5 类都成立。分成 5 张表就要写 5 套判定逻辑、5 个后台页面；合并成一张，定价引擎只需**一次遍历**：取所有 `active=1` 且 `applies_when` 命中且 `waived_when` 未命中的规则，按 `priority` 累加。加新收费点 = 插一行，不改代码。

**`long_life_bump` 就是车主说的"活得特别长的车可能临时加价"** —— `kind='adhoc'`，`applies_when_json: {"bus.avg_lifespan_h":{">":48}}`。

**合并后 `capability_slot` / `pull_round_capability` 作废**，改成 `surcharge_rule` + `pull_round_surcharge`（记每轮实际命中了哪几条、各收了多少，便于回溯和申诉）。

#### C. 加价栈的完整顺序（合并车主的 5 类 + 现有规则）

```
号价（pass-through · 按 vendor_pricing 换算成积分）
  + 号价 × Σ(命中的 surcharge_rule.rate_bp)     ← vendor / zone / retail / capability / adhoc
  + 单次议价（count==1 时号价 × 20%）
  + 服务费（每人每次固定 1 积分 · 见待确认 ①）
  ────────────────────────────────────────
  = 乘客本次扣除
  （通道费不在这里 —— 只在充值时收一次 · §8.21）
```

跟 `00 §3` 现有公式的关系：**结构不变**（都是"号价 + 号价的百分比项 + 固定服务费"），只是把"附加能力费"这一项从单一插槽扩展成 5 类可配规则。

### 8.29 邀请制 · 个人码 vs 系统码 + 邀请奖励 ⏸（v1 上线后立即补 · 阶段 1b）

**车主原话**：
> 第一版上线之后立马补充邀请制。个人邀请码、和系统邀请码划分零售和社群的不是一种。邀请人进来可以 N 轮减免 5% 手续费或者服务费，看哪种。

#### 两种码 · 职责不同（关键区分）

`§8.20` 定了「邀请码（注册时）」vs「优惠码（支付/提号时）」。本条在**邀请码内部再分两类**：

**完整的三种码对照表见 `§8.32`**（本条只讲注册相关的两种）。

| | **系统邀请码** | **个人邀请码** |
|---|---|---|
| 谁发 | 我方（发给社群） | 每个乘客都自动有一个 |
| 作用 | **划社群身份** → 解锁 vendor 真名 + **免区域附加费 20%** | **减免充值通道费 5%**（限次数 / 限时 · §8.32） |
| 被邀请人身份 | **社群** | **仍是零售**（照加区域附加费） |
| `passenger.invited` | `true` | `false` |

**这是本条的核心，也是必须分两类的原因**：如果个人码也解锁社群身份，那**任何人都能生成码让别人免区域附加费** → 20% 加价形同虚设 → `§8.20` 的整个定价分层崩掉。所以个人码**只给通道费减免额度，不改身份**。

#### 邀请奖励

> ⚠️ **本小节已被 `§8.32` 修订**：车主明确定为「个人邀请码减免**充值通道费 5%**，限次数或限时，额度用完就恢复」。
>
> 下面这段是我原来建议的"减免服务费"方案 + 论证，**保留备查**（论证本身仍然成立 —— 减免通道费确实是我方垫付，所以 `§8.32` 里加了"必须有硬上限 + 单独记 `channel_fee_subsidy` 科目"两条约束）。

**减免对象建议选「服务费」不选「手续费」**：

| | 手续费（通道费 5%） | **服务费（推荐）** |
|---|---|---|
| 归属 | **waffo 的**，pass-through | **我方收入** |
| 减免意味着 | 我方**自掏腰包垫付** —— 直接违反 `00 §3`「pass-through，我方不加不承担」和 `§2.13` | 少赚，不倒贴 |
| 触发时机 | **只在充值时**（§8.21） | 每次拉号 |
| 跟"N 轮"匹配吗 | ❌ 充值跟"轮"没关系 | ✅ 服务费本来就是按轮收的 |

所以：**邀请人获得 N 轮服务费减免**。

**但减免比例不能是 5%** —— 服务费是固定费（`§8.31`：社群 1 / 零售 7 积分），5% 就是 0.05~0.35 积分，无感。按轮**全免**才有感知：

```
邀请 1 人成功注册并完成首次拉号 → 邀请人获得 3 轮「服务费全免」
```

| 参数 | 建议值 | 说明 |
|---|---|---|
| 每邀请 1 人奖励轮数 | **3 轮** | 可后台配 |
| 生效条件 | 被邀请人**完成首次拉号** | 防刷号注册（只注册不消费不给奖） |
| 有效期 | 90 天 | 不做永久，免得账上挂一堆永不过期的债 |
| 累积上限 | 待定 | 防止有人靠拉人把服务费永久免掉 |

**奖励价值随身份不同**（`§8.31` 定了服务费两档之后）：

| 邀请人身份 | 3 轮全免值多少 |
|---|---|
| 零售（服务费 7 积分/轮） | **21 积分** |
| 社群（1 积分/轮） | **3 积分** |

这个 7 倍不对称是**合理的** —— 零售本来每轮付 7，减免对他才有意义；社群本来只付 1，给多少轮都无感。**所以邀请机制天然主要激励零售用户拉人**，正好是我们想扩的那批。

#### 数据落地（阶段 1b）

```sql
-- §8.20 的 invite_code 表加 kind

-- personal 码：owner_id = 邀请人 · max_uses 不限 · 不置 invited=true

CREATE TABLE invite_reward (
  id                TEXT PRIMARY KEY,
  inviter_id        TEXT NOT NULL,
  invitee_id        TEXT NOT NULL,
  rounds_granted    INTEGER NOT NULL,       -- 奖励轮数
  rounds_used       INTEGER NOT NULL DEFAULT 0,
  status            TEXT NOT NULL,          -- pending（未完成首拉）| active | exhausted | expired
  expires_at        TEXT NOT NULL,
  created_at        TEXT NOT NULL,
  UNIQUE (inviter_id, invitee_id),          -- 同一对只奖一次
  FOREIGN KEY (inviter_id) REFERENCES passenger(id),
  FOREIGN KEY (invitee_id) REFERENCES passenger(id)
);
```

### 8.27 设置是主入口 · 全局上限归设置 · 每车策略归车 ✅（前端已做）

### 8.26 成员欠费 · 挂起而不停车 + 成员管理 tab ✅（前端已做 · 后端阶段 2a）

**缺口**：§8.23 定了"余额不足只跳过那个人"，但漏了长期后果 —— 他一直不充值，这辆车的分摊就一直是坏的。

**决定：挂起那个成员，车继续跑**

| 触发 | 动作 |
|---|---|
| 余额不足 | **本次跳过** · 不扣钱 · 不给取这批号 · `skipped_count += 1` |
| 连续被跳过 **3 次**（`SUSPEND_AFTER`） | **自动挂起** · `status = suspended` |
| 挂起期间 | `RevokeClientKey`（取不到号）· 不参与任何分摊 · **`share_pct` 不动** |
| 他充值 | **自己解挂** · `skipped_count` 归零 · 不用车主批 |
| 车主想彻底换人 | **手动移除** · 走 §8.18「改 share_pct 要全员确认」 |

**为什么挂起而不停车**：一个人欠钱，停车是把他的问题变成全车人的问题 —— 其他人的号照样在死、照样要补。**挂起只影响他自己**。

**为什么不自动移除**：移除会改所有人的 `share_pct`，等于悄悄让别人多掏钱。这必须全员确认（§8.18），不能由系统或车主单方面触发。

**挂起 vs 移除的区别**（UI 上要说清，否则车主会误用）：
- **挂起**：`share_pct` 保留 · 可逆 · 他充值就回来
- **移除**：`share_pct` 要重算分给其他人 · 要全员确认 · 不可逆

**成员管理 tab**（BusDetail 第 4 个 tab · tab 顺序：号列表 / 拉号历史 / 推送记录 / **成员** / 补车策略 / 数据）：
- 表格列：成员（头像 + 名 + 车主 chip + 进车时间）/ 分摊 % / 余额 / 状态 / 操作
- 状态三态：**正常** / **已跳过 N/3**（warn · 副行"再 M 次自动挂起"）/ **已挂起**（副行"取不到号 · 不参与分摊"）
- 操作：`挂起 / 解挂` 按钮 + `移除` icon 按钮（移除走确认弹窗，弹窗里引导"只是暂时没钱用挂起更合适"）
- **车主自己那行没有操作**（不能挂起 / 移除自己 · 要退出走「车设置 → 解散」）
- **1 人车不显示表格** —— 只有你，没人可挂起也没人可移除，显示"1 人车 · 只有你"
- **拉人进车**：team 车显示邀请码 + 复制 + 「换一个」（旧码立即失效，已进车的人不受影响）

**状态别猜，读事实**：`余额够不够` 是相对"下一轮花多少"的，而那个数不知道（价格随行就市）。所以 UI **不用 `spend_today × share_pct` 去估**，只报后端记下的 `skipped_count` —— 他实际被跳过过几次。

**数据落地（阶段 2a）**：
- `bus_member` 加 `status ∈ {active, suspended}` / `skipped_count` / `last_skipped_at`
- 充值成功后（`wallet` 侧）把该乘客所有车的 `skipped_count` 归零 + 解挂
- 挂起 / 解挂 / 移除都要发通知给当事人（走 §8.17 通道）

**UI 状态收敛**（§12.5）：成员对外只有 **正常 / 已挂起** 二态 · `skipped_count` 是个计数不是状态

**拒绝**：
- ❌ **停车（整车暂停）** —— 一人欠费惩罚全车
- ❌ **自动移除** —— 悄悄改别人的 share_pct
- ❌ **记债务 / 账期** —— §8.18 §8.23 已否决，阶段 2a 太重
- ❌ **车主一人拍板改 share_pct** —— §8.18 已定要全员确认

### 8.23 自费拉的号派进多人车 · 按份额即时清算 ⏸（阶段 2a · 补 §8.18 的缺口）

**缺口**：`§8.18` 只定了「车内拉号时按 `share_pct` 从各成员钱包同时扣」。但漏了这条路径：

> 我从「提取 key」**自己掏钱**拉了号 → 派进车 → 车里其他人也用 → 我垫的钱谁还？

现在实现里 `assign → into_bus` 只改 `owner_bus_id`，**没有任何资金结算** —— 号变成车的共享资源，钱却是一个人出的。没人愿意先垫钱，多人车玩不起来。

**决定：按份额即时清算（方案 A）**

派进车那一刻，按车内 `share_pct` 从其他成员钱包扣、进派入者钱包：

```
我拉号花 100 积分 · 车内 我 40% / A 30% / B 30%
派进车时：A 扣 30 → 我入账 30
         B 扣 30 → 我入账 30
         我净支出 40（= 我该承担的份额）
```

**会计语义**：成员向派入者**买入份额**，我方是清算通道（不抽成 —— 服务费已在拉号时收过）。

**关键规则**：
- **不再收 vendor 费用** —— 号价在提取时已付给 vendor，派发只是内部记账转移
- **余额不足 → 只跳过那个人，不拒绝整车**（**修正**本条早先写的"任何一人不足则拒绝派入"）：
  - 号**已经是我的、钱已经付给 vendor 了** —— 少一个人分摊只是我少收回一点，不是派不进去
  - 那个人这一次：**不扣他积分**，也**不给他取这批号**（`RevokeClientKey`）· `share_pct` 不动
  - 我净支出 = 我那份 + 被跳过的那部分
  - **只有一个人都参与不了才拦** —— 那时候派进去等于纯赠送，提示「等他们充值或先解挂」
  - 挂起的成员（§8.26）同理不参与
- **不做应收/账期** —— 跳过就跳过，不记债务（阶段 2a 太重）· 长期不还走 §8.26 挂起
- **单人车不清算** —— 就一个人，没有分摊对象

**拒绝的替代方案**：
- ❌ **按实际用量后结算** —— `§8.18` 已否决后结算（频率 / 边界模糊）；且 credential 级用量归属 vendor 不给数据
- ❌ **不结算视为赠与** —— 没人愿意垫钱，多人车成不了

**数据落地（阶段 2a）**：
- `assign_event` 加 `settlement JSON`：`[{ member_id, amount, direction }]` · 便于回溯
- `wallet_ledger.reason` 加两种：`share_income`（派入者收）/ `share_expense`（成员付）
- 清算和 `owner_bus_id` 变更**同一事务**（避免"号进车了但钱没结"）

**UI（阶段 2a）**：

派进车确认弹窗 · **选完车之后**出清算提示（选车前算不出来 —— 不知道跟谁分摊）：

| 情况 | 显示 |
|---|---|
| 选中**单人车** | 「独享车 · 无分摊」一句灰字 |
| 选中**多人车** | **一行**：「车友分摊后你将收到 **60 积分**」 |
| 有人参与不了 | 上面那行照出（金额只算付得起的）+ warn 一行「@lin（余额不足）· @zhou（已挂起）· 本次跳过 · 你少收 **15 积分**」· 确认按钮**可用** |
| 一个人都参与不了 | danger「没有车友能参与这次分摊 · 现在派进去等于你白送」· 确认按钮禁用 |

**只给结果，不列明细** —— 用户要知道的就是"我能收回多少"。逐成员的份额明细在车详情页的成员 tab 能看，不在这里重复。

- 有人被跳过时才展开说是谁 + 我少收多少（这时候用户必须知道是谁）· 但**不拦**
- 成员侧收到通知（走 §8.17 通知通道）：「@you 派了 3 个号进「周末拼车局」· 你分摊 30 积分」
- 钱包流水能看到 `share_income` / `share_expense`

**阶段 1a 前端已做这个预览**（覆盖本条早先"1a 不做"的判断）：`bus.members[]` 带 `share_pct` + `balance` 后，mock 里那辆 team 车（`bus_kiro` · 我 40% / wei 35% / lin 25%）算得出真数，不是编的。三种态在 mock 上都可达：

- 选 `bus_kiro` 派 3+ 个号 → lin 余额（12 积分）不够他那 25%，出「@lin 余额不足」+ 确认禁用

**后端结算仍是阶段 2a**（`settlement JSON` / `wallet_ledger` 两种 reason / 同事务）。前端现在只做**预览**，`assign → into_bus` 后端仍不动钱。

  - hover 竖条 → tooltip 列出**那天每一轮**的时刻 / 区 / 单价 / 号数
  - Y 轴**每行独立**（各家价格量级差太多，共享轴会把竖条压成一条线）
  - 颜色**统一品牌紫**（每行独占不重叠 → 不需要区分色相 · 深浅表达轮数）
- **数据模型**：存**轮次级**（`VendorRound` / `VendorDayRounds`），聚合值前端派生
- **Mock 铁律**：**禁止随机噪声 / 正弦叠加造走势** —— 那是编造数据
  - 正确模型：基准价 3-8 天漂移一次 + 每天 N 轮 + 每轮按产量查阶梯
- **阶段 1b+ 才做**：后端采集上游轮次记录、入库聚合、价格预警订阅
- **不做**：预测下 24h 价格（不做金融预测）

### 8.21 通道费只在充值时展示 ✅（澄清 §2.13）
- **背景**：`decisions §2.13` 定了通道费 pass-through（waffo 5% · 我方不加不承担）· 但 UI 上一直在拉号/提取费用明细里显示"通道费 · 充值时收"
- **问题**：用户混淆 —— 以为拉号/提取时还要额外扣通道费。实际**充值积分时已经收过一次**，之后所有积分抵扣操作都不再涉及通道费
- **决策**：
  - **充值积分页 / 充值弹窗** · **显示**通道费（"号价 5% + waffo 通道费"）
  - **拉号 / 提取 / 拼车 / 补车** · **不显示**通道费 · 这些都是积分抵扣，跟通道费无关
- **数据不变**：底层计费公式（`00 §3` 加法顺序）不变 · 只调整 UI 展示时机
- **参考**：`web/src/components/PullExtractForm.tsx`（已删预估卡通道费行）

### 8.20 邀请码双层机制 · 替代地区议价 ✅（覆盖 §2.10 / §2.11 / §2.12）

**背景**：§2.10 地区议价（海外 +20%）因"无法可靠识别地区"⏸。本条用**邀请码**替代地区判定 —— 码是我方发的，**可校验、不可绕、无合规风险**。

#### 两种码 · 名字不同 · 作用不同（必须分清）

| 名称 | 输入时机 | 作用 | 持久性 |
|---|---|---|---|
| **邀请码** | **注册时**填 | ① 解锁 vendor 真名 ② 免加价 | 永久绑账号 |
| **优惠码** | **支付 / 提号确认窗**里填 | 只减免（**不解锁真名**） | 单次生效 |

**术语铁律**：注册那个叫「邀请码」· 支付和提号那个叫「优惠码」· **UI 上不许混用**。

**为什么解耦**：社群成员可以把优惠码发给朋友省钱，但**不会泄露我方 vendor 清单**（防散客绕过我方直连 vendor）。

#### 加价规则

- **无注册码 且 本次无消费码** → 加价（当前 **+20%**，后台可组合多个附加费）
- **有注册码** 或 **本次填了消费码** → 无加价
- **UI 绝不显示原价 / 加价幅度**（不暴露我方成本结构）· 只显示一个最终价

#### vendor 名字显示

| 身份 | 显示 |
|---|---|
| 有注册码 | 真名（Kiro Market / Kiro Drop / …） |
| 无注册码 | **AWS-Q Kiro Vendor 01 / 02 / …**（编号按 `CLAUDE.md §1.1` 六家顺序固定，同一用户每次看到的映射一致） |

#### 提取 key 页的默认项（auto）

**不再用**「让系统按有效成本比价」这种空文案。auto 项**必须展示系统推荐结果 + 价格**：
- 推荐到的 vendor（真名 or Vendor 0N）
- 库存 / 单价（最终价）/ 质保 / 历史成活率
- 预估费用（不能留"选具体 vendor 看预估费用"空占位 —— 散客本来就是 auto，必须能下单）

#### 提取确认窗（不直接拉）

点「提取」**不直接下单** → 弹确认窗：
- 复核提取信息（来源 / 区域 / 数量 / 单价 / 质保）
- **优惠码在这里填**（不放外层表单）· 应用后实时重算价格 · 原价划线显示
- 合计扣除 + 波动提示 → 「确认提取」才真拉

card 左下角常驻灰色小字：**「价格受市场波动影响，会有波动，提取前请仔细核对提取信息。」**

#### 覆盖关系

- **覆盖 §2.10 地区议价** —— 不再尝试识别地区，改用邀请码
- **覆盖 §2.11 双币种** —— 同上，不依赖支付通道分层
- **覆盖 §2.12 多信号识别** —— 彻底放弃地区判定
- **§2.8 指定 vendor 议价** 语义变更 —— 不再是单独收费点，变成**注册码持有者的权益**

#### 数据落地（阶段 1b）

- `passenger.invited`（bool）· `passenger.invite_code_used`（注册时用的邀请码）
- `invite_code` 表（注册用）：code / owner_id / used_count / max_uses / expires_at
- `coupon_code` 表（支付 / 提号用）：code / discount_rule / used_count / max_uses / expires_at
- `surcharge_rule` 表：后台可配多个附加费 —— 完整设计见 **`§8.30`**（多类合并成一张表）
  - 这条规则就叫 `region_markup`（**区域附加费**）· 有系统邀请码 → 免掉它（`§8.32`）
- 定价 API 返回**最终价**，不下发原价和加价明细

**参考**：`docs/14-extract-page-plan.md §4` · `web/src/components/UpstreamStatusPanel.tsx`

### 8.18 多人车 · 按成员百分比分摊扣款 ⏸（阶段 2a）
- **决定**：多人车里每个成员在建车时被分配一个 `member_share_pct`（百分比），加起来 = 100%
  - 车主 60% + 车友 A 30% + 车友 B 10%
  - 一次拉号总花费 100 积分 → 从车主钱包扣 60 · A 钱包扣 30 · B 钱包扣 10
- **谁能触发拉号**：**只有车主**（无论手动 / 自动补车触发）· member 视图 primary 按钮是"提醒车主拉号"（§8.17）
- **单次议价**：跟共享账户一样按 share_pct 分摊 · 不因为"只拉 1 个号"就归某人
- **余额预检**：拉号前**遍历所有成员钱包**
  - ~~任何一人不够即整轮拒绝~~ —— **§8.26 修正**：不够的人**本次跳过**（不扣钱 · 不给取这批号）· 一个人卡死全车不合理
  - **但拉号跟派号不一样**：派号是钱已经花完了（§8.23），拉号得**先收钱才能去 vendor 买**。少一个人的份额 → **收到多少钱买多少号**（缺口靠下一轮补）· 不让其他人垫、不整轮拒绝
  - UI 明确提示"@wei 余额不足 · 本次跳过"（不含糊）
  - 不做债务累积 / 押金冻结（阶段 2a 太重 · 未来讨论）
  - 连续跳过 3 次 → 挂起（§8.26）
- **百分比修改**：
  - 建车时车主拍
  - 运行中改需要**所有成员确认**（阶段 2a 走通知通道 · 走 8.17 的通用通知机制）
  - 不做"车主一人拍板"（避免车主拉黑压死车友的滥用）
- **数据落地**（阶段 2a 表字段）：
  - `bus_member (bus_id, member_id, share_pct)` — 成员 + 比例
  - `pull_round.member_shares JSON` — 每轮实际按什么比例扣 · 便于回溯
  - `wallet_ledger.reason_id` 关联到 pull_round · reason 里带 share_pct
- **拒绝**：
  - **单一车主付全款**（那就不叫拼车，叫"车主赠送 API"，跟散户切片重复 · §5.1 未来产品线）
  - **按用量后结算**（结算频率 / 边界模糊 · 阶段 2a 用不起）
  - **贝壳制**（成员先充值到共享钱包，从共享扣）· 隐私 & 归属不清晰 · 未来讨论
- **参考**：`docs/06-db-schema.md` 阶段 2a 表规划 · `03-modules.md wallet + bus 依赖` · §8.17 member 通知机制

### 8.17 多人车 member 视图 · 提醒车主拉号 + 走通用通知通道 ⏸（阶段 2a）
- **场景**：多人车里 `role === "member"`（车友，非发起人）打开车详情 / focal 卡时，看不到"给这辆车拉号"按钮
- **原因**：多人车号价从**发起人钱包**扣，权限只给 owner；member 不能替 owner 掏钱
- **member 视图的 primary 按钮改成**："提醒车主拉号"
  - 点击后：Toast 提示"已通知" · 后端发通知给车主 · 侧栏计数递增
  - 车主收到后自己决定是否拉
- **通知通道**：**走通用「通知通道插件」**，不硬绑 TG
  - webhookout（阶段 1b 已做）: owner 配了 webhook 就走 webhook
  - 邮件 / TG bot / Discord: 归到"通知通道设置"页（阶段 2c 做通道配置 UI）· owner 自选启用哪些
  - 站内通知（用户偏好里默认开）
- **拒绝**：硬绑 TG 单一渠道
  - 理由：TG 大陆用户不友好 · 阶段 1 没做 bot 基建 · 一旦硬绑就要为它加运维和申诉通道 · 违背通道插件化原则
- **视觉**：`<Button>提醒车主拉号</Button>`（primary 黑 · card 内主动作）+ 副行 `<Muted>已通知 · 12 分钟前</Muted>`（如果最近发过） / `<Muted>暂无通道</Muted>`（车主未配任何通道时）
- **阶段 1a 不做**：现在全 single 车，member 视图不存在 · 视觉先留档，代码等阶段 2a 权限模型落地一起接
- **参考**：`web/src/components/BusFocalCard.tsx` role prop（已就位，行为待接）· `03-modules.md webhookout` · 阶段 2c 通道设置页
