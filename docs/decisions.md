## 三种状态

## 1. 架构分层

### 1.1 内嵌 kiro.rs 到 bus-pooling 单进程 ❌
- **提议**：把 kiro.rs 号池能力做进 bus-pooling 自己的进程里
- **否决**：kiro.rs 已经作为独立服务运维（`kiro.aibbq.xyz`），是**外部依赖**；本项目只做它的 client
- **替代**：`internal/housepool/kirors/` 客户端调 kiro.rs admin API

### 1.2 用数据库替代 housepool ❌
- **提议**："housepool 的价值就是数据回流，用数据库也能做"
- **否决**：数据库只能记账（"这号归谁"），但**运行时**能力（校验凭证、存活探测、用量追踪、分组、并发监控 5 项）**必须号池实现才有**
- **参考**：`01-architecture.md §2 Layer 4`

### 1.3 拉号记录 = 独立数据库表（不进 housepool）❌
- **提议**：单独拉号的号先在数据库里躺着，用户派去向后再进 housepool
- **否决**：**要监控就必须进 housepool**（否则 5 项能力全废）。这些号也需要平均寿命统计
- **替代**：拉号记录 = **housepool 里的 `record-<pid>` group + `disabled=true`**（号已进池、已监控、不发下游）

### 1.4 号推给 passengerpool = 号离开系统 ❌
- **提议**：号一推到乘客的 kiro.rs 就完成交付，我方不再跟踪
- **否决**：**要监控存活就得留副本**。推给 passengerpool 是**双写** —— housepool 保留副本（我方监控），passengerpool 是复制品（乘客用）
- **例外**：只有**去向 ③ handoff（拿走）**才是真正离开系统，我方 `DELETE /credentials/{id}` 后不再跟踪

### 1.5 fire-and-forget 一律不管 ❌
- **提议**："发出去就不管了"
- **否决**：只有 handoff（拿走号数据）才 fire-and-forget。**推 passengerpool 是双写还监控**、进 bus 也监控
- **参考**：`00 §5 用户路径` 3 种去向表

### 1.6 provider 抽象层可以省 ❌
- **提议**：只有一个 provider（kiro），直接把 6 家 vendor 平铺在 `internal/vendors/`
- **否决**：未来加 `cursor` 等 provider 时会撞车
- **替代**：`internal/providers/kiro/vendors/*`；加新 provider 只加 `providers/<name>/`

### 1.7 kiroclient 命名放顶层 ❌
- **提议**：`internal/kiroclient/` 顶层
- **否决**：号池承载**当前**是 kiro.rs，未来可能换其他实现；按"层职责"命名而非"具体实现"命名
- **替代**：`internal/housepool/kirors/`

### 1.8 混淆"我方号池"和"乘客号池"❌
- **提议**：两个 kiro.rs 都叫"号池"或"pool"
- **否决**：**两个不同实体**：
  - 我方 = `housepool`（Layer 4，我方基础设施）
  - 乘客 = `passengerpool`（Layer 5 交付目标，外部系统）

## 2. 收费 / 商业模式

### 2.1 卖号（加价 pass-through 差价）⏸
- **提议**：我方在 vendor 号价上加价卖
- **当前不做**：号价永远 pass-through，我方只赚服务费（`00 §1 是什么/不是什么`）
- **未来可能做**：**利用 vendor 的开号能力**（乘客上传 AWS → 我方转发 vendor 开号，见 §5.1 阶段 3b/3c）→ 号进**公开池 / 市场**（阶段 3d）→ 卖给其他乘客 → **这条路径有利润空间**
- **关键区分**：**"我们不做开号"**（不复刻 vendor 的开号系统） ≠ **"我们不做号买卖"**（未来通过市场可以做）

### 2.2 会员制 / 订阅制 ⏸
- **提议**：月付订阅费享受服务费打折 / 优先撮合 / 优先补车 / 数据看板
- **当前不做**：阶段 1/2 先跑"每次固定服务费"的按需模型
- **未来可能做**：跟拼车主线不冲突，等有稳定用户量再评估

### 2.3 长效号预留池 ⏸
- **提议**：从平均寿命高的 vendor 定期拉号、储备一个小池，预付进入"长效池会员"
- **当前不做**：还没有"长效号"这种类型（vendor 未提供），也无平均寿命历史数据
- **未来是议价空间**：等阶段 1d 采集足够寿命数据后可以评估。**"长效号"是我方少数能提供的稀缺资源**，值得少量储备 → 议价空间
- **参考**：`00 §9 未来增值方向 · 长期稳定号源`

### 2.4 数据看板"作为收益点"（订阅 / API 收费）❌
- **区分两件事**：
  - **数据看板功能** —— 阶段 3a 要做（`00 §7 · 阶段 3a`），乘客和管理端都能看到平均寿命 / 价格趋势 / 缺货率等
  - **数据看板作为收益点**（订阅制收费卖数据 / API 卖看板数据）—— **不做**
- **否决理由**：跟"公益工具"人设不匹配。数据看板是**产品能力**，不是**收费点**
- **不影响**：阶段 3a 的数据图表功能照常做

### 2.5 API 售卖（"我们推自己的池 API 卖"）✅
- **提议**：我方直接用 API 卖自己 kiro.rs 号池给乘客
- **接受，且不需要任何新功能**：**把我方运营账号当作一个普通乘客**，用已有的乘客侧 API（`05-api-contract.md` §5 单独拉号 + `06-scenarios.md` B4 handoff / B3 推 passengerpool）即可完成"卖 API"的全部动作
- **明确不做的形态**：**API 拼车**（把 API 调用本身做成拼车）—— 太复杂，用户明确不搞
- **未来加值**：接入合作下游产品直接消费我方 API（`00 §9 · 合作下游消耗`）

### 2.6 & 2.7 · 稳定优先附加能力（排噪邻 + 优先撮合，打包）⏸
- **提议**：拼车时排除高流量成员 + 撮合优先级更高，打包 +20%
- **当前不做**：先不设限制，阶段 2c 压车治理数据成熟后作为附加能力候选实施
- **完整描述已在**：
  - `00 §9 未决 · 附加能力插槽候选清单 · 稳定优先`（含触发规则：手动勾 or 策略参数含 RPM/TPM 要求）
  - `00 §3 计费模型`（附加能力插槽定义 + 加法顺序）
- **本条只做交叉引用**，不重复叙述

### 2.8 指定 vendor 议价 ⏸
- **提议**：用户指定 X 家 vendor → 加价（限制我方选择）
- **当前不做**：跟"公益"人设不匹配；用户可以指定 vendor 但不加价，属于普通拉号
- **未来可能**：若有场景表明"指定 vendor"确实消耗我方资源，可作为附加能力候选

### 2.9 寿命 SLA 议价 ⏸
- **提议**：用户要求"平均寿命 ≥ X 小时" → 加价
- **当前不做**：**没有历史数据可用**（阶段 1 才开始采集平均寿命）
- **未来可能**：阶段 1d 后有数据再评估。可能与 2.3（长效号预留池）合并考虑

### 2.10 地区议价（海外 +20% / 国内 0）⏸
- **提议**：海外用户加 20%
- **当前不做**：**无法可靠识别**海外/国内：
  - 注册选地区 —— 无法校验
  - IP 定位 —— VPN 可绕
  - 支付通道 —— waffo 单通道不支持币种区分
- **未来可能**：等阶段 2+ 接入多通道（微信/支付宝/信用卡），按通道自然分层（"通道即价目"）；阶段 1 **统一定价**

### 2.11 CNY/USD 双币种价目表 ⏸
- **提议**：用户充值币种自选，CNY 走国内价、USD 走海外价
- **当前不做**：waffo 不收 RMB，单一币种，无法区分
- **未来可能**：同 2.10，等多通道再启用

### 2.12 IP + 手机号 + 时区多信号识别 ❌
- **提议**：多信号打分判定海外/国内
- **否决**：合规风险（跨境用户地区判定敏感）+ 用户可绕，误伤高
- **替代**：同 2.10 走通道自然分层

### 2.13 通道费我方承担 / 我方加收 5% ❌
- **提议**：(b) 我方承担 waffo 5% 通道费 / (c) 我方在通道费上再加收 5% 作为额外收入
- **否决**：违背 pass-through 人设
- **保留**：(a) 通道费 pass-through 给乘客，waffo 收，不进我方账

### 2.14 议价加在总价上 ❌
- **提议**：`总价 × (1 + 议价率)`
- **否决**：用户明确"附加费加在号价上，不加在总价"
- **保留**：`(号价 + 议价) + 服务费` → `× (1 + 通道费)`

### 2.15 一轮 = 一个号 ❌
- **提议**：拉 10 个号 = 10 轮，服务费 × 10
- **否决**：用户原话"每人每轮 1 元，18 轮就是 18 元"—— 一轮 = **一次拉号动作**
- **保留**：**1 轮 = 1 次拉号动作**（不管这次拉几个号）
- **推论**：批量天然便宜（拉 10 个号 1 元服务费 vs 分 10 次拉 10 元服务费），符合"鼓励批量"

### 2.16 退款支持现金 / 退到 payment-gateway ❌
- **提议**：号死了退现金给乘客
- **否决**：我方**只退积分，不退款 / 不退现金**
- **保留**：`wallet` 加积分 + ledger 落 `warranty_refund`；服务费 / 通道费 / 过窗口的号 **不退**
- **参考**：`00 §3 退款原则` + `§7.5 规则 B`

### 2.17 独立质保（超出上游窗口） ❌
- **提议**：我方对乘客做独立质保（例：号死 60 分钟内退款）
- **否决**：质保**完全跟随上游 vendor**，上游过窗口不退我方也不退
- **参考**：`00 §7.5 规则 B`

## 3. bus / 号 / 上车

### 3.1 solo bus / pooled bus 概念 ❌
- **提议**：区分 solo bus（独享）和 pooled bus（拼车）为两种类型
- **否决**：造成命名混乱。**1 人 bus 也是 bus**，多人 bus 也是 bus，都在 `bus-<id>` group
- **保留**：`bus.kind` 字段可以是 `single` / `anon` / `team`，但**都叫 bus**

### 3.2 mode: carpool / solo 二选一 ❌
- **提议**：策略参数带 `mode: carpool | solo`，二选一决定去向
- **否决**：号的去向由分配决定，不是 mode 二选一
- **参考**：拉号 ≠ 上车（`00 §5`）

### 3.3 混合上车（一次拉号分头上多 bus）❌
- **提议**：一次拉 10 个号，5 上 bus X + 5 上 solo bus + `allocation_plan`
- **否决**：**用户否决**（"什么混合上车是什么鬼"）
- **保留**：单独拉号后号进 `record-<pid>` group，用户再对每号选去向

### 3.4 allocation 组件 ❌
- **提议**：单独设 `internal/allocation/` 分配器
- **否决**：跟 3.3 一起否决
- **替代**：`internal/pullrecord/` 承担"派去向"职责

### 3.5 用 `personal-<pid>` group 表示乘客个人号池 ❌
- **提议**：housepool 里有 `personal-<pid>` 这种 group 表示乘客的号
- **否决**：**号池 = 乘客的 passengerpool（外部）**，我方 housepool 里的 group 不叫"号池"
- **替代**：叫 `record-<pid>`（拉号记录 group），只是号"归属"，不叫"号池"

### 3.6 拉号记录 = 数据库表（不进 housepool）❌
- 见 1.3

### 3.7 号归属 = Bus（不是乘客）✅
- **提议**：号在 credential_ledger 有唯一 owner
- **决策**：**号归属 Bus（`owner_bus_id`）**，成员通过 `bus_member` 表拿访问权
- **理由**：拼车语义 = "大家一起养的号"；owner 归 Bus 后：
  - 退出 Bus 不影响号（号仍在 bus group）
  - 解散 Bus 才需要决定号归谁（阶段 1a 简化：解散时号 handoff 给创建人 or 死号扫掉）
  - 拼车分摊 / 补车 / 退款 都以 Bus 为主体
- **单独拉号进 record group** 的号：`owner_bus_id = NULL, owner_record_passenger_id = <pid>`
- **参考**：`06-db-schema.md § 11 credential_ledger`（CHECK 约束保证 XOR）· `09-transactions.md`

## 4. 概念 / 术语作废

### 4.1 用 `carpool / car / carpool_room / carpool_id` ❌
- **提议**：英文命名用 car / carpool
- **否决**：用户明确"没有 car 这个概念"
- **保留**：**统一用 `bus`**（`bus_id`、`bus-<id>` group）

### 4.2 "方式 A / 方式 B" ❌
- **提议**：交付分方式 A（推 passengerpool）和方式 B（乘客调 API 拿）
- **否决**：把**入口**和**去向**糊在一起了
- **替代**：**3 种去向**（进车 / 推 passengerpool / handoff）+ **2 种入口**（UI / API）正交

### 4.3 "上车 = 独享/多人拼车" ❌
- **提议**："上车"泛指号分配到任何 group
- **否决**：号只有一个物理位置（housepool），"上车"这种动作性词汇没实质
- **保留**：只用**去向**表达

### 4.4 P0 / P1 / P4a / P∞ 等 P 标签 ❌
- **提议**：延续旧项目的 P0-P∞ 阶段命名
- **否决**：粒度过细
- **替代**：**3 大阶段 + 内部 milestone**（1a / 1b / 1c / 1d / 1e / 2a / 2b / 2c / 3a / 3b / 3c / 3d）

## 5. 未来产品线

### 1.9 用 SuperTokens 做登录方案 ⏸
- **提议**：用 SuperTokens 或 Casdoor / Ory Kratos 等外接身份管理服务
- **当前不做**：项目是公益工具（`README.md`），阶段 1 只需要"登录 / 登出 / API key"三件事，**Go 自建约 200 行代码**就够（Argon2id + session cookie）
- **未来可能做**：如果需要邮箱验证 / 忘记密码 / 社交登录（Google / GitHub）→ 阶段 3+ 用户量稳定后可评估接入 SuperTokens 或 Ory
- **参考**：`03-modules.md · authpassenger`；密码哈希算法用 Argon2id（跟登录方案是两回事，见对话记录）

### 5.1 散户切片（一把 key 切多份卖给小散户）⏸
- **提议**：用 kiro.rs `CreateClientKey(usage_limit)` 把一把号的额度切成多份卖
- **当前不做**：不是拼车主线，避免混乱；kiro.rs 天然支持但先聚焦拼车
- **未来可能做**：作为**独立产品线**（不并入拼车），阶段 3 之后再评估

### 5.2 数据图表作为收益点 ❌
- 见 2.4（数据看板功能仍做，只是不作为收益点）

### 5.3 拉号记录 N 天过期策略 ❌
- **提议**：拉号记录里号 N 天未处理 → 自动搬迁 / 提醒
- **否决**：**"过期"= 号本身死了**（vendor 判死），不是按 N 天计时
- **保留**：号还活但用户 N 天没处理 → 只**提醒**，不自动搬迁（尊重用户选择权）

## 7. 议价 / 计费历史（速查）

用户拍板的当前收费点（`00 §3` 权威）：

| 项 | 归属 | 说明 |
|---|---|---|
| 号价 | vendor（pass-through） | 拼车按 N 摊 |
| 单次议价 | 我方 | `count==1` 时号价 × 20% |
| 附加能力费 | 我方 | 插槽，可累加多项；阶段 1 无实例 |
| 服务费 | 我方 | 每人每次拉号动作固定 1 元 / 1 USDT |
| 通道费 | waffo（pass-through） | 5% × 小计，充值时扣 |

**议价加在号价上**，通道费加在（号价+议价+服务费）小计之上。

## 8. 前端 UX / 首页结构（阶段 1a mockup 定型）

### 8.1 全局搜索 / ⌘K 命令面板 ⏸
- **提议**：顶栏加全局搜索或 Cmd-K 命令面板（Linear / Superhuman / Arc 风格）
- **否决当前阶段**：阶段 1 数据量小（一个用户几辆车、几十号、几十条记录），翻页 + 筛选够用；用户是消费端普通乘客，不是效率工具用户；Apple Pay / Cash App 也没有全局搜索
- **重启条件**：车 / 号 / 记录列表大到用户找不到时，考虑**局部筛选**（车列表页顶部一个筛选框）—— 但**不做 ⌘K 全局命令面板**
- **参考**：`design/design-brief.md`（顶栏元素）

### 8.2 顶栏结构 · 左对齐 5 tab + 头像 dropdown ✅
- **决定**：顶栏 = K logo · 左对齐 5 tab（概览 / 拼车 / 提取 key / 我的发车 / 对接文档）· 右侧 3 元素（余额 chip / 通知 / 头像）
- **头像 dropdown 内容**：**我的**（用户名 → `/me`）· **设置**（→ `/settings` 索引页）· 语言 · 主题 · 登出
  - **「设置」是真的主入口**：`/settings` 是索引页，下面挂三类设置（我的号池 / 机器人通知 / API key）· dropdown 里**不再**把这三项跟「设置」并列（并列等于说它们跟设置平级，是另外三件事）
  - **「我的」在 `/me`，不在 `/settings/profile`** —— 账号本身不是一种设置；`/me` 也跟 API 的 `GET /api/me` 对齐

### 8.7 UI 单位一律是"积分"不是货币 ✅
- **决定**：前端所有余额 / 消费 / 花费 / 到账数字，单位都是**积分**（如 `1,245 积分` · `-25 积分` · `+50 积分`）
- **1 积分 = 1 元人民币（1 CNY）** —— 平等价值，简单
- **法币金额（USD）只在充值页 + 兑换页出现**（CLAUDE.md §1.4）：
  - 想充 100 积分 → 通道费 = 100 × 5% = 5 积分 → 折 105 CNY → 按 7 CNY/USD 显示 **15 USD** → 到账 **100 积分**
  - 兑换码到账 100 → 显示 +100 积分（没有通道费）
- **正负数**：消耗前置 `-`（`-25 积分`）· 到账前置 `+`（`+50 积分`）· 0 不显示正负
- **精度**：DB 底层用 microunit（`06-db-schema.md §通用约定`：1 元 = 1_000_000），UI 层展示时**整数积分**（微积分四舍五入至整数积分 · 只对号价单价可能出现小数 · 显示保留 2 位）
- **理由**：`00 §3` 用户在我方充值 → 消耗积分，不感知底层币种；简单等值人民币，避免用户困惑
- **参考**：`design/mockups/05-home.pen` · `05-api-contract.md` 需要保证 API 返回也用积分字段

### 8.25 待派 key 的可用性 + 推送失败的结构化错误 ✅

#### 决定 1 · 待派列表必须标可用性，失效的禁止选中

**真实场景**（车主提出）：
- 拉下来的号**放半天没派**，中途挂了
- 号**刚拉下来就挂了**（走质保退款）

失效的号推不上去、进车也没意义，所以：
- 列表每行标状态 Chip：**正常**（ok）/ **质保内失效 · 可退**（warn）/ **已失效**（danger）
- 失效行 `checkbox disabled` + 整行 `opacity-55` + key 加删除线 + 整行不可点
- **全选只选可用的**（`items.filter(status !== 'dead')`）
- 副标显示「可用 N 个 · K 个已失效（不能派）」

**质保区分**：`warranty_until > now` 的失效号标「可退」—— 这是刚拉就挂的情况，用户能拿回积分；过了质保只能认（放太久没派）。

#### 决定 2 · 推送失败要结构化，不能只给一句文案

**原来**：`push_error: string`（一句人话）· 客服/用户都判不了该干什么。

**改成** `PushError` 结构（`web/src/types/index.ts`）：

| 字段 | 用途 |
|---|---|
| `code` | 内部稳定标识 · **判 code 不判文案**（跟 vendor 档案 §12 同原则） |
| `status` | 目标号池返回的 HTTP 码 · `null` = 没连上（超时/DNS） |
| `message` | 给用户看的人话 |
| `retriable` | **重试有没有意义** —— 决定 UI 给「重试」还是「去检查配置」 |
| `attempts` / `last_attempt_at` | 已试几次 · 什么时候 |

`code` 枚举：`unauthorized`（401/403 token 失效）· `not_found`（404 路径错）· `conflict`（409 已存在）· `timeout` · `unreachable`（DNS/拒连）· `rate_limited`（429）· `server_error`（5xx）· `bad_response`

**UI**（推送记录 tab）：
- 失败行直接显示 `message` + 状态码 badge
- `retriable: true` → 给「重试」按钮（title 显示已试几次）
- `retriable: false` → 给「去检查」跳 `/settings/downstream`（重试无用，要先改配置）

#### 决定 3 · 余额不足不会跟推送失败混（车主的顾虑，澄清）

两个**完全不同的域**，不可能误判：

| 域 | 谁返回的错 | 典型 code |
|---|---|---|
| **拉号** | vendor | `insufficient_balance` 402（我方在 vendor 余额不足）· `no_stock` 409 · `purchase_cap_reached` 409 |
| **推送** | 用户自己的号池 | 401 token 失效 · timeout · 409 已存在 |

**推送不涉及任何扣款** —— 号价在提取时已付（§8.21），推送只是把号复制给用户号池。所以 `insufficient_balance` 在推送域**永远不会出现**。

#### 决定 4 · 术语：悬浮栏「进车」改「加入拼车」

「进车」太简省，用户看不出是加入哪个东西。统一成「加入拼车」（跟顶栏「拼车」tab 呼应）。弹窗标题同步改「确认加入拼车」。

**参考**：`docs/vendors/91kiro.md §12`（错误码表 · 判 code 不判文案）· `§8.24`（售后追溯）· `§8.21`（通道费只在充值收）

### 8.24 号交付后的售后追溯 · 台账永不删 + masked 可查 ✅（补 `09-transactions.md §4` 的缺口）

**车主提出**：号不能立马清理干净，数据库起码得有记录 —— 万一没推成功、或者号有问题，用户找客服时无据可查。

**先澄清已有机制**（`09-transactions.md §4`）：
- handoff 已经是**三段式 token 交付**（init → fulfill → confirm 才 DELETE），5 分钟 TTL 内可重试 GET 明文
- **这解决的是「下载时网络断线」**，不是售后
- `credential_ledger`（`06-db-schema §11`）**是永久台账，行永不删** —— housepool 里 DELETE 的是明文，台账留着

**真正的缺口**（现有机制没覆盖的）：

| 场景 | 现状 | 缺口 |
|---|---|---|
| 下载时断线 | ✅ 5 分钟 TTL 内重试 | — |
| 下载成功但**号推不上去 / 号本身有问题** | ⚠️ 台账有行 | 台账**没存 masked**，客服对不上用户说的号 |
| 用户**几小时后**说「这号有问题」 | ⚠️ 同上 | 没有工单/申诉入口 |

#### 决定 1 · 台账补三个售后字段（阶段 1b）

`credential_ledger` 加 `key_masked` / `region` / `credits_used`（见 `06-db-schema §11.1`）：
- `key_masked` **不是明文**（`ksk_live_9f4a…vn6` 只有前缀+后 3 位）· 可以安全长期保留
- 号入池时写入，交付/失效后不再变更（快照语义）
- 客服工作流：用户报 masked → 查台账 → 看到 vendor / 拉号时间 / 交付时间 / 已耗额度 / 死亡来源 → 判断质保内否、要不要退

#### 决定 2 · 台账永不删（阶段 1b）

- **不设保留期限** —— 台账行不含明文，体积极小（一行几十字节），没有清理必要
- housepool 里 DELETE 明文 ≠ 台账删行 · 两件事分开
- 这也是 `§8.22 价格走势` / `§8.19 数据 tab` 的数据基础 —— 删了历史统计就断了

#### 决定 3 · 推送失败要留错误原因（阶段 1b）

`credential_ledger.passengerpool_push_error` 字段已有，但要保证：
- 推送失败**不重置**该字段（保留首次失败原因，便于客服判断是用户 URL 配错还是我方问题）
- 重试成功后写 `pushed_to_passengerpool_at`，`push_error` **保留**（历史痕迹）
- UI：推送记录 tab 的失败行可展开看错误原因

#### 决定 4 · 申诉入口 ⏸（阶段 1c）

阶段 1a/1b **不做工单系统**（一个人运维，上工单系统是负担）。替代：
- 号列表 / 派发历史每行给「反馈问题」入口 → 预填 masked + 时间 + vendor → 走社群（TG / Discord）
- 客服（= 车主自己）拿 masked 去台账查
- 等用户量起来再评估要不要真做工单（阶段 1c 后）

**明确不做**：
- ❌ 保留明文备份「以防用户丢失」—— 违背 `CLAUDE.md §1.2` handoff 语义 + 合规风险（明文一秒不留是产品承诺）
- ❌ handoff 后可重新下载 —— 同上（UI 已明确告知「无法重新下载」）
- ❌ 延长 handoff TTL 到几小时 —— 明文在我方多留一秒都是风险，5 分钟够断线重试

**参考**：`09-transactions.md §4`（三段式交付）· `06-db-schema.md §11 §11.1`（台账）· `CLAUDE.md §1.2`（handoff 语义）

### 8.40 UI 结构 · /me 是综合入口 · 账号设置从 /me 拆到 /settings/account ✅（1a 落地）

**问题**：早期 `/me` 塞了「基本信息 + 改密码」两卡，`/settings` 索引底部带一段
「补车策略在车详情 · 账号和密码在我的」的提示。混乱在于：

1. **`/me` 不像标准 Me 页**——只有账号信息+改密码，没个人数据、没入口导航
2. **改密码本质是账号设置**（跟号池 / 通知 / API key 同类），却单独放在 `/me`
3. **`/settings` 索引底部还得贴纸条指路**——说明结构没自解释

#### 定稿的结构

| 路径 | 干什么 |
|---|---|
| `/me` | **综合 Me 页** · 个人信息 hero 卡 + 关键数据（余额/进行中的车）+ 累计数据（近 30 天）+ 快捷入口（3 大入口：钱包 / 我的车 / 设置） |
| `/settings` | 设置索引 · 5 张卡（拉号偏好 / 我的号池 / 机器人通知 / API key / **账号设置**） |
| `/settings/account` | **账号设置** · 账号信息（只读展示邮箱/用户名/注册时间）+ 改密码 + 第三方登录占位（Google/GitHub · 阶段 3+ 上线） |

**三条铁律**：

1. **`/me` 不放设置子项** —— 快捷入口只放"钱包/我的车/设置"这类**大入口**，不把号池/通知/API key/账号安全平铺出来。平铺=复制设置索引=两处维护
2. **改邮箱 / 用户名不做**（阶段 1）· 展示只读 · 副标注明"要改联系管理员 · 阶段 3+ 自助修改"
3. **第三方登录（Google / GitHub）阶段 3+ 才做** · 现在卡里放灰态"即将上线"占位，说明书面承诺，界面预留位置

#### 为什么不叫「账号安全」

最开始我把这页起名"账号安全"（只放改密码时的名字）。用户否决了：
- 邮箱、用户名、社交登录都不算"安全"，都算账号本身的设置
- 起「账号设置」跟其他 4 张设置卡的命名风格更一致（都是"XX 设置"）

现在扩到**三档**，因为：

1. **"社群"这个名字歧义** —— 车主群里全是**同行**（转卖号的中间商），"社群"通常指 TG/Discord 这类公开群，两个是不同人群。用同一个词很容易混
2. **两档之间跨度太大** —— 零售 2×、社群 1×，中间没有档位给 TG/Discord 里认真拼车的用户
3. **邀请码机制其实天然分两级**（同行群邀请制 vs TG/Discord 里发的），一直用"一种系统邀请码"是简化

#### 三档定稿

| 对外档 | 内部 tier | 谁 | 怎么进来 | 减免层 | 相对倍率 |
|---|---|---|---|---|---|
| **零售价** | `retail` | 散客 | 无码注册 | 无 · 全套加价 | 2.00× |
| **批发价** | `wholesale` | TG/Discord 社群成员 | 用**社群码**注册 | 免区域附加费 | ~1.67× |
| **同行价** | `insider` | 同行群（特殊邀请制）成员 | 用**同行码**注册 | 免 vendor 附加费 + 区域附加费 | 1.00× |

**关键洞察**：每一档"多减一层" —— 语义天然（越靠近核心圈 = 越便宜），
实现也天然（现有"有邀请码就免区域附加费"逻辑保留，"免 vendor 附加费"成为同行档专属）。

#### 加价链算例 · 号价 20 积分 · 拉 5 个号（不触发 count==1）

| 层 | 率 | 零售 | 批发 | 同行 |
|---|---|---|---|---|
| 号价 | - | 20.00 | 20.00 | 20.00 |
| × vendor 附加费 | 67% | ×1.67 → 33.40 | ×1.67 → 33.40 | ~~跳过~~ |
| × 区域附加费 | 20% | ×1.20 → 40.08 | ~~跳过~~ | ~~跳过~~ |
| × 服务费 | 5% | ×1.05 → **42.08** | ×1.05 → **35.07** | ×1.05 → **21.00** |
| 每号 USD（7 积分 ≈ 1 USD） | | **6.01** | **5.01** | **3.00** |

#### 邀请码机制 · 系统邀请码分裂成两类

`§8.32`（三种码）+ `§8.38`（专属邀请码交互）在此基础上加一维 `grants_tier`：

| 码类 | 对外叫 | 场景 | 授予结果 |
|---|---|---|---|
| **同行码** | 专属邀请码 · 同行 | 同行群邀请制 · 车主手发白名单 | `tier=insider` |
| **社群码** | 专属邀请码 · 社群 | TG/Discord 定期投放 · 车主批量生成 | `tier=wholesale` |
| 好友码（`personal_invite_code`）| 邀请码 | 现有 · 用户互邀 | 减手续费额度（不动 tier） |
| 优惠码（`coupon_code`）| 优惠码 | 现有 · 车主临时发 | 本次单拉减免（不动 tier） |

**对外文案铁律**（`CLAUDE.md §0.1 §12.6`）：
- ❌ UI 里**一律不出现**档次名：`retail / wholesale / insider` / `零售 / 批发 / 同行` / `零售价 / 批发价 / 同行价`——这些是**内部术语**
- ❌ UI 里不出现"同行码" / "社群码"（内部字段名）
- ✅ 两种系统码在 UI 上都叫**「专属邀请码」**——用户不需要知道自己拿的是哪级；后端按 `grants_tier` 定 tier
- ✅ 用户视角只有：**绑了专属邀请码 vs 没绑**（Chip 显示"社群成员"）· 加价链算完的最终单价就是他看到的
- 具体是批发还是同行**不下发前端**（`§8.20` 定的"不暴露加价幅度"逻辑一致）

**每人只能绑一次身份码** · 绑完 `tier` 定死 · 不能重复绑升降级。

#### 数据模型变更

**`passenger`** 表：
- 加 `tier TEXT NOT NULL DEFAULT 'retail' CHECK(tier IN ('retail','wholesale','insider'))`
- 保留 `invited BOOL`（下次 schema 变更时删 · 现阶段作为兜底）· 迁移：`invited=true → tier=insider`（保守 · 老用户不掉档）

**`system_invite_code`**（阶段 1b 建表）：
- 加 `grants_tier TEXT NOT NULL CHECK(grants_tier IN ('wholesale','insider'))`
- 白名单里的码按 `grants_tier` 决定授予哪档

**加价链**（`internal/decider/pricing.go` · 阶段 1b）：
- 输入 `passenger.tier` 而不是 `passenger.invited`
- `retail` → 全套 · `wholesale` → 跳过 region_markup · `insider` → 跳过 vendor_markup + region_markup

#### 与旧决策的关系

- **`§8.20` 双层机制** → 扩为三层 · `§8.20` 记录仍保留（讨论历史）· 术语替换：社群 → 同行 / 散客 → 零售
- **`§8.34` 加价栈** → 加价顺序不变 · 每档跳过的层数不同（见上表）· 服务费仍 5% 恒定
- **`§8.32` 三种码** → 变四种（同行码 / 社群码 / 好友码 / 优惠码）· 对外文案不变（两种系统码都叫"专属邀请码"）
- **`§8.38` 两种码补绑** → `/community` 补绑逻辑不变 · 补绑接口按 `grants_tier` 决定授予哪档

#### 老数据迁移策略

现有 `invited=true` 全部迁到 `tier=insider`（车主 2026-08-10 拍板 · 保守 · 老用户不掉档）。
未来如需重新划档，走「白名单降级」，不做自动降。

#### 批发档为什么不居中（不做 vendor 打折率）

批发理论中位应该在 1.50× ≈ 31.5 积分；实际方案是 1.67× ≈ 35 积分。
**为什么不做居中**：居中意味着"批发档 vendor 附加费打折"（新引入一档独立率），
`surcharge_rule` 表要多一条记录，加价链要多一个 tier-specific 分支。
**每档多减一层**这条更值得守住（干净、可解释），比精确居中价值更高。

### 8.38 两种邀请码的输入与补绑 ✅（1c 落地 · 补 §8.29 的交互缺口）

**对外命名**（这条最重要 —— 用户一定会混）：

| 内部字段 | **对外一律叫** | 干什么 | 谁受益 |
|---|---|---|---|
| `system_invite_code` | **专属邀请码** | 绑社群身份 · 拼车更便宜 | 填码的人 |
| `personal_invite_code` | **邀请码**（"邀请好友"页） | 拉人注册平台 | **发码的人**（手续费减免） |
| `bus.invite_code` | **拼车码** | 拉人进某一辆车摊单价 | 车里所有人 |

**关键：拼车侧叫「拼车码」不叫「邀请码」**。三个码都叫"邀请码"时，用户在
「邀请好友」页看到自己的码，会以为它能用来拉人进车 —— 而它不能。

原来的做法是在 `/invite` 页顶部加一段 Alert 解释「这个码不是拼车邀请码……」——
**那是用错名字之后的补救**，越解释越乱。改名之后那段解释直接删掉了：
名字本身就说清了用途，不需要额外说明。

❌ 不许在 UI 上出现「社群码」· ❌ 拼车侧不许叫「邀请码」。

#### 一个输入框认两种码 ✅

注册页**只有一个**「邀请码」输入框。后端 `Register` 先查 `system_invite_code` 白名单，
命中就是专属邀请码（给身份），否则当好友邀请码处理（给邀请人额度）。

**为什么不做两个输入框**：
- 受益人不同但**场景几乎不重叠** —— 你要么从社群来，要么被朋友拉来，同时拿到两个码概率极低
- 两个框的困惑成本（哪个填哪个？填错怎么办？）> 极少场景的收益
- **关键：不需要同时填也能都拿到** —— 用好友码注册（朋友得额度）→ 之后进社群 →
  `/community` 补绑专属邀请码（自己得社群价）· 两步都拿到

#### 补绑：专属邀请码可以 · 好友邀请码**不行** ✅

| | 专属邀请码 | 好友邀请码 |
|---|---|---|
| 供给 | 我方控制（白名单 + `max_uses`） | **每人自动有一个** |
| 受益人 | 填码的人 | **发码的人** |
| 补绑风险 | 低（码数量有限） | **高（两人互绑各刷额度）** |
| 能否补绑 | ✅ `POST /api/me/community-code` | ❌ **只能注册时** |

**为什么好友码必须堵死补绑**：减免额度是我方垫付给支付通道的真金白银。个人码人人都有、
没有供给上限，一旦允许老账号补绑，两个人互相绑对方的码就能凭空造钱。

代码上 `applyPersonalCodeTx` **只在 `Register` 里调**，注释里写了这个设计意图 ——
防止以后有人"顺手"加个补绑接口。

#### `/community` 页卡片顺序 ✅

**加入社群** 在上、**绑定专属邀请码** 在下。

#### 专属邀请码文案：说身份 · **不说获取路径** ✅

原文案「在社群里拿到专属邀请码后填这里」有两个问题：
1. **不准确** —— 不是加社群就有，是特定身份才有
2. **更糟：制造会落空的预期** —— 用户读完去加社群、发现没码，感觉被骗。
   这比不解释更伤

**定稿**：
| 位置 | 文案 |
|---|---|
| 副标 | 身份标识 · 邀请制 · 一个账号只能绑一次 |
| 表单底部 | 拿不到也不影响使用 · 持续拼车的车友会陆续收到 |
| 页头 | 有专属邀请码就绑上 · 享社群价，并且能看到上游真实名字 |
| 加入社群卡 | 公告 · 技术支持 · 公测期间的额度发放都在这里 |

**三条原则**（改这段文案前先看）：
- **不写获取路径** —— 身份象征之所以有效恰恰because不说明怎么拿。一说"只有 X 才有"
  就立刻造出了局外人
- **先消除焦虑再给预期** —— "拿不到也不影响使用" 在前，"会陆续收到" 在后
- **不承诺具体条件** —— ❌「拼 N 次就给」会变成硬指标，到时候不发就是失信

#### 邀请链接必须预填 ✅（修的 bug）

`/invite` 页复制的链接是 `/register?invite=CODE`，但注册页原来**只读 `?next=`** ——
点开看到空输入框，用户不手动填就没有邀请关系（等于邀请链接是废的）。现在读 `?invite=` 预填。

**参考**：`§8.29`（两种码职责）· `§8.32`（三种码对照）· `internal/passenger/invite.go`

### 8.37 提前下车的惩罚 ⏸（框架不支持 · 等积分锁定做了再迭代）

**问题**：成员随时能退出车，退出前刚让全车拉了一轮号、他用完就走 —— 剩下的人吃亏。

**决定：暂时不做**。现在的框架撑不起来 —— 惩罚要有效，前提是**上车时先冻结积分**：

```
上车先冻结一笔（起码覆盖预计车次：一天的 or N 轮的）
→ 正常参与就正常扣
→ 提前下车就从冻结里扣惩罚
```

现在没有"上车冻结"这个机制（`wallet.Reserve` 是**单轮拉号**的冻结，跟"入车押金"不是一回事：
生命周期不同、释放条件不同、金额算法不同）。硬加惩罚只能事后扣余额，而他要是余额为 0
就等于没惩罚 —— 规则形同虚设还不如不做。

**先记录，等做积分锁定时一起迭代**。需要的东西：
- `bus_member` 加冻结额字段（入车时冻 · 退出 / 解散时结算）
- 冻结额算法：预计车次 × 单价（一天的 or N 轮的 —— 具体口径待定）
- 跟单轮拉号冻结（`wallet.reserved`）**分开记** · 否则会互相挤

**当前行为**：提前下车**不退**已花的钱（§8.35 #12），但也**不额外罚**。

**参考**：`§8.35 #12` · `§8.18` · `internal/wallet`（Reserve 是单轮冻结·不是入车押金）

### 8.36 移除成员 = 车主有权 ✅（**覆盖 §8.18「改 share_pct 要全员确认」**）

**原规则**（§8.18 / §8.26）：移除成员会改其他人的 `share_pct`，等于悄悄让别人多掏钱，
所以必须全员确认，车主不能单方面触发。

**改成：车主有权直接移除 · 立即重算**。

**为什么推翻**：全员确认流程太复杂，而且现阶段没有对应的产品形态 ——
- 谁必须同意？超时算同意还是否决？确认期间车能不能拉号？—— 每个都要单独设计 + UI
- 车主移除的真实场景是"这人跑了 / 欠钱不还"，等全员确认反而**卡死**（欠钱那位当然不会点同意）
- 车是车主建的、邀请码是车主发的，**车主对成员构成有处置权**是符合直觉的

**规则**：
- 只 owner 能移除 · **不能移除自己**（要走「车设置 → 解散」）
- 移除后剩余活跃成员 `share_pct` **均分重算**（余数给 owner）
  - 为什么均分：原比例是历史协商结果·少一个人之后按什么比例分没有客观答案。
    均分谁也不多占·最不需要解释
- **不删 `bus_member` 行**（`left_at` 标记）—— 历史 `participants_split_json` 要能找到他，
  他那些号死了走质保退款照样退给他（§8.35 #19）
- 移除**不退**他已花的钱（§8.35 #12）

**车主想要非均分的比例**：得单独做"改分摊比例"流程，那个**仍然该全员确认**
（那是纯粹改钱的分配·跟移除不同）· 阶段 2+ 再说。

**UI 要说清挂起 vs 移除的区别**（否则车主会误用）：
- **挂起**：`share_pct` 保留 · 可逆 · 他充值就自己回来
- **移除**：`share_pct` 重算 · 不可逆 · 不退他钱

**参考**：`§8.18`（原全员确认规则 · 本条覆盖移除那部分）· `§8.26`（挂起 vs 移除）· `internal/bus/bus.go RemoveMember`

### 8.35 多人车资金场景全枚举 ✅（1c 落地 · 补齐 §8.18 / §8.23 / §8.26 的边界）

**背景**：1c 多人拼车落地时发现 `settle.go` 把整轮钱全扣发起人（注释写"1a 只做 single bus"），

- `credential_ledger.warranty_refunded_at` 是**幂等锚点**：条件 UPDATE 抢锁·**先抢锁再入账**·抢不到直接回滚（永不重复给钱）
- 当初 split 里号数为 0 的人不退（他那轮被跳过了 = 没付钱）

**参考**：`00 §7.5 规则 B` · `§8.18` · `§8.23` · `§8.26` · `internal/decider/split.go` · `internal/deathwatch/refund.go`

### 8.34 加价栈 = 逐层乘 · 服务费改回按率 ✅（**覆盖 §8.33 按号计费**）

**车主原话**：
> 你是按基数 x 的我是结果 x 倍率的

**我一直按加法算（每层加在号价上），车主的模型是逐层乘（每层乘在上一层结果上）。** 这是根本差异，不是舍入误差。

#### 两种模型的差

同样的率（vendor 50% · 区域 20% · 服务费 5%）、同样的号价 20：

| 模型 | 结果 |
|---|---|
| 加法（`00 §3` 原来这么写） | 20 × (1+0.5+0.2+0.05) = **35 积分** |
| **乘法（车主的）** | 20 × 1.5 × 1.2 × 1.05 = **37.8 积分** |

**率越多层，差越大** —— 这也是为什么必须先把模型说清再配率。

#### 乘法模型的两个结构优势

1. **顺序无关** —— 乘法可交换，`1.5 × 1.2 × 1.05` 不管先算哪个都一样。加法模型必须额外规定"加在号价上还是加在小计上"（`00 §3` 原来专门写了一句"议价费加在号价上，不加在总价上"），那句规定现在**不需要了**
2. **加插槽不用重算基数** —— 再插一条 10% 就是再乘 1.1，跟已有规则无关。加法下每加一条都要确认它加在谁身上

#### 服务费改回按率（覆盖 §8.33）

`§8.33` 定的"每个号 1 积分"**作废**，改成乘法链的最后一层 `× (1 + 服务费率)`。

**为什么这次是对的**（车主的推理）：服务费率**乘在已加价的金额上** → 零售用户单价本来就高 → 服务费绝对额自动跟着高 → **不需要再设社群/零售两档**（`§8.31` 那个问题从根上没了）。

按号 1 积分那版在号价 20 时恰好等于 5%，所以三轮下来数字碰巧一致 —— 但**结构不同**：按号是恒定额，按率随号价浮动。车主要的是后者。

#### 分项怎么拆（**实现必须照这个**）

乘法给出的是**总额**，但 `wallet_ledger` 要分项落账、API 响应也要分项返回。**交叉项归谁必须定死，否则三笔加起来不等于 total_debit。**

**规则：每一层的费额 = 该层因子作用在「它之前的累计小计」上的增量。**

按乘法链顺序逐层算，每层的增量就是那一层的费额：

```
s0 = 号价
s1 = s0 × (1 + vendor 率)        → vendor 附加费  = s1 − s0
s2 = s1 × (1 + 区域率)            → 区域附加费    = s2 − s1
s3 = s2 × (1 + 单次议价率)        → 单次议价      = s3 − s2
s4 = s3 × (1 + 插槽率…)           → 附加能力费    = s4 − s3
s5 = s4 × (1 + 服务费率)          → 服务费        = s5 − s4

最终单价 = s5
恒等式：号价 + Σ各层费额 = s5   ← 分项之和必然等于总额，不会有对不上的余数
```

**算例**（号价 20 · vendor 67% · 区域 20% · count==1 议价 20% · 服务费 5% · 零售）：

| 层 | 小计 | 该层费额 |
|---|---|---|
| 号价 | 20.00 | 20.00（pass-through 给 vendor） |
| vendor 附加费 | 33.40 | 13.40 |
| 区域附加费 | 40.08 | 6.68 |
| 单次议价 | 48.10 | 8.02 |
| 服务费 | 50.50 | 2.40 |

`20.00 + 13.40 + 6.68 + 8.02 + 2.40 = 50.50` ✅ 等于最终单价

**三条实现约束**：

1. **顺序影响分项，不影响总额** —— 乘法可交换所以 total 不变，但"谁乘在谁后面"决定各层分到多少。所以**链的顺序必须固定**（就按上面那个：号价 → vendor → 区域 → 议价 → 插槽 → 服务费），不能因为可交换就随便排
2. **舍入在最后一层做** —— 逐层取整会让分项之和跟总额差 1~2 microunit。做法：全程用整数 microunit 算，**每层费额取整后，最后一层用「总额 − 已分配」兜底**，保证恒等式成立
3. **`total_debit = 最终单价 × 号数`** · 分项也各自 × 号数（`service_fee_total` 等字段名里的 `_total` 就是这个意思）

**服务费那层的口径澄清**：它乘在**已加价的小计**上（上例是 48.10 × 5% = 2.40），不是乘号价（20 × 5% = 1）。这正是 §8.34 说的"零售服务费绝对额自动比社群高"—— 社群跳过区域附加费那层，小计更小，服务费也更小。

#### 目标价倒推（乘法模型）

批发（社群，只有服务费一层）= 20 × 1.05 = 21 积分 = **3 USD**（按 7 积分 ≈ 1 USD）

| vendor 附加费 | 零售单价 | 零售 / 批发 |
|---|---|---|
| 50%（车主初始说的） | 37.8 积分 = 5.4 USD | 1.80× |
| **67% ← 采用** | 42 积分 = **6.0 USD** | **2.00×** |
| 94% | 49 积分 = 7.0 USD | 2.33× |

**✅ 定了：按 2 倍配** —— `vendor 附加费 = 67%`。车主原话里"7 刀"（2.33 倍）不采用。

**初始配置**（都在 `surcharge_rule` 表里，后台可调，**不写进代码**）：

| 规则 | `kind` | 率 | 何时生效 |
|---|---|---|---|
| `vendor_markup` | `vendor` | **67%** | 每家可覆盖成不同值 |
| `region_markup` | `region` | **20%** | 无系统邀请码时 |
| `single_pull` | `adhoc` | **20%** | `count == 1` |
| `service_fee` | `service` | **5%** | 恒定（链上最后一层） |

**校验点**（后端实现时用它自测）：号价 20 积分 · 1 积分 = 1 RMB · 7 积分 ≈ 1 USD

- 社群批量：`20 × 1.05 = 21 积分 = 3.0 USD`
- 零售批量：`20 × 1.67 × 1.20 × 1.05 = 42.08 积分 = 6.01 USD` → **正好 2 倍**

> **自测时别拿舍入后的中间值接着算** —— 全程用整数 microunit 算到最后一层再舍入（`§8.34` 分项拆法第 2 条）。
- 零售单拉（count==1 再乘议价）：`20 × 1.67 × 1.20 × 1.20 × 1.05 = 50.50 积分 = 7.21 USD`

**倍数是目标，率是手段** —— 号价变了或想调倍数，改 `vendor_markup` 一个值即可。

#### 获利模型的诚实修正（`00 §3` 已改）

```
我方每号收入 = 号价 × (总倍率 − 1)
```

**「我方没有动机加价号成本」这条对齐激励失效了。** 早期它成立是因为收入 = Σ轮数 × 固定单价（跟号价无关）；现在几乎全部收入都是号价的百分比，**号价涨我方就赚更多**。

- 这不是设计失误，是**有意的取舍** —— vendor 附加费本来就是正常加价生意，靠固定小额服务费养不起运维
- 但**不能再对外声称那句话**，它现在是假的 · `00 §3` 已加显式标注
- 仍成立的替代表述：**我方没有动机把号价抬到乘客不拉的程度**（拉不动 = 零交付 = 零收入）—— 定价上限被需求侧约束着

**另一个后果**：服务费率在整条链里占比很小，是**零头不是主项**。主收入是 vendor 附加费那一层。定价心智上别搞反 —— 调收入规模靠 vendor 附加费，服务费率不是杠杆。

#### 落地铁律：这些率**只在文档和后台配置里，不进代码**

车主明确要求。理由不只是整洁：

- 前端代码**发到用户浏览器**，注释和常量在 devtools / source map 里都能读到
- `§8.20` 定了「UI 绝不显示原价 / 加价幅度」「不下发原价和加价明细」—— 把率写进前端等于把那条规则保护的东西泄出去

**已做的清理**：
- 前端注释里的加价率 / 倍数关系 / 社群零售差价**全部删除**，只留"这是预览、实际以服务端为准"
- 两个组件各写一遍的费用公式收进 `web/src/lib/pricing.ts` 一个函数（原来会各自漂移）· 文件头写明它是 **mock 阶段脚手架**，后端就绪后删掉、改用 `useEstimate()`
- `serviceFee()` 从 `lib/utils.ts`（会打进产物的公共模块）移走
- 产物扫过：`零售` / `批发` / `附加费` / `区域附加费` 命中 **0**；剩下的 `社群` / `加价` 全是用户可见文案（"社群成员" chip、"免加价"状态行），不含任何率

**真实计费只在服务端** —— `POST /api/me/pull/estimate` 已在契约里（`05-api-contract §5`），前端渲染返回值即可。前端算一份、后端算一份必然漂移，用户会看到预估跟实际扣款不一致。

**参考**：`00 §3`（公式 + 获利模型都已改）· `web/src/lib/pricing.ts` · §8.30（surcharge_rule）· §8.32（三种码）· §8.33（被本条覆盖）

### 8.33 服务费 = 每个号 1 积分 ❌（**已被 §8.34 覆盖** · 保留记录）

> **作废理由**：车主的加价模型是**逐层乘**，服务费是链上最后一层 `× (1 + 率)`，不是固定额。
> 按率之后零售的服务费绝对额自动比社群高 —— `§8.31` 两档制要解决的问题从根上没了。
> **本条纠正的那个老错（按次 → 按号）仍然有效且重要**：文档原写"一次动作一轮，跟 count 无关"，
> 那会让拉 10 个号只收 1 份服务费。乘法模型下这个错自然消失（单价 × 号数）。

**车主原话**：
> 我主要是考虑针对有邀请码和无邀请码设置 2 个价格很奇怪，而且之前说 1 个号 1 积分，拉一次 10 个号是 10 积分不是 1 积分

**两点合起来是一致的一件事**，而且第二点纠正了一个**一直写错的规则**：

#### ① 按号，不是按次（**这是老错**）

`00 §3` 原写「每人每**轮**固定单价」· `05-api-contract` 原写「一次动作一轮，**跟 count 无关**」—— 按这个实现，**拉 10 个号只收 1 积分**，服务费跟工作量完全脱钩。

**正确**：**每个号 1 积分**。拉 1 个 = 1 积分，拉 10 个 = **10 积分**。

#### ② 单一费率，不分社群 / 零售（**覆盖 §8.31**）

`§8.31` 定的 1/7 两档**作废**。理由（车主说"很奇怪"，我认为他对）：

- **区分社群和零售已经有专门的一项了** —— **区域附加费 20%**，有系统邀请码就免（`§8.32`）
- 服务费再按同一个身份分一档 = **对同一件事收两次差价**
- 用户视角更糟：同一个"服务费"名目在两个人账上是不同数字，很难解释

#### ③ 这同时回答了车主上一轮说的"按百分比更合理"

**1 积分/号 在号价 20 积分时约等于 5%** —— 车主的诉求是"服务费该跟量挂钩"，**按号计费天然实现了这个**，而且比真的写成百分比更好：

| | 按号 1 积分 | 真百分比（5%） |
|---|---|---|
| 号价 20 → 服务费 | 1 | 1 |
| 号价 40 → 服务费 | **1** | 2 |
| 可预期性 | **恒定**，用户一眼知道 10 个号 10 积分 | 随号价浮动，每次要算 |
| 对齐激励 | **跟号价无关** → 我方没动机加价号成本 | 号价越高我方赚越多 |

所以按号计费**兼得两者**：跟量挂钩（车主要的）+ 跟号价无关（`00 §3` 的对齐激励）。

#### 获利模型跟着改（`00 §3` 已更新）

```
我们收入 = Σ(交付的号数) × 1 积分
```

**按号比按轮更对齐**：按轮算的话我方最优策略是"多轮少号"（每轮 1 个号收 1 积分），跟乘客想要的"一次多拿"**相反**。按号算就没这个反向激励，而且多了一条正向的 —— **我方有动机多交付号**。

**诚实标注**：`vendor 附加费` 和 `区域附加费` 是按号价百分比的（`§8.32`），这两项**确实让我方从号价上涨中受益**。所以"没有动机加价号成本"这条严格来说**只对服务费成立**。但服务费是主收入，方向不会整体跑偏 —— 这个取舍已写进 `00 §3`。

#### 多人车怎么分

一轮拉 9 个号 → 服务费 **9 积分**，按各人 `share_pct` **分摊**（不是每人 9 积分）。

这跟 `00 §3` 原来写的"服务费固定、不分摊"**不一样了** —— 原来按人头收（3 人各付 1），现在按号数收再分摊。**按号计费下"不分摊"讲不通**：号是共享的，凭什么每人都为同一批号付全额服务费。

#### 落地

- `serviceFee(count)` 已改（`web/src/lib/utils.ts`）· 前端三处调用点全改
- UI 上标出算式：`服务费 · 1 × 3` → `3 积分`（让用户看得懂怎么来的）
- 后端 `pull_round.service_fee_total = purchased × SERVICE_FEE_PER_KEY`
- **单价做成后台可配**（`SERVICE_FEE_PER_KEY`），不写死在代码里

**参考**：`00 §3`（计费模型 + 获利模型都已改）· `CLAUDE.md §1.3` · `05-api-contract §5`（三处示例连算术一起改）· §8.31（被本条覆盖）· §8.32（区域附加费才是分社群/零售的那一项）

### 8.32 三种码 · 各减免什么 + 加价栈定稿 ⏸（阶段 1b · 加价栈模型见 `§8.34`）

**车主原话**：
> 有系统邀请码，进去是没有区域附加费的。我们是 20% 单次/批量 + 20% 区域附加费 + 服务费（**感觉其实服务费按百分比更合理**）的，系统邀请码可以减免区域附加费，个人邀请码是按限制减免，限制过了就恢复了，比如减免的是充值通道费 5%（限次数或者限时）。随机的邀请码，这个是临时少量的，支付的时候少比如 20% 按此的。可能就是比如单次的有这个相当于可以把这个减免掉，批量的相当于更优惠了。但是我可能不会这么高，可能少 5% + vendor 附加费，是我们 vendor 定价的基础上加价，比如 5%。我们是多插槽的。

#### 三种码 · 职责完全不同（这是本条的核心）

| | **系统邀请码** | **个人邀请码** | **随机优惠码** |
|---|---|---|---|
| 谁发 | 我方 → 社群 | 每个乘客自动有 | 我方临时少量发 |
| 填在哪 | **注册时** | 注册时 / 使用时 | **支付 / 提号确认窗** |
| 减免什么 | **区域附加费 20%** | **充值通道费 5%** | 提号时**减 5~20%** |
| 持久性 | **永久绑账号** | **限次数或限时**，用完/过期就恢复 | **单次** |
| 解锁 vendor 真名 | ✅ | ❌ | ❌ |
| `passenger.invited` | `true` | 不变（仍 false） | 不变 |

**三条互不重叠** —— 各自减免的是**不同的费用项**，所以可以叠加（一个人可以同时是社群身份 + 有个人码额度 + 本次用了优惠码）。

**个人邀请码减免的是通道费**（车主明确说的）。这跟我上一轮 `§8.29` 写的「减免服务费」**不一样，按车主的改**。但要记清代价：

- 通道费是 **waffo 实收的 5%**，我方减免 = **我方自掏腰包垫付**
- 这**违反** `00 §3` / `§2.13` 的「pass-through，我方不加不承担」原则
- **但车主明确要这么做**，所以它不是"违反"而是**有意的营销支出** —— 类似"充值返现"
- 正因为是真金白银的支出，「**限次数或限时**」这个约束**不是可选项，是必须的**（车主也这么说了）· 必须有硬上限，否则是无底洞
- 会计上要**单独记一个科目**（`channel_fee_subsidy`），不要混进 `channel_fee` —— 否则财务上看不出补贴了多少

#### 加价栈定稿

```
号价（vendor 报价 · 按 vendor_pricing 换算成积分）
  + vendor 附加费     号价 × 5%（每家可不同 · 在我方 vendor 定价基础上加）
  + 区域附加费        号价 × 20%   ← 有系统邀请码则免
  + 单次议价          号价 × 20%   ← 仅 count==1
  + 插槽（多个）      号价 × N%    ← capability / adhoc · 动态增减
  + 服务费            ⚠️ 固定两档 or 百分比 · 见下面待定
  ──────────────────────────────
  = 本次扣除

（充值时另收）通道费 5% → 个人邀请码可在限额内减免
（提号确认窗）随机优惠码 → 减 5~20%
```

**「多插槽」= `§8.30 B` 那张 `surcharge_rule` 表**：上面每一项（vendor / region / capability / adhoc）都是表里一行，`applies_when_json` 控制什么条件开启、`waived_when_json` 控制什么条件减免。加新收费点 = 插一行，不改代码。这正是车主要的"控制哪个开启，什么条件开启，什么条件减免"。

#### 随机优惠码的额度 · 5% 还是 20%

车主自己在原话里推翻了一次：先说 20%，又说「**我可能不会这么高，可能少 5%**」。

他观察到的那个效应是对的：
- **20% 的码 + `count==1`** → 正好抵掉单次议价，等于"单拉也不罚"
- **20% 的码 + 批量**（本来就没单次议价）→ 净赚 20%，**批量反而更优惠**

这个"批量更优惠"的方向跟 `00 §3`「天然鼓励批量」一致，不冲突。但 20% 对批量单是纯让利，成本不低。

**建议：额度做成后台可配（`coupon_code.discount_bp`），默认 5%，需要冲量时临时发 20% 的。** 不写死在代码里 —— 这本来就是"临时少量发"的营销工具。

#### 服务费口径 → ✅ 已定，见 `§8.34`：**加价链最后一层 `× (1+率)`**

下面这段是当时的论证，保留备查。结论被「按号计费」绕过了 —— 它既跟量挂钩（车主要的那个「百分比感」），又跟号价无关（保住对齐激励），两头都占。

<summary>原论证：固定两档 vs 百分比</summary>

车主这次说「**感觉其实服务费按百分比更合理**」，但上一轮刚定了两档固定（`§8.31`：社群 1 / 零售 7 积分）。**这两个方向互斥，得选一个。**

**百分比制的代价（必须知道再决定）**：

`00 §3` 有一条推导 —— 「我方收入 = Σ轮数 × **固定**单价」→ 所以「**我方没有动机加价号成本**」。这是写进价值观的**对齐激励**。服务费改成百分比后，号价越高我方赚越多，这条推导就不成立了。

**但**：`vendor 附加费` 和 `区域附加费` 本来就是按号价百分比的 —— 所以**这个激励其实已经部分破了**。服务费再改百分比，只是让它破得更彻底一点，不是从 0 到 1。

**两种制度的实际差异**（以零售用户为例，假设百分比取 10%）：

| 号价 | 固定制（7 积分） | 百分比制（10%） | 差异 |
|---|---|---|---|
| 拉 1 个 · 20 积分 | +7（**占号价 35%**） | +2 | 固定制贵得多 |
| 拉 1 个 · 100 积分 | +7 | +10 | 百分比制略贵 |
| 拉 10 个 · 200 积分 | +7（**占 3.5%**） | +20 | 百分比制贵 3 倍 |

**关键差异不在贵贱，在结构**：
- **固定制**：小单贵（7 积分对 20 积分的号是 35% 的税）· 大单几乎免费（3.5%）· **强烈鼓励批量**
- **百分比制**：跟单量无关，永远同一比例 · **对批量没有额外激励**，而且大单绝对额高
- 现在「单次议价 20%」已经在惩罚小单了，固定服务费是**第二层**惩罚 —— 两者叠加，小单可能贵到没人拉

**我的建议：保持固定两档，理由是它跟"鼓励批量"这个产品目标一致**（拼车的本质就是凑批量）。如果嫌 7 积分对小额号太重，调低零售档（比如 3-4 积分）比改成百分比更简单，也不动对齐激励。

**但这是你的商业判断，不是技术问题** —— 代码里 `serviceFee()` 已经收口在一处，改动很小。

### 8.31 服务费两档 · 社群 1 积分 / 零售 7 积分 ❌（**已被 §8.33 → §8.34 覆盖** · 保留记录）

> **作废理由**（车主原话：针对有邀请码和无邀请码设置 2 个价格很奇怪）：
> 区分社群 / 零售已经由**区域附加费 20%** 承担，服务费再分一档是对同一件事重复计价。
> **现行规则：加价链最后一层 `× (1+服务费率)`**（`§8.34`）· 按率不按额。
> 下面内容保留 —— 其中「7 是定价档位不是实时汇率」「优惠码不改身份档位」两条论证在别处仍有参考价值。

**车主原话**：
> 服务费有系统邀请码是 1 积分，没有系统邀请码是 1$，1 积分 = 1RMB，没有系统邀请码是 7 积分约等于 1 $

| 身份 | 服务费 / 人·轮 | 判据 |
|---|---|---|
| **社群** | **1 积分**（= 1 RMB） | 注册时填了**系统**邀请码 → `passenger.invited = true` |
| **零售** | **7 积分**（≈ 1 USD） | 没填 / 只填了个人码 → `invited = false` |

**这解掉了 §8.30 待确认 ①，而且不是原来给的两个选项** —— 既不是"固定 1 元"也不是"1%"，是**两档固定费**。

**关键：仍是固定费** → `00 §3` 的对齐激励（**我方没有动机加价号成本**，因为收入 = Σ轮数 × 固定单价，跟号价无关）**完整保住**。百分比制才会破坏它。

#### 三条实现约束

1. **7 是定价档位，不是实时汇率**
   - 不接汇率 API 算这个数。汇率波动让用户看到服务费每天变是糟糕体验，而且 1 USD 这个量级下汇率波动的绝对值很小，不值得引入外部依赖 + 失败面
   - 真实汇率只用于 **vendor 成本换算**（`vendor_pricing.credits_per_unit` · `§8.30 A`）—— 那是我方成本，跟对用户的定价档位是两回事
   - 汇率长期漂移到 7 明显不合理时，**手工改这个常量**（后台可配）

2. **优惠码不改档位**
   - 优惠码只免**零售附加费**（`§8.20`）· 服务费档位**只看注册时的系统邀请码**
   - 理由：档位是**身份**（永久绑账号），优惠码是**单次减免**。让优惠码能降服务费档，等于把永久身份变成一次性可买 —— 社群身份就不值钱了

3. **个人邀请码不给社群档**
   - `§8.29` 已定个人码不解锁社群身份 · 本条让那个区分**更值钱**了（差 7 倍不是 20%）
   - 所以 `§8.29` 那个"邀请奖励 = N 轮服务费全免"对**零售**邀请人价值 7 倍于社群邀请人（3 轮 = 21 积分 vs 3 积分）· 这个不对称是合理的（零售本来付得多）

#### 零售总成本的量级（拍这个数之前先看清）

拉 1 个 20 积分的号：

| | 社群 | 零售 |
|---|---|---|
| 号价 | 20 | 20 |
| 零售附加费 20%（§8.20） | 0 | +4 |
| 单次议价 20%（count==1） | +4 | +4 |
| 服务费 | +1 | **+7** |
| **合计** | **25** | **35** |

**零售比社群贵 40%**。批量拉时差距收窄（服务费按轮不按号）：拉 10 个 → 社群 201 / 零售 247，贵 23%。

**这是主要的变现杠杆**，也意味着**社群邀请码的分发要克制** —— 发滥了收入结构就塌了。

#### 待确认（多人车 · 不挡 1a）

多人车里成员身份可能不同（2 个零售 + 1 个社群），服务费是「**各人按自己的档位付**」还是「**按 share_pct 分摊总额**」？

- 我倾向**各人按自己档位付**：服务费是"每人每次动作"的固定费，本来就不分摊（`00 §3` 明确写了"固定，不分摊"）· 3 人车一轮 = 7+7+1 = 15 积分
- 阶段 1a 全是 1 人车，不挡开工 · 2a 做多人车分摊时定

### 8.30 加价栈重构 · vendor 定价配置 + 统一 surcharge 插槽 ⏸（阶段 1b）

**车主原话**：
> 我们后台或者服务配置，最好每个 vendor 对应有他的积分价格、vendor 积分对 rmb 还是 usd、对应价格是多少、转换 rmb 或 usd 是多少。我们每个 vendor 的加价控制之前是 1% 的服务费，内部还要有个加价。比如活得特别长的车可能临时加价。所以我们是 vendor 附加费 + 服务费 + 区域附加费 + 零售附加费 + 插槽（可动态增加减少）控制哪个开启，什么条件开启，什么条件减免。

#### A. vendor 定价配置（无冲突 · 直接做）

`07-provider-contract §161-166` 已经暴露出这个需求：**各家 vendor 的价格口径本来就不一致** ——

| vendor | 价格字段 | 币种 |
|---|---|---|
| 91kiro / kiroceo | `zones[].unit_price` | CNY |
| kirooo | `key-price-tiers` **阶梯**（产量越大单价越低） | CNY |
| kiroappio | `price_min` / `price_max` **区间** | CNY |
| **kirodrop** | `stock.price` | **USD** |

那份文档里写了「混币在 decider 里换算」但没定换算表在哪。落成一张配置表：

```sql
CREATE TABLE vendor_pricing (
  vendor_id            TEXT PRIMARY KEY,
  -- vendor 报价的原始币种（我方不改它，只做换算）
  quote_currency       TEXT NOT NULL,          -- CNY | USD
  -- 换算成积分的汇率 · 1 积分 = 1 CNY（decisions §8.7）
  -- CNY 家填 1_000_000（1:1）· USD 家填当期汇率 × 1_000_000
  credits_per_unit     INTEGER NOT NULL,       -- microunit
  rate_source          TEXT,                    -- manual | 汇率 API 名（阶段 1b 先 manual）
  rate_updated_at      TEXT,
  -- 该 vendor 的附加费（我方内部加价 · 见 B）
  vendor_surcharge_bp  INTEGER NOT NULL DEFAULT 0,
  active               INTEGER NOT NULL DEFAULT 1,
  updated_at           TEXT NOT NULL
);
```

**汇率阶段 1b 手工配**（`rate_source='manual'`）—— 接汇率 API 是额外的外部依赖和失败面，等 USD 家的量起来再说。手工配的风险是汇率漂移吃掉利润，所以 `rate_updated_at` 要在后台显眼处提示"多久没更新了"。

#### B. 统一 surcharge 插槽（**推荐把 5 类合并成一张表**）

车主列的 5 类：`vendor 附加费 + 服务费 + 区域附加费 + 零售附加费 + 插槽`。其中"插槽"本来就是 `capability_slot`（`06-db-schema §15`），而前 4 类的结构完全一样（都是"某条件下按号价加 X%"）。**建议合并成一张 `surcharge_rule`**，`capability_slot` 并入它：

```sql
CREATE TABLE surcharge_rule (
  id                  TEXT PRIMARY KEY,
  kind                TEXT NOT NULL,          -- vendor | zone | retail | capability | adhoc
  name                TEXT NOT NULL UNIQUE,   -- 'retail_markup' | 'zone_eu' | 'long_life_bump' …
  rate_bp             INTEGER NOT NULL,       -- basis point · 2000 = 20%
  base                TEXT NOT NULL DEFAULT 'key_cost',  -- 加在号价上（跟 00 §3「议价费加在号价上」一致）
  active              INTEGER NOT NULL DEFAULT 0,
  -- 什么条件开启（JSON 谓词 · 例 {"vendor_id":"kirodrop"} / {"zone":"eu"}
  --   / {"passenger.invited":false} / {"bus.avg_lifespan_h":{">":48}}）
  applies_when_json   TEXT,
  -- 什么条件减免（例 {"coupon_code":"any"} / {"passenger.invited":true}）· 优先级高于 applies_when
  waived_when_json    TEXT,
  -- 用户能否主动勾选（capability 类为 1，其余 0 —— 系统自动判定）
  user_selectable     INTEGER NOT NULL DEFAULT 0,
  priority            INTEGER NOT NULL DEFAULT 100,   -- 多条同时命中时的计算顺序
  created_at          TEXT NOT NULL,
  updated_at          TEXT NOT NULL
);
```

**为什么合并**：车主要的是「**插槽控制哪个开启、什么条件开启、什么条件减免**」—— 这句话对 5 类都成立。分成 5 张表就要写 5 套判定逻辑、5 个后台页面；合并成一张，定价引擎只需**一次遍历**：取所有 `active=1` 且 `applies_when` 命中且 `waived_when` 未命中的规则，按 `priority` 累加。加新收费点 = 插一行，不改代码。

**`long_life_bump` 就是车主说的"活得特别长的车可能临时加价"** —— `kind='adhoc'`，`applies_when_json: {"bus.avg_lifespan_h":{">":48}}`。

**合并后 `capability_slot` / `pull_round_capability` 作废**，改成 `surcharge_rule` + `pull_round_surcharge`（记每轮实际命中了哪几条、各收了多少，便于回溯和申诉）。

#### C. 加价栈的完整顺序（合并车主的 5 类 + 现有规则）

```
号价（pass-through · 按 vendor_pricing 换算成积分）
  + 号价 × Σ(命中的 surcharge_rule.rate_bp)     ← vendor / zone / retail / capability / adhoc
  + 单次议价（count==1 时号价 × 20%）
  + 服务费（每人每次固定 1 积分 · 见待确认 ①）
  ────────────────────────────────────────
  = 乘客本次扣除
  （通道费不在这里 —— 只在充值时收一次 · §8.21）
```

跟 `00 §3` 现有公式的关系：**结构不变**（都是"号价 + 号价的百分比项 + 固定服务费"），只是把"附加能力费"这一项从单一插槽扩展成 5 类可配规则。

### 8.29 邀请制 · 个人码 vs 系统码 + 邀请奖励 ⏸（v1 上线后立即补 · 阶段 1b）

**车主原话**：
> 第一版上线之后立马补充邀请制。个人邀请码、和系统邀请码划分零售和社群的不是一种。邀请人进来可以 N 轮减免 5% 手续费或者服务费，看哪种。

#### 两种码 · 职责不同（关键区分）

`§8.20` 定了「邀请码（注册时）」vs「优惠码（支付/提号时）」。本条在**邀请码内部再分两类**：

**完整的三种码对照表见 `§8.32`**（本条只讲注册相关的两种）。

| | **系统邀请码** | **个人邀请码** |
|---|---|---|
| 谁发 | 我方（发给社群） | 每个乘客都自动有一个 |
| 作用 | **划社群身份** → 解锁 vendor 真名 + **免区域附加费 20%** | **减免充值通道费 5%**（限次数 / 限时 · §8.32） |
| 被邀请人身份 | **社群** | **仍是零售**（照加区域附加费） |
| `passenger.invited` | `true` | `false` |

**这是本条的核心，也是必须分两类的原因**：如果个人码也解锁社群身份，那**任何人都能生成码让别人免区域附加费** → 20% 加价形同虚设 → `§8.20` 的整个定价分层崩掉。所以个人码**只给通道费减免额度，不改身份**。

#### 邀请奖励

> ⚠️ **本小节已被 `§8.32` 修订**：车主明确定为「个人邀请码减免**充值通道费 5%**，限次数或限时，额度用完就恢复」。
>
> 下面这段是我原来建议的"减免服务费"方案 + 论证，**保留备查**（论证本身仍然成立 —— 减免通道费确实是我方垫付，所以 `§8.32` 里加了"必须有硬上限 + 单独记 `channel_fee_subsidy` 科目"两条约束）。

**减免对象建议选「服务费」不选「手续费」**：

| | 手续费（通道费 5%） | **服务费（推荐）** |
|---|---|---|
| 归属 | **waffo 的**，pass-through | **我方收入** |
| 减免意味着 | 我方**自掏腰包垫付** —— 直接违反 `00 §3`「pass-through，我方不加不承担」和 `§2.13` | 少赚，不倒贴 |
| 触发时机 | **只在充值时**（§8.21） | 每次拉号 |
| 跟"N 轮"匹配吗 | ❌ 充值跟"轮"没关系 | ✅ 服务费本来就是按轮收的 |

所以：**邀请人获得 N 轮服务费减免**。

**但减免比例不能是 5%** —— 服务费是每号 1 积分（`§8.33`），5% 就是 0.05 积分/号，无感。**按轮全免**才有感知：

```
邀请 1 人成功注册并完成首次拉号 → 邀请人获得 3 轮「服务费全免」
```

| 参数 | 建议值 | 说明 |
|---|---|---|
| 每邀请 1 人奖励轮数 | **3 轮** | 可后台配 |
| 生效条件 | 被邀请人**完成首次拉号** | 防刷号注册（只注册不消费不给奖） |
| 有效期 | 90 天 | 不做永久，免得账上挂一堆永不过期的债 |
| 累积上限 | 待定 | 防止有人靠拉人把服务费永久免掉 |

**奖励价值取决于那几轮拉了多少号**（`§8.33` 服务费按号计费之后）：

| 被奖励的轮次拉了几个号 | 3 轮全免值多少 |
|---|---|
| 每轮 1 个（小单） | 3 积分 |
| 每轮 10 个（批量） | **30 积分** |

**这个不确定性是个问题** —— 奖励价值随用户行为浮动 10 倍，我方无法预估这项营销支出的上限。

**所以按轮全免可能不如「固定额度」**：直接给「**减免 N 积分服务费**」（例 10 积分），用户自己决定怎么花完。额度封顶、口径清晰、财务可预测。**待车主定**（不挡 1a —— 邀请制整体是 1b）。

```sql
  expires_at        TEXT NOT NULL,
  created_at        TEXT NOT NULL,
  UNIQUE (inviter_id, invitee_id),          -- 同一对只奖一次
  FOREIGN KEY (inviter_id) REFERENCES passenger(id),
  FOREIGN KEY (invitee_id) REFERENCES passenger(id)
);
```

计费时：若邀请人有 `status='active'` 且未过期的 reward，本轮服务费记 0 并 `rounds_used += 1`，`wallet_ledger` 留一条 `service_fee_waived` 说明来源（用户要看得见"这轮免了，因为邀请了 @xx"）。

### 8.27 设置是主入口 · 全局上限归设置 · 每车策略归车 ✅（前端已做）

**背景**：`§8.6` 定了"补车策略跟 bus 绑，不放全局设置"。这条**没错但被过度引用** —— 它说的是**每车的补车策略**，不是**全局上限**。两者被混成一件事，结果全局那半边一直没有入口。

**缺口**：`06-db-schema §16 passenger_strategy_default` 里 `daily_round_limit` / `daily_spend_limit` 是**全局**的（跨所有车累加，跟车级限额 **AND**），而且 **提取 key 只受这个全局限额管**（车级限额管不到 record group）。`05-api-contract` 也已把 `GET/PUT /api/me/strategy` 标成阶段 1a。但前端零入口 —— **用户被一个自己看不见也改不了的限额管着**。

**三层分工**（`14-extract-page-plan §5.1` 已定，这里落地）：

| 层 | 放哪 | 管什么 |
|---|---|---|
| **手动拉号** | 拉号 / 提取弹窗 | 当次的 count / zone / vendor · **无护栏** · 眼见为实价 |
| **每车策略**（§8.6） | **车详情 › 补车策略 tab** | 那辆车的自动补车：watermark / per_round_count / 车级限额 |

**「设置」是真主入口**：`/settings` 索引页，四张卡（拉号偏好 / 我的号池 / 机器人通知 / API key），每张带实时状态。**凡是"跨对象复用的配置"都归设置**；**跟单个对象绑的配置归那个对象自己的页面**（车策略在车里、成员在车里）。

**拉号偏好页 · 两块分开摆**（语义不同，混一起会让人以为改默认值就改了上限）：

**① 拉号上限**（`拉号上限` card）—— 会真的拦下操作
- **单价上限**：「单价超过 N 就不拉」· 每次都判 · 单独一行（跟下面两个"每天累加"的判法不同）
- **每天最多几轮 / 最多花多少**：跨所有车累加 · 带今日用量进度条（<80% 绿 / ≥80% 黄 / 满 红 +「已拉满」）
- 留空 = 不限 · **不限时不画进度条**（没有分母，画了是假的）

**② 新车默认值** —— 只预填新车，改它不动已有的车（每次几个 / 默认来源 / 默认区域）

**单价上限是硬上限，不是"新车默认值"**（本条初稿放错过）：
- **手动拉号也拦** —— 提取确认窗里超了就**禁用确认按钮**，提示「现在 26 / 你的上限 5 / 超了 21」+ 给「去拉号偏好调高上限」的链接

### 8.26 成员欠费 · 挂起而不停车 + 成员管理 tab ✅（前端已做 · 后端阶段 2a）

**缺口**：§8.23 定了"余额不足只跳过那个人"，但漏了长期后果 —— 他一直不充值，这辆车的分摊就一直是坏的。

**决定：挂起那个成员，车继续跑**

| 触发 | 动作 |
|---|---|
| 余额不足 | **本次跳过** · 不扣钱 · 不给取这批号 · `skipped_count += 1` |
| 连续被跳过 **3 次**（`SUSPEND_AFTER`） | **自动挂起** · `status = suspended` |
| 挂起期间 | `RevokeClientKey`（取不到号）· 不参与任何分摊 · **`share_pct` 不动** |
| 他充值 | **自己解挂** · `skipped_count` 归零 · 不用车主批 |
| 车主想彻底换人 | **手动移除** · 车主有权直接移除（§8.36）· 剩余成员均分重算 |

**为什么挂起而不停车**：一个人欠钱，停车是把他的问题变成全车人的问题 —— 其他人的号照样在死、照样要补。**挂起只影响他自己**。

**为什么不自动移除**：移除会改所有人的 `share_pct`。**车主可以手动移除**（§8.36 已给车主这个权利），但系统不该自动踢人 —— 欠费的人挂起就够了，自动移除等于系统替车主做人事决定。

**挂起 vs 移除的区别**（UI 上要说清，否则车主会误用）：
- **挂起**：`share_pct` 保留 · 可逆 · 他充值就回来
- **移除**：`share_pct` 重算分给其他人 · **车主有权直接做**（§8.36）· 不可逆

**成员管理 tab**（BusDetail 第 4 个 tab · tab 顺序：号列表 / 拉号历史 / 推送记录 / **成员** / 补车策略 / 数据）：
- 表格列：成员（头像 + 名 + 车主 chip + 进车时间）/ 分摊 % / 余额 / 状态 / 操作
- 状态三态：**正常** / **已跳过 N/3**（warn · 副行"再 M 次自动挂起"）/ **已挂起**（副行"取不到号 · 不参与分摊"）
- 操作：`挂起 / 解挂` 按钮 + `移除` icon 按钮（移除走确认弹窗，弹窗里引导"只是暂时没钱用挂起更合适"）
- **车主自己那行没有操作**（不能挂起 / 移除自己 · 要退出走「车设置 → 解散」）
- **1 人车不显示表格** —— 只有你，没人可挂起也没人可移除，显示"1 人车 · 只有你"
- **拉人进车**：team 车显示邀请码 + 复制 + 「换一个」（旧码立即失效，已进车的人不受影响）

**状态别猜，读事实**：`余额够不够` 是相对"下一轮花多少"的，而那个数不知道（价格随行就市）。所以 UI **不用 `spend_today × share_pct` 去估**，只报后端记下的 `skipped_count` —— 他实际被跳过过几次。

**数据落地（阶段 2a）**：
- `bus_member` 加 `status ∈ {active, suspended}` / `skipped_count` / `last_skipped_at`
- 充值成功后（`wallet` 侧）把该乘客所有车的 `skipped_count` 归零 + 解挂
- 挂起 / 解挂 / 移除都要发通知给当事人（走 §8.17 通道）

**UI 状态收敛**（§12.5）：成员对外只有 **正常 / 已挂起** 二态 · `skipped_count` 是个计数不是状态

**拒绝**：
- ❌ **停车（整车暂停）** —— 一人欠费惩罚全车
- ❌ **自动移除** —— 悄悄改别人的 share_pct
- ❌ **记债务 / 账期** —— §8.18 §8.23 已否决，阶段 2a 太重
- ⚠️ **车主一人拍板改 share_pct** —— 移除成员这条**已放开**（§8.36 覆盖）· 但「直接改某人的百分比」仍该全员确认（那是纯改钱的分配·跟移除不同）

### 8.23 自费拉的号派进多人车 · 按份额即时清算 ⏸（阶段 2a · 补 §8.18 的缺口）

**缺口**：`§8.18` 只定了「车内拉号时按 `share_pct` 从各成员钱包同时扣」。但漏了这条路径：

> 我从「提取 key」**自己掏钱**拉了号 → 派进车 → 车里其他人也用 → 我垫的钱谁还？

现在实现里 `assign → into_bus` 只改 `owner_bus_id`，**没有任何资金结算** —— 号变成车的共享资源，钱却是一个人出的。没人愿意先垫钱，多人车玩不起来。

**决定：按份额即时清算（方案 A）**

派进车那一刻，按车内 `share_pct` 从其他成员钱包扣、进派入者钱包：

```
我拉号花 100 积分 · 车内 我 40% / A 30% / B 30%
派进车时：A 扣 30 → 我入账 30
         B 扣 30 → 我入账 30
         我净支出 40（= 我该承担的份额）
```

**会计语义**：成员向派入者**买入份额**，我方是清算通道（不抽成 —— 服务费已在拉号时收过）。

**关键规则**：
- **不再收 vendor 费用** —— 号价在提取时已付给 vendor，派发只是内部记账转移
- **余额不足 → 只跳过那个人，不拒绝整车**（**修正**本条早先写的"任何一人不足则拒绝派入"）：
  - 号**已经是我的、钱已经付给 vendor 了** —— 少一个人分摊只是我少收回一点，不是派不进去
  - 那个人这一次：**不扣他积分**，也**不给他取这批号**（`RevokeClientKey`）· `share_pct` 不动
  - 我净支出 = 我那份 + 被跳过的那部分
  - **只有一个人都参与不了才拦** —— 那时候派进去等于纯赠送，提示「等他们充值或先解挂」
  - 挂起的成员（§8.26）同理不参与
- **不做应收/账期** —— 跳过就跳过，不记债务（阶段 2a 太重）· 长期不还走 §8.26 挂起
- **单人车不清算** —— 就一个人，没有分摊对象

**拒绝的替代方案**：
- ❌ **按实际用量后结算** —— `§8.18` 已否决后结算（频率 / 边界模糊）；且 credential 级用量归属 vendor 不给数据
- ❌ **不结算视为赠与** —— 没人愿意垫钱，多人车成不了

**数据落地（阶段 2a）**：
- `assign_event` 加 `settlement JSON`：`[{ member_id, amount, direction }]` · 便于回溯
- `wallet_ledger.reason` 加两种：`share_income`（派入者收）/ `share_expense`（成员付）
- 清算和 `owner_bus_id` 变更**同一事务**（避免"号进车了但钱没结"）

**UI（阶段 2a）**：

派进车确认弹窗 · **选完车之后**出清算提示（选车前算不出来 —— 不知道跟谁分摊）：

| 情况 | 显示 |
|---|---|
| 选中**单人车** | 「独享车 · 无分摊」一句灰字 |
| 选中**多人车** | **一行**：「车友分摊后你将收到 **60 积分**」 |
| 有人参与不了 | 上面那行照出（金额只算付得起的）+ warn 一行「@lin（余额不足）· @zhou（已挂起）· 本次跳过 · 你少收 **15 积分**」· 确认按钮**可用** |
| 一个人都参与不了 | danger「没有车友能参与这次分摊 · 现在派进去等于你白送」· 确认按钮禁用 |

**只给结果，不列明细** —— 用户要知道的就是"我能收回多少"。逐成员的份额明细在车详情页的成员 tab 能看，不在这里重复。

- 有人被跳过时才展开说是谁 + 我少收多少（这时候用户必须知道是谁）· 但**不拦**
- 成员侧收到通知（走 §8.17 通知通道）：「@you 派了 3 个号进「周末拼车局」· 你分摊 30 积分」
- 钱包流水能看到 `share_income` / `share_expense`

**阶段 1a 前端已做这个预览**（覆盖本条早先"1a 不做"的判断）：`bus.members[]` 带 `share_pct` + `balance` 后，mock 里那辆 team 车（`bus_kiro` · 我 40% / wei 35% / lin 25%）算得出真数，不是编的。三种态在 mock 上都可达：
- 选 single 车（`bus_weekend` / `bus_daily`）→ 「独享车 · 无分摊」
- 选 `bus_kiro` 派 2 个号（40 积分）→ 「车友分摊后你将收到 24 积分」
- 选 `bus_kiro` 派 3+ 个号 → lin 余额（12 积分）不够他那 25%，出「@lin 余额不足」+ 确认禁用

**后端结算仍是阶段 2a**（`settlement JSON` / `wallet_ledger` 两种 reason / 同事务）。前端现在只做**预览**，`assign → into_bus` 后端仍不动钱。

  - 竖条上下端 = 当天最高 / 最低轮价 · 颜色深浅 = 那天几轮车 · 横线 = 只 1 轮 · 灰点 = 没车

  - Y 轴**每行独立**（各家价格量级差太多，共享轴会把竖条压成一条线）
  - 颜色**统一品牌紫**（每行独占不重叠 → 不需要区分色相 · 深浅表达轮数）
- **数据模型**：存**轮次级**（`VendorRound` / `VendorDayRounds`），聚合值前端派生
- **Mock 铁律**：**禁止随机噪声 / 正弦叠加造走势** —— 那是编造数据
  - 正确模型：基准价 3-8 天漂移一次 + 每天 N 轮 + 每轮按产量查阶梯
- **阶段 1b+ 才做**：后端采集上游轮次记录、入库聚合、价格预警订阅
- **不做**：预测下 24h 价格（不做金融预测）

### 8.21 通道费只在充值时展示 ✅（澄清 §2.13）
- **背景**：`decisions §2.13` 定了通道费 pass-through（waffo 5% · 我方不加不承担）· 但 UI 上一直在拉号/提取费用明细里显示"通道费 · 充值时收"
- **问题**：用户混淆 —— 以为拉号/提取时还要额外扣通道费。实际**充值积分时已经收过一次**，之后所有积分抵扣操作都不再涉及通道费
- **决策**：
  - **充值积分页 / 充值弹窗** · **显示**通道费（"号价 5% + waffo 通道费"）
  - **拉号 / 提取 / 拼车 / 补车** · **不显示**通道费 · 这些都是积分抵扣，跟通道费无关
- **数据不变**：底层计费公式（`00 §3` 加法顺序）不变 · 只调整 UI 展示时机
- **参考**：`web/src/components/PullExtractForm.tsx`（已删预估卡通道费行）

### 8.20 邀请码双层机制 · 替代地区议价 ✅（覆盖 §2.10 / §2.11 / §2.12）

**背景**：§2.10 地区议价（海外 +20%）因"无法可靠识别地区"⏸。本条用**邀请码**替代地区判定 —— 码是我方发的，**可校验、不可绕、无合规风险**。

#### 两种码 · 名字不同 · 作用不同（必须分清）

| 名称 | 输入时机 | 作用 | 持久性 |
|---|---|---|---|
| **邀请码** | **注册时**填 | ① 解锁 vendor 真名 ② 免加价 | 永久绑账号 |
| **优惠码** | **支付 / 提号确认窗**里填 | 只减免（**不解锁真名**） | 单次生效 |

**术语铁律**：注册那个叫「邀请码」· 支付和提号那个叫「优惠码」· **UI 上不许混用**。

**为什么解耦**：社群成员可以把优惠码发给朋友省钱，但**不会泄露我方 vendor 清单**（防散客绕过我方直连 vendor）。

#### 加价规则

- **无注册码 且 本次无消费码** → 加价（当前 **+20%**，后台可组合多个附加费）
- **有注册码** 或 **本次填了消费码** → 无加价
- **UI 绝不显示原价 / 加价幅度**（不暴露我方成本结构）· 只显示一个最终价

#### vendor 名字显示

| 身份 | 显示 |
|---|---|
| 有注册码 | 真名（Kiro Market / Kiro Drop / …） |
| 无注册码 | **AWS-Q Kiro Vendor 01 / 02 / …**（编号按 `CLAUDE.md §1.1` 六家顺序固定，同一用户每次看到的映射一致） |

#### 提取 key 页的默认项（auto）

**不再用**「让系统按有效成本比价」这种空文案。auto 项**必须展示系统推荐结果 + 价格**：
- 推荐到的 vendor（真名 or Vendor 0N）
- 库存 / 单价（最终价）/ 质保 / 历史成活率
- 预估费用（不能留"选具体 vendor 看预估费用"空占位 —— 散客本来就是 auto，必须能下单）

#### 提取确认窗（不直接拉）

点「提取」**不直接下单** → 弹确认窗：
- 复核提取信息（来源 / 区域 / 数量 / 单价 / 质保）
- **优惠码在这里填**（不放外层表单）· 应用后实时重算价格 · 原价划线显示
- 合计扣除 + 波动提示 → 「确认提取」才真拉

card 左下角常驻灰色小字：**「价格受市场波动影响，会有波动，提取前请仔细核对提取信息。」**

#### 覆盖关系

- **覆盖 §2.10 地区议价** —— 不再尝试识别地区，改用邀请码
- **覆盖 §2.11 双币种** —— 同上，不依赖支付通道分层
- **覆盖 §2.12 多信号识别** —— 彻底放弃地区判定
- **§2.8 指定 vendor 议价** 语义变更 —— 不再是单独收费点，变成**注册码持有者的权益**

#### 数据落地（阶段 1b）

- `passenger.invited`（bool）· `passenger.invite_code_used`（注册时用的邀请码）
- `invite_code` 表（注册用）：code / owner_id / used_count / max_uses / expires_at
- `coupon_code` 表（支付 / 提号用）：code / discount_rule / used_count / max_uses / expires_at
- `surcharge_rule` 表：后台可配多个附加费 —— 完整设计见 **`§8.30`**（多类合并成一张表）
  - 这条规则就叫 `region_markup`（**区域附加费**）· 有系统邀请码 → 免掉它（`§8.32`）
- 定价 API 返回**最终价**，不下发原价和加价明细

**参考**：`docs/14-extract-page-plan.md §4` · `web/src/components/UpstreamStatusPanel.tsx`

### 8.18 多人车 · 按成员百分比分摊扣款 ⏸（阶段 2a）
- **决定**：多人车里每个成员在建车时被分配一个 `member_share_pct`（百分比），加起来 = 100%
  - 车主 60% + 车友 A 30% + 车友 B 10%
  - 一次拉号总花费 100 积分 → 从车主钱包扣 60 · A 钱包扣 30 · B 钱包扣 10
- **谁能触发拉号**：**只有车主**（无论手动 / 自动补车触发）· member 视图 primary 按钮是"提醒车主拉号"（§8.17）
- **单次议价**：跟共享账户一样按 share_pct 分摊 · 不因为"只拉 1 个号"就归某人
- **余额预检**：拉号前**遍历所有成员钱包**
  - ~~任何一人不够即整轮拒绝~~ —— **§8.26 修正**：不够的人**本次跳过**（不扣钱 · 不给取这批号）· 一个人卡死全车不合理
  - **但拉号跟派号不一样**：派号是钱已经花完了（§8.23），拉号得**先收钱才能去 vendor 买**。少一个人的份额 → **收到多少钱买多少号**（缺口靠下一轮补）· 不让其他人垫、不整轮拒绝
  - UI 明确提示"@wei 余额不足 · 本次跳过"（不含糊）
  - 不做债务累积 / 押金冻结（阶段 2a 太重 · 未来讨论）
  - 连续跳过 3 次 → 挂起（§8.26）
- **百分比修改**：
  - 建车时车主拍
  - 运行中改需要**所有成员确认**（阶段 2a 走通知通道 · 走 8.17 的通用通知机制）
  - 不做"车主一人拍板"（避免车主拉黑压死车友的滥用）
- **数据落地**（阶段 2a 表字段）：
  - `bus_member (bus_id, member_id, share_pct)` — 成员 + 比例
  - `pull_round.member_shares JSON` — 每轮实际按什么比例扣 · 便于回溯
  - `wallet_ledger.reason_id` 关联到 pull_round · reason 里带 share_pct
- **拒绝**：
  - **单一车主付全款**（那就不叫拼车，叫"车主赠送 API"，跟散户切片重复 · §5.1 未来产品线）
  - **按用量后结算**（结算频率 / 边界模糊 · 阶段 2a 用不起）
  - **贝壳制**（成员先充值到共享钱包，从共享扣）· 隐私 & 归属不清晰 · 未来讨论
- **参考**：`docs/06-db-schema.md` 阶段 2a 表规划 · `03-modules.md wallet + bus 依赖` · §8.17 member 通知机制

### 8.17 多人车 member 视图 · 提醒车主拉号 + 走通用通知通道 ⏸（阶段 2a）
- **场景**：多人车里 `role === "member"`（车友，非发起人）打开车详情 / focal 卡时，看不到"给这辆车拉号"按钮

- ⏸ **vendor 加了 fleet 端点通知机制**：给 vendor 加 webhook `fleet.dispatched` 事件 · 从 push 拿数据不再靠 poll · 需要六家都实现 · 阶段 3+
- ⏸ **crowd-sourced dispatch**：让登录乘客的 my/order 数据聚合成 fleet 视图 · 数据敏感 · 需要合规评估 · 大概率不做

### 11.8 vendor 质量标签（Score 内部 + Tags 对外）✅

**背景**：Status 卡片要让乘客"一眼看出高质量家" · 但直接暴露 A/B/C 或分数会让乘客困惑（`§0.1` 内部量化不出前端）。

**决策**：**多维标签制**（`internal/vendorview/quality.go`）。

- **Score 只做内部排序**（0-100 · 加权：Uptime 30% + Volume 35% + Freshness 20% + Stock 15%）· `json:"-"` 不出接口
- **Tags 对外显示**（前端 `web/src/components/VendorQualityTags.tsx`）·
  - `stable` · 24h uptime ≥ 95%（绿）
  - `high-volume` · 窗口内批次 ≥ 20（紫）
  - `active` · 最新一次 ≤ 24h（灰蓝）
  - `in-stock` · 当下 stock=many（绿）
  - `warranty` · has_warranty=true（紫）
  - `watching` · 数据不足 / uptime<50%（黄）
- **数据不足**（uptime 无样本 且 dispatchBatches=0）→ 只挂 watching · Score=0 排最后

**为什么不 A/B/C**：单字母吞掉多维信号（一家可能"高产但不稳"·A/B/C 表达不出来）· 标签叠加更直观。

### 11.9 stock-delta 推算 restock 事件流 ✅

**背景**：探针每 60s 打 `vendor.Stock` 拿快照 · 但号上架几分钟就被抢空 · 探针只看到"stock=0"· `vendor_dispatch` 表拿不到批次 · Status 图 4 家全空。同类聚合站（xi8.cc）30s 轮 + prev_stock delta 推算 · 数据完整。

**决策**：**Prober 落库前跟上一轮 stock 对比 · 正 delta 落 `vendor_dispatch`**（`internal/vendorview/prober.go:deriveStockDelta`）。

- source=`vendor_self` · dispatch_key=`delta-{region}-{ts}`
- **零额外 API 调用** · 完全复用现有 Stock 端点响应
- 时间窗保护：相邻两轮 > 2×interval 视作重启 · 不算 delta
- alive 保护：上一轮挂了不算（避免从挂到活首次读数误当 restock）
- fleet 端点有的 vendor · fleet 为主 · delta 只补漏

**已知局限**（跟 xi8 同类）：vendor 侧发号 → 抢空 < 2×interval 的短命批漏 · prev=0, cur=0 但期间有一波来又走漏（探针间隙盲区 · 只有事件源能救 · §11.7）。

**跟提频挂钩**：探针间隔从 60s 缩到 30s 后 · 漏批率减半 · 但成本翻倍。**自适应频次**（`§11.11`）解决这个 tradeoff。

### 11.10 时区 bug fix + 数据洗（2026-08-11）✅

**根因**：本 vendor 群里有两家返 `"2026-08-12 10:25:00"` 这种**北京墙钟无 tz** 字符串 · `time.Parse` 把它当 UTC 处理 · `.UTC()` 只改标签不移时钟 · 存进 db 的 `dispatched_at` 超前真时刻 8 小时。

**实证**：xi8 restock-log 记同一批次的时间戳跟我方 db 对比 · 差 8 小时。库里最新 dispatched_at > `datetime('now')` 的行全部集中在这两家。

**修法**（`internal/providers/kiro/vendors/{kirooo,kiroceo}/history.go`）：
- 从 `time.Parse(layout, s)` 换成 `time.ParseInLocation(layout, s, chinaTZ)` · chinaTZ = `time.FixedZone("CST", 8*3600)`
- 出向 `.UTC()` 才真的移 8 小时
- kirooo 的 `public_status.go` `ps_started_at` 字段同源问题·一并修
- 其他 4 家不动（实证格式正确 · kiro91 是真 UTC · kiroappio/kiroappcc/kirodrop 用 RFC3339 带 tz）

**数据洗**：一次性 SQL 只针对这两家 · `UPDATE ... SET dispatched_at = datetime(dispatched_at, '-8 hours')` · 共洗 129 条 vendor_dispatch + 1148 条 vendor_probe.ps_started_at。备份 `data/dev.db.bak.<ts>`。

**教训**：Go `time.Parse` 无 tz 字符串**默认 UTC** · 用 `ParseInLocation` 显式绑 tz 才对。写 vendor adapter 时**必须先实证 vendor 返的是墙钟还是 UTC** · 别信文档。

### 11.15 抢号链 · 运营态自动切 + 人工强制 + 急停（`internal/stockwatch/`）✅ 部分落码

**问题**：市场号短命（几分钟抢空）· 拉号时 vendor 缺货直接失败退款 · 用户体验差 · 也没利用后续 restock 事件。且"该不该抢"是**动态判断** —— 车多 key 少要抢 · 库存充足没排队白抢浪费 API。

**决策 · 三层优先级**：

```
① 急停（KILL_PULLS 文件哨兵）  → 一切 Purchase 停 · 最高优先
② turbo（TURBO_ON 文件哨兵）   → 人工强制 · 无视 mode 自动判断 · 一律抢
③ ModeMgr 自动                 → 平时自动切 tight / balance / cool
```

**运营态自动判**（每 30s 采样 · `ModeMgr.sample`）：

```
demand = pending + in_flight 的 pull_intent 总数
supply = 6 家 vendor 过去 5min stock 均值累加
ratio  = demand / max(1, supply)

ratio > 2       → tight   紧张 · 探针 + webhook 都 fire
0.3 < ratio ≤ 2 → balance 均衡 · 只 webhook fire · 探针只观测
ratio ≤ 0.3     → cool    冷 · 都不 fire · 用户来了现打 vendor
```

**source × mode 决策表**（`Watcher.sourceShouldFire`）：

| source | tight | balance | cool | turbo 开 |
|---|---|---|---|---|
| `webhook`（vendor push · 最快 200ms-2s） | ✅ | ✅ | ❌ | ✅ |
| `xi8_signal`（xi8 转推 · 3s） | ✅ | ✅ | ❌ | ✅ |
| `stock_delta`（探针推算 · 60s） | ✅ | ❌ | ❌ | ✅ |
| `manual`（CLI 手工） | ✅ | ✅ | ✅ | ✅ |

**为什么 turbo 是文件哨兵不是 env**：env 改了要重启 · 人工干预要**即时生效**。

```bash
ssh vps22 'touch /opt/bus-pooling/data/TURBO_ON'   # 5 秒内生效 · 强制抢
ssh vps22 'rm    /opt/bus-pooling/data/TURBO_ON'   # 关
ssh vps22 'touch /opt/bus-pooling/data/KILL_PULLS' # 急停
```

开销：每 5s 两次 `os.Stat` · 读走 `atomic.Load`（5ns）· 相对 vendor HTTP 200ms 可忽略。

**turbo 的必要性**（运营者实际场景）：上游连续几天缺货 · 自动判断可能算成 cool（supply 长期 0 · demand 也不高 · ratio 落 cool 区）· 但运营者知道"还要用 · 有货就抢" · 手工按住不放。

**幂等 · 一号一抢**：多信号源同时到 · `stock_watcher.status` 走 conditional UPDATE（`WHERE status='watching'`）· 只有一个抢到 `fired` · 其他 skip。抢到的调 `decider.Purchase` 用 `pull_intent.client_order_id` · vendor 侧同 order_id 重放不重复扣（`09-transactions §2`）。

**表**：`stock_watcher`（migration 027）· 主键 `intent_id` 一对一 · `fire_count` 计数防 spam retry。

**加速预存池**（Q2=C 定稿 · **还没落码** · 下一轮）：
- 抢到的号 **必须落 housepool**（kiro.rs group `prebuy-pool`）· 不做纯内存中间池
- `credential_ledger` owner 都 NULL · `current_group='prebuy-pool'`
- 有 pull_intent 排队 → 从 `prebuy-pool` 移到 `bus-<id>` · 台账 owner 改 bus
- **5min TTL** · janitor 扫过期 → 走 warranty 退 vendor + 删 kiro.rs 里的号
- **跟 §2.3 长效号预留池的区别**：§2.3 是"预付 + 议价"商业模型（号老 · 已否决）· 这个是"看到就抢的短时缓冲"（号新 · 5min TTL · 纯抢号动作）· CLAUDE.md §5 已加提示行防未来 AI 混淆

**当前进度**：
- ✅ migration 027 `stock_watcher` 表（**自包含** · 见下方修正）
- ✅ `stockwatch` 包 · Enqueue / Notify / Sweep / ModeMgr / FileFlag / StartSweeper

**落码时修正的两个设计错**（初稿踩的坑 · 记下来防重犯）：

**① `stock_watcher` 不能引 `pull_intent`** —— 初稿把 `intent_id` 设成主键 + 外键指
`pull_intent(id)`。但**生产代码从没写过 `pull_intent`**：实际拉号走 `pending_purchase`
状态机（`decider/state.go`）· `pull_intent` 是 001 建表时的规划 · coalescer 的
Anon/Team 至今是 stub。连带 `ModeMgr.sample` 查 `pull_intent` 算 demand → **恒得 0**
→ mode 永远锁 `cool` → 抢号链一次都不会 fire（装配看着好 · 功能全死）。

修法：`stock_watcher` 改成**自包含** —— 自己的 `id`（uuid v7）+ 重建拉号所需全部上下文
（`passenger_id` / `bus_id` / `target_group` / `vendor_id` / `client_order_id` / `count` /
`max_unit_price`）· fire 时不回查任何前置行。`ModeMgr` 改查 `pending_purchase` 活跃状态
+ `stock_watcher` 里 `watching` 的条数。加回归哨兵测试
`TestModeMgr_Sample_ReadsPendingPurchase` 锁死这件事。

**② TTL sweeper 不是"清垃圾"· 是 mode 正确性的一部分** —— `watching` 计入 demand ·
过期挂单不扫会让 demand 虚高 → mode 永远 tight → 探针一直 fire 白打上游 API。
`StartSweeper` 60s 一轮 · 哨兵测试 `TestModeMgr_Sample_ExpiredNotCountedAsDemand`。

**幂等的三层保障**（落码后确认）：
1. `stock_watcher.status` conditional UPDATE（`WHERE status='watching'`）· 三源竞争只一个中
2. `client_order_id` 挂单时定 · fire 时**复用**（`PullInput.ClientOrderID` 覆盖内部生成）
   —— 防"上次 fire 其实买到了但返超时 · 回退 watching 后再 fire"在 vendor 侧变两单
3. `pending_purchase UNIQUE(vendor_id, client_order_id)` · DB 层兜底

**死循环哨兵**：`maybeEnqueueOnNoStock` 第三道门是 `in.ClientOrderID == ""` ——
fire 触发的那轮缺货**不能再挂单**（否则刚 fire 的挂单被复位成 watching · 下次事件
又 fire · 无限循环）。测试 `TestMaybeEnqueue_FromFire_NoReEnqueue`。

**不预冻结**（落码时的取舍）：挂单时不冻钱 · fire 时走完整 Pull 现冻现扣。理由：缺货时
拿不到真单价（stock=0 的 zone 没 unit_price）· 冻多少无依据；且冻 10min 可能白占款。
代价：fire 时余额可能已被花掉 → 那轮标 expired · 用户重挂。`reserved_amount` 列和
`ListExpiredNeedingRelease` / `MarkReleased` 已就位 · 当前恒 0 · 未来若改成预冻结直接用。

### 11.12 探针自适应频次（hot / baseline 两档）✅

**背景**：60s 探针 · 短命批（几分钟被抢空）漏 50%。提到 30s 漏批减半但 API 成本翻倍 · vendor 侧可能触发 rate limit / 反爬。要"稳态省钱 · 热点期快"。

**决策**（`internal/vendorview/prober.go`）：

- **baseline 60s** · 常态省 API
- **hot 10s** · 6min 内 stock-delta 推算发现 restock → 拉进 hot 状态
- **6min 无事件** → 退回 baseline
- 每 vendor 独立热度（`sync.Map` vendor_id → hotUntil）· 一家开号不影响其他家
- **触发条件**：目前只有 stock-delta 检测到 delta > 0 · 未来加 pending_on_stock 意向也 bump

**估算 API 打上游成本**（6 家 vendor）：
- 稳态：60s 一轮 · 6 家/min = **360/hour**
- vendor 开号 6min 窗内：10s 一轮 · 6 家 · 6min = 216 次 vs baseline 36 次 · **多 180 次**
- 假设一天每家开 3 次号 · 一天多 3×6×18 = **324 次** · 微不足道

**已知局限**：
- vendor 每次开号后 6min 内没再补货 · 那 6min 白多打 API（但换来"下一批立即抓到"的能力）
- 冷启动第一批必漏（没历史数据触发不了 hot）· 只有事件源（vendor webhook）能救 · §11.7 长期方向
