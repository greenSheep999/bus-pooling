## 三种状态

| 标记 | 含义 | 未来 |

| **❌ 永久否决** | 方向错，永远不做 | **不再讨论** |
| **⏸ 当前不做，未来迭代** | 想法有价值，等阶段 / 数据 / 能力就位 | **可以再谈**，但要先看这里的条件是否已满足 |

## 1. 架构分层

### 1.1 内嵌 kiro.rs 到 bus-pooling 单进程 ❌
- **提议**：把 kiro.rs 号池能力做进 bus-pooling 自己的进程里
- **否决**：kiro.rs 已经作为独立服务运维（`kiro.aibbq.xyz`），是**外部依赖**；本项目只做它的 client
- **替代**：`internal/housepool/kirors/` 客户端调 kiro.rs admin API

### 1.2 用数据库替代 housepool ❌
- **提议**："housepool 的价值就是数据回流，用数据库也能做"
- **否决**：数据库只能记账（"这号归谁"），但**运行时**能力（校验凭证、存活探测、用量追踪、分组、并发监控 5 项）**必须号池实现才有**
- **参考**：`01-architecture.md §2 Layer 4`

### 1.3 拉号记录 = 独立数据库表（不进 housepool）❌
- **提议**：单独拉号的号先在数据库里躺着，用户派去向后再进 housepool
- **否决**：**要监控就必须进 housepool**（否则 5 项能力全废）。这些号也需要平均寿命统计
- **替代**：拉号记录 = **housepool 里的 `record-<pid>` group + `disabled=true`**（号已进池、已监控、不发下游）

### 1.4 号推给 passengerpool = 号离开系统 ❌
- **提议**：号一推到乘客的 kiro.rs 就完成交付，我方不再跟踪
- **否决**：**要监控存活就得留副本**。推给 passengerpool 是**双写** —— housepool 保留副本（我方监控），passengerpool 是复制品（乘客用）
- **例外**：只有**去向 ③ handoff（拿走）**才是真正离开系统，我方 `DELETE /credentials/{id}` 后不再跟踪

### 1.5 fire-and-forget 一律不管 ❌
- **提议**："发出去就不管了"
- **否决**：只有 handoff（拿走号数据）才 fire-and-forget。**推 passengerpool 是双写还监控**、进 bus 也监控
- **参考**：`00 §5 用户路径` 3 种去向表

### 1.6 provider 抽象层可以省 ❌
- **提议**：只有一个 provider（kiro），直接把 6 家 vendor 平铺在 `internal/vendors/`
- **否决**：未来加 `cursor` 等 provider 时会撞车
- **替代**：`internal/providers/kiro/vendors/*`；加新 provider 只加 `providers/<name>/`

### 1.7 kiroclient 命名放顶层 ❌
- **提议**：`internal/kiroclient/` 顶层
- **否决**：号池承载**当前**是 kiro.rs，未来可能换其他实现；按"层职责"命名而非"具体实现"命名
- **替代**：`internal/housepool/kirors/`

### 1.8 混淆"我方号池"和"乘客号池"❌
- **提议**：两个 kiro.rs 都叫"号池"或"pool"
- **否决**：**两个不同实体**：
  - 我方 = `housepool`（Layer 4，我方基础设施）
  - 乘客 = `passengerpool`（Layer 5 交付目标，外部系统）

## 2. 收费 / 商业模式

### 2.1 卖号（加价 pass-through 差价）⏸
- **提议**：我方在 vendor 号价上加价卖
- **当前不做**：号价永远 pass-through，我方只赚服务费（`00 §1 是什么/不是什么`）
- **未来可能做**：**利用 vendor 的开号能力**（乘客上传 AWS → 我方转发 vendor 开号，见 §5.1 阶段 3b/3c）→ 号进**公开池 / 市场**（阶段 3d）→ 卖给其他乘客 → **这条路径有利润空间**
- **关键区分**：**"我们不做开号"**（不复刻 vendor 的开号系统） ≠ **"我们不做号买卖"**（未来通过市场可以做）

### 2.2 会员制 / 订阅制 ⏸
- **提议**：月付订阅费享受服务费打折 / 优先撮合 / 优先补车 / 数据看板
- **当前不做**：阶段 1/2 先跑"每次固定服务费"的按需模型
- **未来可能做**：跟拼车主线不冲突，等有稳定用户量再评估

### 2.3 长效号预留池 ⏸
- **提议**：从平均寿命高的 vendor 定期拉号、储备一个小池，预付进入"长效池会员"
- **当前不做**：还没有"长效号"这种类型（vendor 未提供），也无平均寿命历史数据
- **未来是议价空间**：等阶段 1d 采集足够寿命数据后可以评估。**"长效号"是我方少数能提供的稀缺资源**，值得少量储备 → 议价空间
- **参考**：`00 §9 未来增值方向 · 长期稳定号源`

### 2.4 数据看板"作为收益点"（订阅 / API 收费）❌
- **区分两件事**：
  - **数据看板功能** —— 阶段 3a 要做（`00 §7 · 阶段 3a`），乘客和管理端都能看到平均寿命 / 价格趋势 / 缺货率等
  - **数据看板作为收益点**（订阅制收费卖数据 / API 卖看板数据）—— **不做**
- **否决理由**：跟"公益工具"人设不匹配。数据看板是**产品能力**，不是**收费点**
- **不影响**：阶段 3a 的数据图表功能照常做

### 2.5 API 售卖（"我们推自己的池 API 卖"）✅
- **提议**：我方直接用 API 卖自己 kiro.rs 号池给乘客
- **接受，且不需要任何新功能**：**把我方运营账号当作一个普通乘客**，用已有的乘客侧 API（`05-api-contract.md` §5 单独拉号 + `06-scenarios.md` B4 handoff / B3 推 passengerpool）即可完成"卖 API"的全部动作
- **明确不做的形态**：**API 拼车**（把 API 调用本身做成拼车）—— 太复杂，用户明确不搞
- **未来加值**：接入合作下游产品直接消费我方 API（`00 §9 · 合作下游消耗`）

### 2.6 & 2.7 · 稳定优先附加能力（排噪邻 + 优先撮合，打包）⏸
- **提议**：拼车时排除高流量成员 + 撮合优先级更高，打包 +20%
- **当前不做**：先不设限制，阶段 2c 压车治理数据成熟后作为附加能力候选实施
- **完整描述已在**：
  - `00 §9 未决 · 附加能力插槽候选清单 · 稳定优先`（含触发规则：手动勾 or 策略参数含 RPM/TPM 要求）
  - `00 §3 计费模型`（附加能力插槽定义 + 加法顺序）
- **本条只做交叉引用**，不重复叙述

### 2.8 指定 vendor 议价 ⏸
- **提议**：用户指定 X 家 vendor → 加价（限制我方选择）
- **当前不做**：跟"公益"人设不匹配；用户可以指定 vendor 但不加价，属于普通拉号
- **未来可能**：若有场景表明"指定 vendor"确实消耗我方资源，可作为附加能力候选

### 2.9 寿命 SLA 议价 ⏸
- **提议**：用户要求"平均寿命 ≥ X 小时" → 加价
- **当前不做**：**没有历史数据可用**（阶段 1 才开始采集平均寿命）
- **未来可能**：阶段 1d 后有数据再评估。可能与 2.3（长效号预留池）合并考虑

### 2.10 地区议价（海外 +20% / 国内 0）⏸
- **提议**：海外用户加 20%
- **当前不做**：**无法可靠识别**海外/国内：
  - 注册选地区 —— 无法校验
  - IP 定位 —— VPN 可绕
  - 支付通道 —— waffo 单通道不支持币种区分
- **未来可能**：等阶段 2+ 接入多通道（微信/支付宝/信用卡），按通道自然分层（"通道即价目"）；阶段 1 **统一定价**

### 2.11 CNY/USD 双币种价目表 ⏸
- **提议**：用户充值币种自选，CNY 走国内价、USD 走海外价
- **当前不做**：waffo 不收 RMB，单一币种，无法区分
- **未来可能**：同 2.10，等多通道再启用

### 2.12 IP + 手机号 + 时区多信号识别 ❌
- **提议**：多信号打分判定海外/国内
- **否决**：合规风险（跨境用户地区判定敏感）+ 用户可绕，误伤高
- **替代**：同 2.10 走通道自然分层

### 2.13 通道费我方承担 / 我方加收 5% ❌
- **提议**：(b) 我方承担 waffo 5% 通道费 / (c) 我方在通道费上再加收 5% 作为额外收入
- **否决**：违背 pass-through 人设
- **保留**：(a) 通道费 pass-through 给乘客，waffo 收，不进我方账

### 2.14 议价加在总价上 ❌
- **提议**：`总价 × (1 + 议价率)`
- **否决**：用户明确"附加费加在号价上，不加在总价"
- **保留**：`(号价 + 议价) + 服务费` → `× (1 + 通道费)`

### 2.15 一轮 = 一个号 ❌
- **提议**：拉 10 个号 = 10 轮，服务费 × 10
- **否决**：用户原话"每人每轮 1 元，18 轮就是 18 元"—— 一轮 = **一次拉号动作**
- **保留**：**1 轮 = 1 次拉号动作**（不管这次拉几个号）
- **推论**：批量天然便宜（拉 10 个号 1 元服务费 vs 分 10 次拉 10 元服务费），符合"鼓励批量"

### 2.16 退款支持现金 / 退到 payment-gateway ❌
- **提议**：号死了退现金给乘客
- **否决**：我方**只退积分，不退款 / 不退现金**
- **保留**：`wallet` 加积分 + ledger 落 `warranty_refund`；服务费 / 通道费 / 过窗口的号 **不退**
- **参考**：`00 §3 退款原则` + `§7.5 规则 B`

### 2.17 独立质保（超出上游窗口） ❌
- **提议**：我方对乘客做独立质保（例：号死 60 分钟内退款）
- **否决**：质保**完全跟随上游 vendor**，上游过窗口不退我方也不退
- **参考**：`00 §7.5 规则 B`

## 3. bus / 号 / 上车

### 3.1 solo bus / pooled bus 概念 ❌
- **提议**：区分 solo bus（独享）和 pooled bus（拼车）为两种类型
- **否决**：造成命名混乱。**1 人 bus 也是 bus**，多人 bus 也是 bus，都在 `bus-<id>` group
- **保留**：`bus.kind` 字段可以是 `single` / `anon` / `team`，但**都叫 bus**

### 3.2 mode: carpool / solo 二选一 ❌
- **提议**：策略参数带 `mode: carpool | solo`，二选一决定去向
- **否决**：号的去向由分配决定，不是 mode 二选一
- **参考**：拉号 ≠ 上车（`00 §5`）

### 3.3 混合上车（一次拉号分头上多 bus）❌
- **提议**：一次拉 10 个号，5 上 bus X + 5 上 solo bus + `allocation_plan`
- **否决**：**用户否决**（"什么混合上车是什么鬼"）
- **保留**：单独拉号后号进 `record-<pid>` group，用户再对每号选去向

### 3.4 allocation 组件 ❌
- **提议**：单独设 `internal/allocation/` 分配器
- **否决**：跟 3.3 一起否决
- **替代**：`internal/pullrecord/` 承担"派去向"职责

### 3.5 用 `personal-<pid>` group 表示乘客个人号池 ❌
- **提议**：housepool 里有 `personal-<pid>` 这种 group 表示乘客的号
- **否决**：**号池 = 乘客的 passengerpool（外部）**，我方 housepool 里的 group 不叫"号池"
- **替代**：叫 `record-<pid>`（拉号记录 group），只是号"归属"，不叫"号池"

### 3.6 拉号记录 = 数据库表（不进 housepool）❌
- 见 1.3

### 3.7 号归属 = Bus（不是乘客）✅
- **提议**：号在 credential_ledger 有唯一 owner
- **决策**：**号归属 Bus（`owner_bus_id`）**，成员通过 `bus_member` 表拿访问权
- **理由**：拼车语义 = "大家一起养的号"；owner 归 Bus 后：
  - 退出 Bus 不影响号（号仍在 bus group）
  - 解散 Bus 才需要决定号归谁（阶段 1a 简化：解散时号 handoff 给创建人 or 死号扫掉）
  - 拼车分摊 / 补车 / 退款 都以 Bus 为主体
- **单独拉号进 record group** 的号：`owner_bus_id = NULL, owner_record_passenger_id = <pid>`
- **参考**：`06-db-schema.md § 11 credential_ledger`（CHECK 约束保证 XOR）· `09-transactions.md`

## 4. 概念 / 术语作废

### 4.1 用 `carpool / car / carpool_room / carpool_id` ❌
- **提议**：英文命名用 car / carpool
- **否决**：用户明确"没有 car 这个概念"
- **保留**：**统一用 `bus`**（`bus_id`、`bus-<id>` group）

### 4.2 "方式 A / 方式 B" ❌
- **提议**：交付分方式 A（推 passengerpool）和方式 B（乘客调 API 拿）
- **否决**：把**入口**和**去向**糊在一起了
- **替代**：**3 种去向**（进车 / 推 passengerpool / handoff）+ **2 种入口**（UI / API）正交

### 4.3 "上车 = 独享/多人拼车" ❌
- **提议**："上车"泛指号分配到任何 group
- **否决**：号只有一个物理位置（housepool），"上车"这种动作性词汇没实质
- **保留**：只用**去向**表达

### 4.4 P0 / P1 / P4a / P∞ 等 P 标签 ❌
- **提议**：延续旧项目的 P0-P∞ 阶段命名
- **否决**：粒度过细
- **替代**：**3 大阶段 + 内部 milestone**（1a / 1b / 1c / 1d / 1e / 2a / 2b / 2c / 3a / 3b / 3c / 3d）

## 5. 未来产品线

### 1.9 用 SuperTokens 做登录方案 ⏸
- **提议**：用 SuperTokens 或 Casdoor / Ory Kratos 等外接身份管理服务
- **当前不做**：项目是公益工具（`README.md`），阶段 1 只需要"登录 / 登出 / API key"三件事，**Go 自建约 200 行代码**就够（Argon2id + session cookie）
- **未来可能做**：如果需要邮箱验证 / 忘记密码 / 社交登录（Google / GitHub）→ 阶段 3+ 用户量稳定后可评估接入 SuperTokens 或 Ory
- **参考**：`03-modules.md · authpassenger`；密码哈希算法用 Argon2id（跟登录方案是两回事，见对话记录）

### 5.1 散户切片（一把 key 切多份卖给小散户）⏸
- **提议**：用 kiro.rs `CreateClientKey(usage_limit)` 把一把号的额度切成多份卖
- **当前不做**：不是拼车主线，避免混乱；kiro.rs 天然支持但先聚焦拼车
- **未来可能做**：作为**独立产品线**（不并入拼车），阶段 3 之后再评估

### 5.2 数据图表作为收益点 ❌
- 见 2.4（数据看板功能仍做，只是不作为收益点）

### 5.3 拉号记录 N 天过期策略 ❌
- **提议**：拉号记录里号 N 天未处理 → 自动搬迁 / 提醒
- **否决**：**"过期"= 号本身死了**（vendor 判死），不是按 N 天计时
- **保留**：号还活但用户 N 天没处理 → 只**提醒**，不自动搬迁（尊重用户选择权）

## 7. 议价 / 计费历史（速查）

用户拍板的当前收费点（`00 §3` 权威）：

| 项 | 归属 | 说明 |
|---|---|---|
| 号价 | vendor（pass-through） | 拼车按 N 摊 |
| 单次议价 | 我方 | `count==1` 时号价 × 20% |
| 附加能力费 | 我方 | 插槽，可累加多项；阶段 1 无实例 |
| 服务费 | 我方 | 每人每次拉号动作固定 1 元 / 1 USDT |
| 通道费 | waffo（pass-through） | 5% × 小计，充值时扣 |

**议价加在号价上**，通道费加在（号价+议价+服务费）小计之上。

## 8. 前端 UX / 首页结构（阶段 1a mockup 定型）

### 8.1 全局搜索 / ⌘K 命令面板 ⏸
- **提议**：顶栏加全局搜索或 Cmd-K 命令面板（Linear / Superhuman / Arc 风格）
- **否决当前阶段**：阶段 1 数据量小（一个用户几辆车、几十号、几十条记录），翻页 + 筛选够用；用户是消费端普通乘客，不是效率工具用户；Apple Pay / Cash App 也没有全局搜索
- **重启条件**：车 / 号 / 记录列表大到用户找不到时，考虑**局部筛选**（车列表页顶部一个筛选框）—— 但**不做 ⌘K 全局命令面板**
- **参考**：`design/design-brief.md`（顶栏元素）

### 8.2 顶栏结构 · 左对齐 5 tab + 头像 dropdown ✅
- **决定**：顶栏 = K logo · 左对齐 5 tab（概览 / 拼车 / 提取 key / 我的发车 / 对接文档）· 右侧 3 元素（余额 chip / 通知 / 头像）
- **头像 dropdown 内容**：我的（用户名）· API key · **机器人通知** · 设置（含"我的号池"passengerpool 对接）· 语言 · 主题 · 登出
- **左侧栏推翻**：早期设计契约禁止 sidebar，但主菜单挤成一横排后可读性差；改为**顶栏左对齐**（Vercel / GitHub 风格）而非 sidebar

### 8.7 UI 单位一律是"积分"不是货币 ✅
- **决定**：前端所有余额 / 消费 / 花费 / 到账数字，单位都是**积分**（如 `1,245 积分` · `-25 积分` · `+50 积分`）
- **1 积分 = 1 元人民币（1 CNY）** —— 平等价值，简单
- **`¥` 和 `USDT` 只在充值页 + 兑换页出现**：
  - 充 100 元 → waffo 扣 5% 通道费 5 元 → 我方到账 95 元 → **积分 +95**
  - 兑换码到账走口径同 100 → 显示 +100 积分
- **正负数**：消耗前置 `-`（`-25 积分`）· 到账前置 `+`（`+50 积分`）· 0 不显示正负
- **精度**：DB 底层用 microunit（`06-db-schema.md §通用约定`：1 元 = 1_000_000），UI 层展示时**整数积分**（微积分四舍五入至整数积分 · 只对号价单价可能出现小数 · 显示保留 2 位）
- **理由**：`00 §3` 用户在我方充值 → 消耗积分，不感知底层币种；简单等值人民币，避免用户困惑
- **参考**：`design/mockups/05-home.pen` · `05-api-contract.md` 需要保证 API 返回也用积分字段

### 8.20 邀请码双层机制 · 替代地区议价 ✅（覆盖 §2.10 / §2.11 / §2.12）

**背景**：§2.10 地区议价（海外 +20%）因"无法可靠识别地区"⏸。本条用**邀请码**替代地区判定 —— 码是我方发的，**可校验、不可绕、无合规风险**。

#### 两种码 · 名字不同 · 作用不同（必须分清）

| 名称 | 输入时机 | 作用 | 持久性 |
|---|---|---|---|
| **邀请码** | **注册时**填 | ① 解锁 vendor 真名 ② 免加价 | 永久绑账号 |
| **优惠码** | **支付 / 提号确认窗**里填 | 只减免（**不解锁真名**） | 单次生效 |

**术语铁律**：注册那个叫「邀请码」· 支付和提号那个叫「优惠码」· **UI 上不许混用**。

**为什么解耦**：社群成员可以把优惠码发给朋友省钱，但**不会泄露我方 vendor 清单**（防散客绕过我方直连 vendor）。

#### 加价规则

- **无注册码 且 本次无消费码** → 加价（当前 **+20%**，后台可组合多个附加费）
- **有注册码** 或 **本次填了消费码** → 无加价
- **UI 绝不显示原价 / 加价幅度**（不暴露我方成本结构）· 只显示一个最终价

#### vendor 名字显示

| 身份 | 显示 |
|---|---|
| 有注册码 | 真名（Kiro Market / Kiro Drop / …） |
| 无注册码 | **AWS-Q Kiro Vendor 01 / 02 / …**（编号按 `CLAUDE.md §1.1` 六家顺序固定，同一用户每次看到的映射一致） |

#### 提取 key 页的默认项（auto）

**不再用**「让系统按有效成本比价」这种空文案。auto 项**必须展示系统推荐结果 + 价格**：
- 推荐到的 vendor（真名 or Vendor 0N）
- 库存 / 单价（最终价）/ 质保 / 历史成活率
- 预估费用（不能留"选具体 vendor 看预估费用"空占位 —— 散客本来就是 auto，必须能下单）

#### 提取确认窗（不直接拉）

点「提取」**不直接下单** → 弹确认窗：
- 复核提取信息（来源 / 区域 / 数量 / 单价 / 质保）
- **优惠码在这里填**（不放外层表单）· 应用后实时重算价格 · 原价划线显示
- 合计扣除 + 波动提示 → 「确认提取」才真拉

card 左下角常驻灰色小字：**「价格受市场波动影响，会有波动，提取前请仔细核对提取信息。」**

#### 覆盖关系

- **覆盖 §2.10 地区议价** —— 不再尝试识别地区，改用邀请码
- **覆盖 §2.11 双币种** —— 同上，不依赖支付通道分层
- **覆盖 §2.12 多信号识别** —— 彻底放弃地区判定
- **§2.8 指定 vendor 议价** 语义变更 —— 不再是单独收费点，变成**注册码持有者的权益**

#### 数据落地（阶段 1b）

- `passenger.invited`（bool）· `passenger.invite_code_used`（注册时用的邀请码）
- `invite_code` 表（注册用）：code / owner_id / used_count / max_uses / expires_at
- `coupon_code` 表（支付 / 提号用）：code / discount_rule / used_count / max_uses / expires_at
- `surcharge_rule` 表：后台可配多个附加费（当前只有一条 region_markup 20%）
- 定价 API 返回**最终价**，不下发原价和加价明细

**参考**：`docs/14-extract-page-plan.md §4` · `web/src/components/UpstreamStatusPanel.tsx`

### 8.18 多人车 · 按成员百分比分摊扣款 ⏸（阶段 2a）
- **决定**：多人车里每个成员在建车时被分配一个 `member_share_pct`（百分比），加起来 = 100%
  - 车主 60% + 车友 A 30% + 车友 B 10%
  - 一次拉号总花费 100 积分 → 从车主钱包扣 60 · A 钱包扣 30 · B 钱包扣 10
- **谁能触发拉号**：**只有车主**（无论手动 / 自动补车触发）· member 视图 primary 按钮是"提醒车主拉号"（§8.17）
- **单次议价**：跟共享账户一样按 share_pct 分摊 · 不因为"只拉 1 个号"就归某人
- **余额预检**：拉号前**遍历所有成员钱包**，任何一人不够即**整轮拒绝**
  - UI 明确提示"@wei 余额不足 · 差 12 积分"（不含糊）
  - 不做部分扣款 / 债务累积 / 押金冻结（阶段 2a 太重 · 未来讨论）
- **百分比修改**：
  - 建车时车主拍
  - 运行中改需要**所有成员确认**（阶段 2a 走通知通道 · 走 8.17 的通用通知机制）
  - 不做"车主一人拍板"（避免车主拉黑压死车友的滥用）
- **数据落地**（阶段 2a 表字段）：
  - `bus_member (bus_id, member_id, share_pct)` — 成员 + 比例
  - `pull_round.member_shares JSON` — 每轮实际按什么比例扣 · 便于回溯

### 8.14 号用量进度条 · 参照 10k 积分寿命阈值 ✅
- **决定**：号"用量"字段在 UI 上是**进度条 + 文字标签**（`N.Nk / 10k 积分`），参照 = **该号累计消耗积分 / 10000 积分**
- **10k 积分 = 号大概率寿终阈值**（vendor 侧观察值，非硬阈值，可后续按数据回流调整）
- **视觉**：紫色 track（brand-strong）+ 灰色底色（hairline）· 100px 宽 · 4px 高 · 下方 11px 文字
- **失败行 / 无用量数据**：不显示进度条，显示"—"
- **未来**：如 vendor 差异大，可按 vendor 分别设 10k 阈值（如某 vendor 号 15k、另一 vendor 6k）
- **参考**：`design/mockups/05-home.pen` OLSh3 · row usage bar

### 8.6 补车策略跟 bus 绑（非全局设置）✅
- **决定**：`auto_enabled` / `per_round_count` / `max_unit_price` / `daily_spend_limit` 等**每车一策略**，配置面板在**车详情页**内，不放全局"设置"
- **理由**：不同车（1 人 / 多人 / 短期 / 长期）策略需求差异大；跟 bus 绑更符合"一辆车一策略"直觉
- **推翻**：早期设计的独立"策略页"作废
- **参考**：`docs/sprint-1a-frontend.md` #F10 需要更新
