# bus-pooling · 三大价值 & 分层与阶段

> 前置阅读：[`docs/vendors/`](./vendors/) 里六份 vendor 官方 API 档案。
> 本文只写共识（"我们是什么/不是什么"、三大价值、阶段），不预先设计尚未对齐的细节。

## 1. bus-pooling 是什么 / 不是什么

**是**：一个**公益拼车工具**。

- 帮乘客从**一个入口**接入多家上游 kiro vendor
- 加一层**决策模型**（比价 · fallback · 集单）
- 提供**号池承载与监控**（号池能力全部由 kiro.rs 提供）
- **只收技术信息服务费**：每人每轮固定单价（例：1 元/人·轮）

**不是**：

- ✗ 不是**号商** —— 不加价卖号，上游 key 成本 pass-through
- ✗ 不做**上游能做的** —— AWS 开号、vendor 内部号池、发车调度、拼车池调度，全都调 vendor
- ✗ 不做**乘客的下游** —— 乘客的号池是乘客自己搭的，我们只送到
- ✗ **不做超出上游的独立质保** —— 号的质量是 vendor 的产物，跟随 vendor 质保逻辑（详见 §7.5）

## 2. 三大价值

三大价值全部体现在**进货侧**（我们向 6 家 vendor 拉号的那一刻）：

| 价值 | 含义 | 依赖 |
|---|---|---|
| **① 聚合** | 乘客只在 bus-pooling 有一个账号，就能拉到 6 家 vendor 的号 | 我们代持 6 家 vendor 账号（乘客不知情） |
| **② 比价** | 跨 vendor 归一算**有效成本 = 单价 / 平均寿命**（不是只看单价，看"每积分能活多久"）| 各家 vendor 单价字段口径拉齐；vendor × 时间窗口 → 平均寿命统计（详见 `01 §2 Layer 3e`） |
| **③ Fallback** | 一家缺货 / 死了 → 自动改另一家 | 订阅 6 家 stock / status / webhook |

**衍生的第四价值（核心业务）：拼车集单**

- 多个乘客同一策略窗口内的需求合并 → 一次向 vendor 批量拉
- 好处 1：吃到 vendor 的**阶梯低价档**（母号累计产量分档，量大更便宜）
- 好处 2：**摊薄上游 key 成本**（20 元的 key，N 人拼 → 每人 20/N 元）
- 好处 3：摊薄"每次开号 / 发车"的固定手续费（部分 vendor 有）

## 3. 计费模型

### 三笔钱各归其位

```
乘客账户流水 =
    充值端：入账积分 - 通道费（pass-through，充值时扣）
    消费端：号价（pass-through，一轮内多人拼车按 N 分摊）
          + 我方服务费（每人每轮固定）
```

**通道费（Payment Gateway）**：

- 目前渠道：`waffo`，收 **5%**
- **pass-through 给乘客**（乘客承担，我方不吃差价）
- 例：乘客充值 100 → 我方收到 95 → 乘客到账**95 积分**
- payment-gateway 已经打通；bus-pooling 只做它的 client（详见 `01-architecture.md` Layer 3a）

**上游 key 成本（pass-through，我们不加价）**：

- 独享 1 人：20 元 → 一人吃 20 元
- 拼车 N 人：20 元 → 每人 20/N 元

**我们的技术信息服务费（固定，不分摊）**：

- 每人每轮固定单价（例：1 元/人·轮）
- 独享 1 人 · 18 轮：1 × 18 = 18 元
- 拼车 3 人 · 18 轮：1 × 18 × 3 = 54 元（每人 18 元，我们收 54）

### 我们的获利模型

```
我们收入 = Σ(乘客参与轮数) × 固定单价
```

**推导出的对齐激励**：

- 我们**没有动机加价号成本**（加了也不进自己口袋）
- 我们**有动机推拼车**（人越多我们越多 & 乘客号价越便宜）
- 我们**没有动机囤号**（囤号 = 乘客不拉 = 没服务费）
- 我们**有动机保号池存活**（号死 → 乘客停拉 → 停收费）

**其他收费点**：TBD，先跑通固定服务费再说。

## 4. 分层

```
上游进货侧
┌─ 6 家 vendor（我们代持账号）
│    91kiro / kiro.ceo / kiro.ooo /
│    kiroapp.io / kiroapp.cc / drop.kiro.ss
└─ 各家档案见 docs/vendors/*.md

           │ 拉号
           ▼
bus-pooling 本体（Go 服务）
┌─ 乘客账号 / 积分 / 兑换码
├─ 策略引擎（自动 · 手动 · 上限 · 拼车/独享）
├─ 集单调度（拼车窗口合流）
├─ 跨 vendor 决策（聚合 · 比价 · fallback）
└─ 每轮固定中间费计费

           │ BatchImport
           ▼
我们的 kiro.rs 号池（已搭好，kiro.aibbq.xyz）
─ credential 存储与加密
─ 分组（每乘客一个 group）
─ 下发 client_key
─ 存活监控 / 封号检测
─ 号池管理能力全部由 kiro.rs 承担，我们不复刻

           │ 交付
           ▼
下游 · 两种方式并存
┌─ 去向 ②：推到乘客自己的 kiro.rs（双写监控副本）
│    乘客配 url + token → 我们做 kiro.rs → kiro.rs 的 BatchImport
│    号仍在我们池里，我们跟踪存活；号死清理后进下一轮
│
└─ 去向 ③：拿走号数据（离开系统，我方不监控）
     我们的 API 端点形状对齐 vendor（GET /stock、POST /claim、webhook）
     多出的是策略层参数
     去向 ③ 是唯一"发出去不管"的路径
```

## 5. 用户路径

```
乘客（在 bus-pooling 一个账号）
    │
    ├── 充值：兑换码 / payment-gateway（waffo 5% pass-through）→ 积分
    │
    ├── 两个主入口（用户拉号的两个起点）
    │     │
    │     ├── 主入口 · 拼车（最大价值）
    │     │     ─ 建 bus（1 人或多人）
    │     │     ─ 拼车动作触发拉号，号 vendor → housepool 的 bus group
    │     │     ─ 手动拼车 / 自动拼车都是这条路径
    │     │
    │     └── 次入口 · 单独拉号
    │           ─ 选 vendor + 数量，拉一批号
    │           ─ 号进"拉号记录"（数据库表，不进池，不监控）
    │           ─ 用户后续对每号选一个去向 ▼
    │
    ├── 号的 3 种去向（去向 1/2 进池监控；去向 3 离开系统）
    │     ├─ ① 进车 → housepool 的 bus group（进池，监控）
    │     ├─ ② 推给自己号池 → 双写：housepool 保留监控副本 + passengerpool 乘客用
    │     └─ ③ 拿走号数据 → 号离开系统，不监控（用户自己怎么处理是他的事）
    │
    ├── 2 种触发入口（都能触发上面 3 种去向）
    │     ├─ UI 触发
    │     └─ API 触发
    │
    ├── 策略参数（自动模式起作用）
    │     ─ 是否开启自动 / 每轮拉多少 / 最少多少
    │     ─ 单价上限 / 每日上限
    │     ─ 补车规则（bus 存活跌破水位触发新一轮拉）
    │     ─ 目标 bus（哪辆车）
    │
    └── housepool 里的号：号死 → 踢出 group → 分组跌水位 → 触发补车
```

**核心不变量**：

- **拼车是主入口**（最大价值）；单独拉号是次入口
- **拉号 ≠ 进池**：拼车触发的号直接进池（bus group）；单独拉号进"拉号记录"（不进池）
- **推给乘客号池 = 双写**：housepool 永远保留副本用于监控，乘客那侧是**复制**
- **只有"拿走号数据"才离开系统**——那 3 个号相当于用户拉走自己处理，我们不留、不管
- **API 是入口方式，不是去向**（API 也能触发 3 种去向的任一种）

## 6. 我们做 / 不做（明单）

**我们做**：

- 乘客账号 · 积分 · 兑换码 · 计费流水
- 策略引擎与参数配置
- 集单调度（拼车窗口）
- 跨 vendor 决策（聚合 · 比价 · fallback）
- vendor 的 API 客户端与 webhook 接收
- 我们的对下游 API 与 webhook 出向
- kiro.rs 承载调度（作为 kiro.rs 的客户端）

**我们不做**：

- ✗ AWS 开号 / 母号管理 / 发车（调 vendor）
- ✗ vendor 内部号池调度（调 vendor）
- ✗ vendor 内部拼车（调 vendor）
- ✗ 号池的存储/分组/客户端 key 下发（调 kiro.rs）
- ✗ 号池存活探测底层（调 kiro.rs）
- ✗ 乘客的下游业务（不知情）

## 7.5 业务规则（跨阶段一致，不因阶段变化）

### 规则 A · 号死处理：上游死 → 下游停 → 进入新一轮

- 号从 kiro.rs 侧被判死（`credential.status = dead` 或 vendor webhook `all_keys_dead`）→ 立即从**分组的 client_key 可用池**里踢出
- **不复用、不复活、不硬撑**
- 该分组内还有存活号 → 继续用剩余的
- 该分组内**全部死光** → 触发**新一轮拉号**（走同一套策略参数 / 决策模型 / 集单窗口）
- 去向 ①（进车 bus group）和 去向 ②（推 passengerpool 双写）由我方跟踪存活；去向 ③ handoff（拿走号数据）号离开系统，我方不再跟踪

### 规则 B · 质保跟随上游，不做独立质保

- 我方**不承诺**号的可用时长，也**不承诺**任何质量指标
- 质保逻辑**完全跟随上游**：
  - 上游 vendor 判定该号在其质保窗口内失效 → 上游退我方 → 我方**按比例退乘客积分**（拼车按 N 分摊比例退）
  - 上游过窗口不退 → **我方也不退**
- 各家 vendor 质保规则不一致（10 分钟、其他窗口、`refund` ledger 类型等），见 `docs/vendors/*.md` §13
- **技术服务费不退**（服务已交付：拉号动作本身发生了）

### 规则 C · 号价 pass-through，服务费固定

已在 §3 定义，此处强调它是**跨阶段不变的约束**：号价永远直传 vendor 单价，服务费永远按人·轮固定。任何阶段引入新功能都不得违反。

## 8. 术语（与 vendor 档案对齐）

### 8.1 平台角色 / 上游

| 中文 | 英文命名 | 含义 |
|---|---|---|
| Provider | `provider` | 上游协议族（当前只有 `kiro`；未来可能 `cursor` 等） |
| Vendor | `vendor` | 同 provider 下的具体供应源，每家独立域名 / 认证 / 契约（见 `docs/vendors/*.md`） |
| Vendor 账号 | — | 我方在 vendor 那里的账号（乘客不知情） |
| 乘客 | `passenger` | bus-pooling 的终端用户 |
| 我方号池 | `housepool` | 我方运维的 kiro.rs（Layer 4） |
| 乘客号池 | `passengerpool` | 乘客自己运维的号池（去向 ② 双写的目标，外部系统） |
| 号 / Key | `credential` | housepool 里一份 credential，具体形态由 vendor 决定（`ksk_` / `{key,account,password,issuer_url}` / etc.） |

### 8.2 入口 · 拉号 · 号的 3 种去向

| 中文 | 英文命名 | 含义 |
|---|---|---|
| 一轮 | `round` | 一次拉号动作。**服务费按人按轮固定** |
| 拉号 | `pull` | 从 vendor 取号 |
| **主入口 · 拼车** | `bus entry` | 建 bus → 拼车动作触发拉号，号**直接进 bus group（进池）** |
| **次入口 · 单独拉号** | `solo pull entry` | 用户手动/API 拉一批号 → 号进"拉号记录" → 用户后续再定去向 |
| 车 / bus | `bus` | 拼车局实体（1 人或多人都是 bus）。housepool 里对应 `bus-<bus_id>` group |
| 拉号记录 | `pull record` | 数据库表。装单独拉号后**未定去向**的号，**不进池、不监控** |
| 系统撮合 | `anonymous match` | 匿名拼车：系统按标签匹配成员进同一 bus |
| 邀请码组队 | `invite team` | 认识的人主动组车：建 bus + 邀请码分发 |
| 补车 | `refill` | bus 内号死后触发新一轮拉号，补回目标水位 |
| 集单 | `coalesce` | 同 bus 多成员补车意图在窗口内合流成一次拉号 |
| 意图 | `intent` | 策略引擎产出的"要拉多少号 / 目的 bus 是谁 / 去向" |

**号的 3 种去向**（不管 UI 触发还是 API 触发，去向都是这 3 种之一）：

| 去向 | 英文 | 号最终所在 | 我方监控 |
|---|---|---|---|
| ① 进车 | `to-bus` | housepool 的 `bus-<bus_id>` group | ✓ |
| ② 推给自己号池 | `to-passengerpool` | **双写**：housepool 保留副本 + passengerpool（乘客用） | ✓ 靠 housepool 副本 |
| ③ 拿走号数据 | `handoff` | 离开系统（用户自己拿走处理） | ✗ 不监控 |

**触发入口 2 种**：UI 触发 / API 触发。**API 不是"一种去向"**，它是**操作方式**，能触发任意 3 种去向。

### 8.3 治理 / 未来

| 中文 | 英文命名 | 含义 |
|---|---|---|
| 压车 | `hog` / noisy neighbor | bus 内某成员 RPM/TPM 过高触发 429，连累全车 |
| 发车 | `dispatch` | 乘客上传 AWS 凭证 → 我方转发 vendor → vendor 开号（阶段 3b/3c） |

### 8.4 计费

| 中文 | 英文命名 | 含义 |
|---|---|---|
| 号价 | `key_cost` | 上游 vendor 单价，pass-through 分摊到参与者 |
| 服务费 | `service_fee` | 我方收入，每人每轮固定 |
| 通道费 | `channel_fee` | payment-gateway 收（waffo 5%），pass-through 给乘客 |

### 8.5 交付实现（去向 ② 与 ③ 的技术形式）

| 中文 | 英文命名 | 含义 |
|---|---|---|
| 推 passengerpool | `push` | 去向 ②：**双写** —— housepool 保留监控副本 + 复制到乘客 kiro.rs |
| 拿走 | `handoff` | 去向 ③：号数据交给用户（UI 下载 / API 返回原始 credential），不留副本 |

**入口 vs 去向**：

- **UI** / **API** = 入口（谁怎么触发动作）
- **进车 / 推 passengerpool / 拿走** = 去向（号最终去哪）
- 早期讨论出现过的"方式 A / 方式 B"**作废**（那把入口和去向糊在一起）
