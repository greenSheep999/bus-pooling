# bus-pooling · 三大价值 & 分层与阶段

> 前置阅读：[`docs/vendors/`](./vendors/) 里六份 vendor 官方 API 档案。
> 本文只写共识（"我们是什么/不是什么"、三大价值、阶段），不预先设计尚未对齐的细节。

## 1. bus-pooling 是什么 / 不是什么

**是**：一个**公益拼车工具**。

- 帮乘客从**一个入口**接入多家上游 kiro vendor
- 加一层**决策模型**（比价 · fallback · 集单）
- 提供**号池承载与监控**（号池能力全部由 kiro.rs 提供）
- **收技术信息服务费 + 加价**：服务费是加价链最后一层（按率）· 加价栈见 §3（`decisions §8.34`）

**不是**：

- ✗ 不是**号商** —— 不加价卖号，上游 key 成本 pass-through
- ✗ 不做**上游能做的** —— AWS 开号、vendor 内部号池、发车调度、拼车池调度，全都调 vendor
- ✗ 不做**乘客的下游** —— 乘客的号池是乘客自己搭的，我们只送到
- ✗ **不做超出上游的独立质保** —— 号的质量是 vendor 的产物，跟随 vendor 质保逻辑（详见 §7.5）

## 2. 三大价值

三大价值全部体现在**进货侧**（我们向 6 家 vendor 拉号的那一刻）：

| 价值 | 含义 | 依赖 |
|---|---|---|
| **① 聚合** | 乘客只在 bus-pooling 有一个账号，就能拉到 6 家 vendor 的号 | 我们代持 6 家 vendor 账号（乘客不知情） |
| **② 比价** | 跨 vendor 归一算**有效成本 = 单价 / 平均寿命**（不是只看单价，看"每积分能活多久"）| 各家 vendor 单价字段口径拉齐；vendor × 时间窗口 → 平均寿命统计（详见 `01 §2 Layer 3e`） |
| **③ Fallback** | 一家缺货 / 死了 → 自动改另一家 | 订阅 6 家 stock / status / webhook |

**衍生的第四价值（核心业务）：拼车集单**

- 多个乘客同一策略窗口内的需求合并 → 一次向 vendor 批量拉
- 好处 1：吃到 vendor 的**阶梯低价档**（母号累计产量分档，量大更便宜）
- 好处 2：**摊薄上游 key 成本**（20 元的 key，N 人拼 → 每人 20/N 元）
- 好处 3：摊薄"每次开号 / 发车"的固定手续费（部分 vendor 有）

## 3. 计费模型

### 收费点清单（跨阶段一致 · **逐层乘**）

```
乘客一次拉号单价 =
    号价（vendor 报价 · 按 vendor_pricing 换算成积分）
      × (1 + vendor 附加费)      每家可不同
      × (1 + 区域附加费)         **有系统邀请码则跳过这一层**
      × (1 + 单次议价)           仅 count == 1
      × (1 + 插槽 1) × (1 + 插槽 2) …   动态增减
      × (1 + 服务费率)
  = 用户看到的最终单价

本次扣除 = 最终单价 × 号数
（充值时另收）通道费 → 个人邀请码可在限额内减免
（提号确认窗）随机优惠码 → 在上面结果上再打折
```

**逐层乘，不是加在号价上**（`decisions §8.34`）：每一层乘在上一层的结果上。

两个好处：
- **顺序无关** —— 乘法可交换，不用像加法那样额外规定"加在号价上还是加在小计上"
- **加插槽不用重算基数** —— 再插一条就是再乘一个因子，跟已有规则无关

**阶段 1a 的链只有 `号价 × (1+单次议价) × (1+服务费率)`** —— vendor 附加费和区域附加费是 1b（`decisions §8.30 §8.32`），插槽阶段 1 无实例。

### 三档定价（`decisions §8.39` 定稿 · 1b 落地）

`passenger.tier` 决定跳过哪些层。每档"多减一层"：

| 对外档 | tier | 谁 | 减免层 | 相对倍率 |
|---|---|---|---|---|
| **零售价** | `retail` | 散客 · 无码注册 | 无 · 全套加价 | 2.00× |
| **批发价** | `wholesale` | TG/Discord 社群 · 用**社群码**注册 | 免区域附加费 | ~1.67× |
| **同行价** | `insider` | 同行群 · 用**同行码**注册 | 免 vendor + 区域附加费 | 1.00× |

**算例**（号价 20 积分 · 拉 5 个号 · 服务费 5% 恒定）：

| 层 | 零售 | 批发 | 同行 |
|---|---|---|---|
| 号价 | 20.00 | 20.00 | 20.00 |
| × vendor 附加费 67% | ×1.67 → 33.40 | ×1.67 → 33.40 | ~~跳过~~ |
| × 区域附加费 20% | ×1.20 → 40.08 | ~~跳过~~ | ~~跳过~~ |
| × 服务费 5% | ×1.05 → **42.08** | ×1.05 → **35.07** | ×1.05 → **21.00** |
| 每号 USD | 6.01 | 5.01 | 3.00 |

**服务费所有档都收** —— 单一 5% 恒定 · 不分档。

### 四种码各减免哪一项

（完整对照见 `decisions §8.42` 四码分离 + `docs/10-pricing §2.1`）：

| 用户侧叫 | 内部字段 | 减免 | 持久性 |
|---|---|---|---|
| **专属邀请码**（community 版）| `system_invite_code` · `grants_tier=community` | 跳 zone 减免 | 永久绑账号 |
| **专属邀请码**（wholesale 版）| `system_invite_code` · `grants_tier=wholesale` | 跳 vendor + zone 减免 · **只有它能看 vendor 真名** | 永久绑账号 |
| **邀请码**(好友邀请)| `personal_invite_code` | 发码人得手续费/通道费减免额度(必须有硬上限) | **限次数 / 限时** · 用完恢复 · **不改被邀请人 tier** |
| **优惠码**（支付 / 提号时）| `coupon_code` | 单次提号价 5~20%（后台可配） | 单次 · **不改 tier · 不建 referral** |

**对外**:两种专属邀请码 UI 上都叫「专属邀请码」——用户只需要输入 · 后端按码定 tier · **不暴露 community/wholesale 内档**。**只有 wholesale 能看 vendor 真名** —— community 也不看。

**通道费不在这条链里** —— 它在**充值**时收一次（`decisions §8.21`），不在每次拉号时扣。

**充值端**：
- 乘客想充 100 积分 → 通道费 = 100 × 5% = 5 积分 → 折 105 CNY → 按 7 CNY/USD 显示 **15 USD** 走 waffo → 内部记两笔：`recharge +105` + `channel_fee −5` → 乘客净 +100 积分（详见 CLAUDE.md §1.4）

**通道费（Payment Gateway）**：

- 目前渠道：`waffo`，收 **5%**
- **pass-through 给乘客**（乘客承担，我方不吃差价）
- 例：乘客充值 100 → 我方收到 95 → 乘客到账**95 积分**
- payment-gateway 已经打通；bus-pooling 只做它的 client（详见 `01-architecture.md` Layer 3a）

**上游 key 成本（pass-through，我们不加价）**：

- 1 人 bus：20 元 → 一人吃 20 元
- 拼车 N 人：20 元 → 每人 20/N 元

**单次议价**（`count == 1` 时触发）：

- 拉号 `count == 1` → 号价 × 20%（我方收入）
- 拉号 `count >= 2` → **0**（批量无议价，天然鼓励批量）
- 逻辑：单次占用一整轮资源却只出 1 个号，等于把拼车的规模优势排除掉了

**附加能力费（插槽，未来可扩展多项）**：

- 每项附加能力独立触发（用户主动勾选 or 策略参数隐含触发）
- 每项独立议价率（例：+20% × 号价）
- 多项累加
- **阶段 1 无实例**（先把插槽预留；具体附加能力等 §9 未决里的候选进入实施再定名字 / 维度 / 权限）

**我们的技术信息服务费 · 按率**（`decisions §8.34 §8.39`）：

- 是乘法链里的**最后一层**（`× (1 + 服务费率)`）
- **单一费率，不分档** —— 区分档次是**vendor 附加费 / 区域附加费**那两层的职责（`tier` 决定跳过哪几层）
- 正因为它乘在**已加价的金额**上，零售用户的服务费绝对额自动比批发 / 同行高 —— **不需要再按档设服务费率**
- 具体费率是**内部配置**（后台可调），不写进代码也不下发前端

### 我们的获利模型

```
我方每号收入 = 号价 × (总倍率 − 1)
             其中 总倍率 = (1+vendor)(1+区域)(1+议价)(1+插槽…)(1+服务费率)
我方总收入   = Σ(交付的号数 × 号价 × (总倍率 − 1))
```

**主收入是 vendor 附加费那一层**（`decisions §8.34`）—— 服务费率在整条链里占比很小，是零头不是主项。定价心智上别搞反：调整收入规模靠 vendor 附加费，服务费率不是杠杆。

**保留的对齐激励**：

- 我们**有动机多交付号**（收入按交付号数累加 · 跟乘客"想拿到号"同向）
- 我们**有动机推拼车**（人越多号越多 & 乘客分摊后每人更便宜）
- 我们**没有动机囤号**（囤号 = 没交付 = 没收入）
- 我们**有动机保号池存活**（号死 → 乘客停拉 → 停收费）

**⚠️ 已经失效的那一条 —— 诚实记录**：

早期版本写过「我们**没有动机加价号成本**（加了也不进自己口袋）」，因为那时收入 = Σ轮数 × **固定**单价，跟号价无关。

**加价栈改成按号价逐层乘之后，这条不再成立** —— 现在几乎全部收入都是号价的百分比，**号价涨我方就赚更多**。

- 这不是设计失误，是**有意的取舍**：vendor 附加费本来就是正常的加价生意，靠固定小额服务费养不起运维
- 但**别再对外声称"我方没有动机加价号成本"** —— 那句话现在是假的
- 仍然成立的替代表述：**我方没有动机把号价抬到乘客不拉的程度**（拉不动 = 零交付 = 零收入），所以定价上限被需求侧约束着

### 退款原则（跨场景一致）

- **我方对乘客只退积分**（wallet + ledger），**不退款 / 不退现金**
- 通道费一旦付给 payment-gateway 就是乘客承担的沉没成本，我方不代扣代付
- 详见 §7.5 规则 B

```
上游进货侧
┌─ 6 家 vendor（我们代持账号）
│    91kiro / kiro.ceo / kiro.ooo /
│    kiroapp.io / kiroapp.cc / drop.kiro.ss
└─ 各家档案见 docs/vendors/*.md

           │ 拉号
           ▼
bus-pooling 本体（Go 服务）
┌─ 乘客账号 / 积分 / 兑换码
├─ 策略引擎（自动 · 手动 · 上限 · 拼车/独享）
├─ 集单调度（拼车窗口合流）
├─ 跨 vendor 决策（聚合 · 比价 · fallback）
└─ 每轮固定中间费计费

           │ BatchImport
           ▼
我们的 kiro.rs 号池（已搭好，kiro.aibbq.xyz）
─ credential 存储与加密
─ 分组（每乘客一个 group）
─ 下发 client_key
─ 存活监控 / 封号检测
─ 号池管理能力全部由 kiro.rs 承担，我们不复刻

           │ 交付
           ▼
下游 · 两种方式并存
┌─ 去向 ②：推到乘客自己的 kiro.rs（双写监控副本）
│    乘客配 url + token → 我们做 kiro.rs → kiro.rs 的 BatchImport
│    号仍在我们池里，我们跟踪存活；号死清理后进下一轮
│
└─ 去向 ③：拿走号数据（离开系统，我方不监控）
     我们的 API 端点形状对齐 vendor（GET /stock、POST /claim、webhook）
     多出的是策略层参数
     去向 ③ 是唯一"发出去不管"的路径
```

## 5. 用户路径

```
乘客（在 bus-pooling 一个账号）
    │
    ├── 充值：兑换码 / payment-gateway（waffo 5% pass-through）→ 积分
    │
    ├── 两个主入口（用户拉号的两个起点）
    │     │
    │     ├── 主入口 · 拼车（最大价值）
    │     │     ─ 建 bus（1 人或多人）
    │     │     ─ 拼车动作触发拉号，号 vendor → housepool 的 bus group
    │     │     ─ 手动拼车 / 自动拼车都是这条路径
    │     │
    │     └── 次入口 · 单独拉号
    │           ─ 选 vendor + 数量，拉一批号
    │           ─ 号进 housepool 的 `record-<pid>` group（disabled=true，不发下游）
    │           ─ 已进池、有监控；等用户派去向 ▼
    │
    ├── 号的 3 种去向（去向 1/2 进池监控；去向 3 离开系统）
    │     ├─ ① 进车 → housepool 的 bus group（进池，监控）
    │     ├─ ② 推给自己号池 → 双写：housepool 保留监控副本 + passengerpool 乘客用
    │     └─ ③ 拿走号数据 → 号离开系统，不监控（用户自己怎么处理是他的事）
    │
    ├── 2 种触发入口（都能触发上面 3 种去向）
    │     ├─ UI 触发
    │     └─ API 触发
    │
    ├── 策略参数（自动模式起作用）
    │     ─ 是否开启自动 / 每轮拉多少 / 最少多少
    │     ─ 单价上限 / 每日上限
    │     ─ 补车规则（bus 存活跌破水位触发新一轮拉）
    │     ─ 目标 bus（哪辆车）
    │
    └── housepool 里的号：号死 → 踢出 group → 分组跌水位 → 触发补车
```

**核心不变量**：

- **拼车是主入口**（最大价值）；单独拉号是次入口
- **所有拉的号都进 housepool**（monitoring 是硬需求）—— 差别只在 group 与 disabled 状态：
  - 拼车触发 → `bus-<bus_id>` group, `disabled=false`
  - 单独拉号 → `record-<pid>` group, `disabled=true`（等派去向）
- **改去向 = 改 group + 改 disabled**（kiro.rs `PUT /credentials/{id}`）
- **推给乘客号池 = 双写**：housepool 永远保留副本用于监控，乘客那侧是**复制**
- **只有"拿走号数据"才真正离开系统**（kiro.rs `DELETE /credentials/{id}`）—— 唯一 fire-and-forget 的路径
- **API 是入口方式，不是去向**（API 也能触发 3 种去向的任一种）

## 6. 我们做 / 不做（明单）

**我们做**：

- 乘客账号 · 积分 · 兑换码 · 计费流水
- 策略引擎与参数配置
- 集单调度（拼车窗口）
- 跨 vendor 决策（聚合 · 比价 · fallback）
- vendor 的 API 客户端与 webhook 接收
- 我们的对下游 API 与 webhook 出向
- kiro.rs 承载调度（作为 kiro.rs 的客户端）

**我们不做**：

- ✗ AWS 开号 / 母号管理 / 发车（调 vendor）
- ✗ vendor 内部号池调度（调 vendor）
- ✗ vendor 内部拼车（调 vendor）
- ✗ 号池的存储/分组/客户端 key 下发（调 kiro.rs）
- ✗ 号池存活探测底层（调 kiro.rs）
- ✗ 乘客的下游业务（不知情）

## 6.5 功能优先级矩阵

**三个分类**（这跟 §7 阶段是**正交**的两个维度：**分类**决定"该不该做"，**阶段**决定"什么时候做"）：

| 分类 | 含义 | 决策规则 |
|---|---|---|
| 🟥 **核心保障** | 缺了产品不成立、跑不通 | **必须做**，无条件 |
| 🟨 **加分项** | 提升体验 / 效率 / 决策质量，但不阻塞主流程 | 按阶段推进；砍功能时**从这里砍**，别砍 🟥 |
| 🟩 **衍生收益空间** | 未来利润点 / 差异化 | 不阻塞主线；等条件（数据 / 通道 / 用户量）成熟再评估 |

### 🟥 核心保障（22 项）

**账户 / 钱**：
- 乘客账号（注册 / 登录 / API key）→ `passenger` / `authpassenger`
- 积分钱包 + 流水 → `wallet`
- 兑换码充值 → `redeem`
- payment-gateway 充值（waffo）+ 通道费 pass-through → `payment`

**拉号主链**：
- vendor 拉号（**首家 91kiro**）→ `providers/kiro/vendors/kiro91`
- 6 家 vendor 全量接入 → `providers/kiro/vendors/*`（阶段 1b）
- 号价 pass-through + 服务费 1/1 → `decider` + `wallet`
- 单次议价 +20%（`count==1`）→ `decider`
- housepool 承载（credential 校验/探活/用量/分组/并发）→ `housepool/kirors`
- 号死自动补车 → `deathwatch`
- 质保退款（跟随上游，按 N 分摊退积分）→ `deathwatch` + `wallet`

**Bus 主入口**：
- 建 bus / 拉号进 bus / 退出 / 解散 → `bus` + `strategy` + `decider`
- 1 人 bus + 匿名撮合多人 bus（`kind: single/anon`）→ `bus` + `coalescer/anon`
- Bus 补车集单 → `coalescer`

**单独拉号次入口**：
- 单独拉号进 `record-<pid>` group（disabled=true）→ `pullrecord`
- 派去向（进车 / 推 passengerpool / handoff）→ `pullrecord` + `delivery/*`

**下游交付**：
- 推 passengerpool 双写 → `delivery/passengerpool/kirors`
- Handoff 拿走 → `delivery/handoff`

**基础配置**：
- 乘客配 passengerpool url + token（`downstream_config`）
- 乘客配对外 webhook + 我方推送 → `webhookout`
- vendor webhook 入向归一化 → `webhookin`

### 🟨 加分项（15 项）

**决策 / 策略**：
- 自动策略引擎（`auto_enabled` + `per_round_count` + `min_count` + `keep_safety_stock` + `max_unit_price` + `daily_round_limit` + `daily_spend_limit`）→ `strategy`（阶段 1d）
- 跨 vendor 比价（有效成本 = 单价 / 平均寿命）→ `decider`（1d）
- Fallback（首选 vendor 挂 → 次选）→ `decider`（1d）
- 平均寿命统计（`vendor_lifespan_snapshot`）→ `deathwatch`（1d）
- 全 vendor 缺货 → 排队等 webhook → `decider` + `webhookin`（1d）

**拼车增强**：
- 列队策略（多 bus 抢同 vendor 排队 + bus 内集单窗口调优）→ `coalescer` + `decider`（2a）
- 压车治理（bus 内 RPM/TPM 探测 + 隔离）→ `deathwatch` + `bus`（2b）

**并发配置**（用户此轮明确列出的散点）：
- 乘客并发上限（`max_rpm` / `max_tpm`）→ `strategy` + `bus`（2c，与压车治理绑定）
- Bus 并发配置（成员容量、每成员 RPM/TPM 分配）→ `bus`（2c）

**数据 / 可视化**：

**运维便利**：
- 单价上限过滤（策略里 `max_unit_price` 拒绝超价拉号）→ `strategy`（1d）
- 每日轮次 / 花费上限自动停 → `strategy`（1d）

### 🟩 衍生收益空间（10 项，全部 ⏸ 或阶段 3+）

- **附加能力插槽**（`capability_fee`，阶段 1 无实例；参考 `decisions §2.6&2.7`）→ `decider` + `capability_slot` 表

  - 其他候选待定

## 7.5 业务规则（跨阶段一致，不因阶段变化）

### 规则 A · 号死处理：上游死 → 下游停 → 进入新一轮

- 号从 kiro.rs 侧被判死（`credential.status = dead` 或 vendor webhook `all_keys_dead`）→ 立即从**分组的 client_key 可用池**里踢出
- **不复用、不复活、不硬撑**
- 该分组内还有存活号 → 继续用剩余的
- 该分组内**全部死光** → 触发**新一轮拉号**（走同一套策略参数 / 决策模型 / 集单窗口）
- 去向 ①（进车 bus group）和 去向 ②（推 passengerpool 双写）由我方跟踪存活；去向 ③ handoff（拿走号数据）号离开系统，我方不再跟踪

### 规则 B · 质保跟随上游，不做独立质保 · **只退积分，不退款**

- 我方**不承诺**号的可用时长，也**不承诺**任何质量指标
- **我方对乘客的退款一律是积分**（`wallet` 加余额 + ledger 落 `warranty_refund`）—— **绝不退现金 / 绝不走 payment-gateway 反向退款通道**
- 质保逻辑**完全跟随上游**：
  - 上游 vendor 判定该号在其质保窗口内失效 → 上游把**积分/余额**退到我方在 vendor 侧的账户 → 我方**按比例退乘客积分**（拼车按 N 分摊比例退）
  - 上游过窗口不退 → **我方也不退**（对乘客既不退积分也不退款）
- 各家 vendor 质保规则不一致（10 分钟、其他窗口、`refund` ledger 类型等），见 `docs/vendors/*.md` §13
- **不退项目**：
  - **技术服务费**（服务已交付：拉号动作本身发生了，无论号后来死没死）
  - **通道费**（已经支付给 payment-gateway / waffo，我方无回收路径）
  - **上游已过窗口的号**（跟随上游）
  - **任何形式的现金 / 银行卡 / 微信 / 支付宝 退款**（我方账户模型只处理积分）

### 规则 C · 号价 pass-through，服务费固定

已在 §3 定义，此处强调它是**跨阶段不变的约束**：**号价永远直传 vendor 单价**（我方不改 vendor 报价本身），加价只通过 §3 那条乘法链上的独立层实现。任何阶段引入新收费点都必须是链上的一层，不得改写号价。

> **修订**（`decisions §8.34`）：本条原写「服务费永远按人·轮固定」—— 那是加法模型时代的说法，现在服务费是链上按率的一层。措辞上禁止的正是 §3 现在的做法，已改。

## 8. 术语（与 vendor 档案对齐）

### 8.1 平台角色 / 上游

| 中文 | 英文命名 | 含义 |
|---|---|---|
| Provider | `provider` | 上游协议族（当前只有 `kiro`；未来可能 `cursor` 等） |
| Vendor | `vendor` | 同 provider 下的具体供应源，每家独立域名 / 认证 / 契约（见 `docs/vendors/*.md`） |
| Vendor 账号 | — | 我方在 vendor 那里的账号（乘客不知情） |
| 乘客 | `passenger` | bus-pooling 的终端用户 |
| 我方号池 | `housepool` | 我方运维的 kiro.rs（Layer 4） |
| 乘客号池 | `passengerpool` | 乘客自己运维的号池（去向 ② 双写的目标，外部系统） |
| 号 / Key | `credential` | housepool 里一份 credential，具体形态由 vendor 决定（`ksk_` / `{key,account,password,issuer_url}` / etc.） |

### 8.2 入口 · 拉号 · 号的 3 种去向

| 中文 | 英文命名 | 含义 |
|---|---|---|
| 一轮 | `round` | 一次拉号动作。**服务费按人按轮固定** |
| 拉号 | `pull` | 从 vendor 取号 |
| **主入口 · 拼车** | `bus entry` | 建 bus → 拼车动作触发拉号，号**直接进 bus group（进池）** |
| **次入口 · 单独拉号** | `solo pull entry` | 用户手动/API 拉一批号 → 号进"拉号记录" → 用户后续再定去向 |
| 车 / bus | `bus` | 拼车局实体（1 人或多人都是 bus）。housepool 里对应 `bus-<bus_id>` group |
| 拉号记录 | `pull record` | **housepool 里的 `record-<pid>` group + `disabled=true`**。号已进池、被监控，但不发下游，等用户派去向 |
| 系统撮合 | `anonymous match` | 匿名拼车：系统按标签匹配成员进同一 bus |
| 拼车码加入 | `join by invite code` | 认识的人主动组车：车主拿**拼车码**(`bus.invite_code`)分享 · 好友输码加入 · **不是**好友邀请码 |
| 补车 | `refill` | bus 内号死后触发新一轮拉号，补回目标水位 |
| 集单 | `coalesce` | 同 bus 多成员补车意图在窗口内合流成一次拉号 |
| 意图 | `intent` | 策略引擎产出的"要拉多少号 / 目的 bus 是谁 / 去向" |

**号的 3 种去向**（不管 UI 触发还是 API 触发，去向都是这 3 种之一）：

| 去向 | 英文 | 底层 kiro.rs 动作 | 号最终所在 | 我方监控 |
|---|---|---|---|---|
| ① 进车 | `to-bus` | `PUT /credentials/{id}` `groups=[bus-X]`, `disabled=false` | housepool `bus-<bus_id>` group | ✓ |
| ② 推给自己号池 | `to-passengerpool` | housepool 保留 + BatchImport 到 passengerpool | **双写** | ✓（靠 housepool 副本）|
| ③ 拿走号数据 | `handoff` | `DELETE /credentials/{id}` | 离开 housepool + 交给用户 | ✗ 唯一"fire-and-forget" |

**触发入口 2 种**：UI 触发 / API 触发。**API 不是"一种去向"**，它是**操作方式**，能触发任意 3 种去向。

### 8.3 治理 / 未来

| 中文 | 英文命名 | 含义 |
|---|---|---|
| 压车 | `hog` / noisy neighbor | bus 内某成员 RPM/TPM 过高触发 429，连累全车 |
| 发车 | `dispatch` | 乘客上传 AWS 凭证 → 我方转发 vendor → vendor 开号（阶段 3b/3c） |

### 8.4 计费

| 中文 | 英文命名 | 归属 | 含义 |
|---|---|---|---|
| 号价 | `key_cost` | vendor | 上游 vendor 单价，pass-through 分摊到参与者 |
| 单次议价 | `single_pull_fee` | 我方 | 拉号 `count == 1` 时加号价 × 20%；`count >= 2` 时 0 |
| 附加能力费 | `capability_fee` | 我方 | 插槽，可累加多项。每项独立议价率、独立触发条件。**阶段 1 无实例** |
| 服务费 | `service_fee` | 我方 | 加价链最后一层 `× (1+率)` · 费率是内部配置（不写进代码 · `decisions §8.34`） |
| 通道费 | `channel_fee` | 通道方（waffo） | 5% × 小计，充值时扣，pass-through 给乘客 |

### 8.5 交付实现（去向 ② 与 ③ 的技术形式）

| 中文 | 英文命名 | 含义 |
|---|---|---|
| 推 passengerpool | `push` | 去向 ②：**双写** —— housepool 保留监控副本 + 复制到乘客 kiro.rs |
| 拿走 | `handoff` | 去向 ③：号数据交给用户（UI 下载 / API 返回原始 credential），不留副本 |

**入口 vs 去向**：

- **UI** / **API** = 入口（谁怎么触发动作）
- **进车 / 推 passengerpool / 拿走** = 去向（号最终去哪）
- 早期讨论出现过的"方式 A / 方式 B"**作废**（那把入口和去向糊在一起）
