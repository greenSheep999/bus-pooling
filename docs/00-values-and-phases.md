# bus-pooling · 三大价值 & 分层与阶段

> 前置阅读：[`docs/vendors/`](./vendors/) 里六份 vendor 官方 API 档案。
> 本文只写共识（"我们是什么/不是什么"、三大价值、阶段），不预先设计尚未对齐的细节。

## 1. bus-pooling 是什么 / 不是什么

**是**：一个**公益拼车工具**。

- 帮乘客从**一个入口**接入多家上游 kiro vendor
- 加一层**决策模型**（比价 · fallback · 集单）
- 提供**号池承载与监控**（号池能力全部由 kiro.rs 提供）
- **只收技术信息服务费**：每人每轮固定单价（例：1 元/人·轮）

**不是**：

- ✗ 不是**号商** —— 不加价卖号，上游 key 成本 pass-through
- ✗ 不做**上游能做的** —— AWS 开号、vendor 内部号池、发车调度、拼车池调度，全都调 vendor
- ✗ 不做**乘客的下游** —— 乘客的号池是乘客自己搭的，我们只送到

## 2. 三大价值

三大价值全部体现在**进货侧**（我们向 6 家 vendor 拉号的那一刻）：

| 价值 | 含义 | 依赖 |
|---|---|---|
| **① 聚合** | 乘客只在 bus-pooling 有一个账号，就能拉到 6 家 vendor 的号 | 我们代持 6 家 vendor 账号（乘客不知情） |
| **② 比价** | 跨 vendor 归一算价，"现在最合算的是哪家" | 各家 vendor 单价字段口径拉齐（CNY / USD / 积分 / 阶梯档 / 手续费） |
| **③ Fallback** | 一家缺货 / 死了 → 自动改另一家 | 订阅 6 家 stock / status / webhook |

**衍生的第四价值（核心业务）：拼车集单**

- 多个乘客同一策略窗口内的需求合并 → 一次向 vendor 批量拉
- 好处 1：吃到 vendor 的**阶梯低价档**（母号累计产量分档，量大更便宜）
- 好处 2：**摊薄上游 key 成本**（20 元的 key，N 人拼 → 每人 20/N 元）
- 好处 3：摊薄"每次开号 / 发车"的固定手续费（部分 vendor 有）

## 3. 计费模型

### 两笔钱完全分开

```
一轮拉号 = 上游 key 成本（pass-through） + 我们的服务费（固定）
```

**上游 key 成本（pass-through，我们不加价）**：

- 独享 1 人：20 元 → 一人吃 20 元
- 拼车 N 人：20 元 → 每人 20/N 元

**我们的技术信息服务费（固定，不分摊）**：

- 每人每轮固定单价（例：1 元/人·轮）
- 独享 1 人 · 18 轮：1 × 18 = 18 元
- 拼车 3 人 · 18 轮：1 × 18 × 3 = 54 元（每人 18 元，我们收 54）

### 我们的获利模型

```
我们收入 = Σ(乘客参与轮数) × 固定单价
```

**推导出的对齐激励**：

- 我们**没有动机加价号成本**（加了也不进自己口袋）
- 我们**有动机推拼车**（人越多我们越多 & 乘客号价越便宜）
- 我们**没有动机囤号**（囤号 = 乘客不拉 = 没服务费）
- 我们**有动机保号池存活**（号死 → 乘客停拉 → 停收费）

## 4. 分层

```
上游进货侧
┌─ 6 家 vendor（我们代持账号）
│    91kiro / kiro.ceo / kiro.ooo /
│    kiroapp.io / kiroapp.cc / drop.kiro.ss
└─ 各家档案见 docs/vendors/*.md

           │ 拉号
           ▼
bus-pooling 本体（Go 服务）
┌─ 乘客账号 / 积分 / 兑换码
├─ 策略引擎（自动 · 手动 · 上限 · 拼车/独享）
├─ 集单调度（拼车窗口合流）
├─ 跨 vendor 决策（聚合 · 比价 · fallback）
└─ 每轮固定中间费计费

           │ BatchImport
           ▼
我们的 kiro.rs 号池（已搭好，kiro.aibbq.xyz）
─ credential 存储与加密
─ 分组（每乘客一个 group）
─ 下发 client_key
─ 存活监控 / 封号检测
─ 号池管理能力全部由 kiro.rs 承担，我们不复刻

           │ 交付
           ▼
下游 · 两种方式并存
┌─ 方式 A：推到乘客自己的 kiro.rs
│    乘客配 url + token → 我们做 kiro.rs → kiro.rs 的 BatchImport
│    号仍在我们池里，我们跟踪存活；号死清理后进下一轮
│
└─ 方式 B：乘客调我们的 API 拿走
     我们的 API 端点形状对齐 vendor（GET /stock、POST /claim、webhook）
     多出的是策略层参数
     发出去后我们不再跟踪
```

## 5. 用户路径

```
乘客（在 bus-pooling 一个账号）
    │
    ├── 充值：兑换码 / 支付渠道（P0 先只做兑换码）→ 积分
    │
    ├── 拉号触发（二选一）
    │     ┌─ 手动：UI 点一次，可指定 vendor 或让我们选
    │     └─ 自动：配好策略参数，我们按规则代拉
    │
    ├── 策略参数（自动模式起作用）
    │     ─ 是否开启自动
    │     ─ 每轮拉多少个 / 最少多少个
    │     ─ 是否保留兜底（安全库存跌破补充）
    │     ─ 单价上限（超过不拉）
    │     ─ 每日上限（轮次 / 累计花费）
    │     ─ 拼车 / 独享
    │
    ├── 我们代拉：跨 vendor 比价 + fallback + 集单 → kiro.rs 号池
    │
    └── 交付：方式 A（推到乘客 kiro.rs）/ 方式 B（乘客调我们 API）
```

## 6. 我们做 / 不做（明单）

**我们做**：

- 乘客账号 · 积分 · 兑换码 · 计费流水
- 策略引擎与参数配置
- 集单调度（拼车窗口）
- 跨 vendor 决策（聚合 · 比价 · fallback）
- vendor 的 API 客户端与 webhook 接收
- 我们的对下游 API 与 webhook 出向
- kiro.rs 承载调度（作为 kiro.rs 的客户端）

**我们不做**：

- ✗ AWS 开号 / 母号管理 / 发车（调 vendor）
- ✗ vendor 内部号池调度（调 vendor）
- ✗ vendor 内部拼车（调 vendor）
- ✗ 号池的存储/分组/客户端 key 下发（调 kiro.rs）
- ✗ 号池存活探测底层（调 kiro.rs）
- ✗ 乘客的下游业务（不知情）

## 7. 分阶段

| 阶段 | 目标 | 核心边界 |
|---|---|---|
| **P0 · 单 vendor 拉存推** | 一个 vendor（91kiro）+ 单乘客手动拉一次 → 进 kiro.rs → 交付方式 B（API 拿走） | 无策略引擎、无自动、无拼车、无比价 |
| **P1 · 兑换码 + 手动多 vendor** | 加兑换码充值；乘客可 UI 选 vendor；6 家都接入；下游方式 A（推 kiro.rs） | 仍是手动，一次一乘客 |
| **P2 · 比价 & fallback** | 决策引擎："当前最合算 X"、"X 挂了走 Y"；订阅 6 家 webhook 归一化事件 | 仍是手动/单乘客单轮 |
| **P3 · 自动策略引擎** | 每轮/每日上限、保留兜底、单价上限；自动模式跑起来 | 单人策略，无集单 |
| **P4 · 拼车集单** | 同窗口多乘客需求合流一次向 vendor 拉；号价按 N 分摊；服务费按人按轮 | 核心变现开跑 |
| **P5+** | 上游存活/价格订阅推给乘客；下游 A/B 两种交付模式打磨；其他收费点探索 | 待 P4 之后再看 |

**每阶段完成标准**：能跑通一条端到端主流程 + 该阶段引入的每个新能力有一个可回归的测试。

**每阶段不做的事**：本表右列列出后再引入的一律不做，避免重蹈旧项目 90+ 模块 60+ 文档的覆辙。

## 8. 术语（与 vendor 档案对齐）

| 术语 | 含义 |
|---|---|
| Provider | 上游协议族（当前只有 `kiro`；未来可能 `cursor` 等） |
| Vendor | 同 provider 下的具体供应源，每家独立域名 / 认证 / 契约（见 `docs/vendors/*.md`） |
| Vendor 账号 | 我方在 vendor 那里的账号（乘客不知情） |
| 乘客 | bus-pooling 的终端用户 |
| 号池 | kiro.rs 承载的 credential 集合 |
| Key | 号池里一份 credential，具体形态由 vendor 决定（`ksk_` / `{key,account,password,issuer_url}` / etc.） |
| 一轮 | 一次拉号动作。计费单位 |
| 集单 | 同策略窗口内多乘客的订单合流 |
| 拼车 | 集单 + 上游 key 成本按 N 分摊 |
| 独享 | 单乘客单独一轮，号价一人吃 |
| 交付方式 A | 推到乘客自己的 kiro.rs（号仍在我们池里） |
| 交付方式 B | 乘客调我们 API 拿走（发出去不管） |
